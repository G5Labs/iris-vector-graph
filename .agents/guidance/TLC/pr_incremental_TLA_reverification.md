# PR incremental TLA+ / TLC reverification

Guidance for incremental TLA+/TLC reverification of a pull request, covering PR scope, exact operation correspondence and supported input domains. Apply when PR reverification is requested; this file does not itself start a run. Use the repository’s existing tools and evidence locations and the shared [model-checking mechanics](model-checking.md). A reverification request continues this maintenance workflow; it does not restart [TLA+/TLC design](tla-design.md).

Re-establish the ontology, model applicability and verification affected by this PR, carrying forward established unaffected guarantees from the foundation.

Your primary deliverable is an evidence-backed answer that this maintenance goal has been achieved, or precisely which required obligations prevent it. Discovering and fixing bugs contributes to that goal. Updating files, matching every declared TLC expectation, or completing a checklist does not alone establish it.

Work in this checkout using only designated requirements, references and foundation evidence. Start with the project’s verification README under `.g5/TLA_verification/` or its existing equivalent. Follow its local instructions for validating receipts, running affected checks and recording applicability. In an older foundation without a runbook, inspect the existing runner, manifests and saved receipts. Read the baseline description if present. Do not consult branches, sessions, assessment findings or solution artifacts from other verification tasks. Use existing verification tools and collectors; do not build an agent harness or replacement maintenance framework. Do not push, merge, promote a trusted baseline or launch a separate verification task.

1. Establish the baseline and obligation ledger.

Pin the actual pre-PR product, current product, accepted requirements/ontology, verification foundation and relevant tool/dependency identities. Distinguish the foundation's demonstrated guarantees from unsupported claims and inherited gaps. State the assurance level being preserved: bounded model checking, tested/reviewed correspondence, checked implementation proof, or their explicit combination. Do not silently lower that level or claim stronger evidence than the foundation provides.

Inspect the complete dependency paths needed to establish the PR's required behavior, including unchanged code. Before a production repair, establish whether the defect was introduced or worsened by this PR against the actual pre-PR product. Repair those defects, including regressions from these repairs. Report pre-existing product defects without repairing them unless separately authorized, even when relevant to this PR. If the PR worsens an existing defect, fix the PR-caused regression; this does not authorize broader baseline cleanup. Record origin, PR relevance and repair authority separately in the existing ledger. Keep uncertain origin explicit rather than assuming either repair authority or a baseline exclusion.

The absence of a field, API or display path in the pre-PR implementation does not by itself make an explicit PR requirement a baseline exception or external blocker. First check whether authorized PR changes can supply the behavior or preserve/recover the needed facts; do not invent unavailable historical facts or broaden baseline repair authority.

Account for the inherited catalog, but do not turn that accounting into completion of unrelated pre-existing proofs. For an unaffected inherited gap, record a brief baseline-backed exclusion and stop investigating it; missing proof alone is not evidence of PR impact. Validate the exact reused contract and record how any relevant baseline defect limits the PR's guarantees rather than recursively re-proving every dependency.

Before repairs or TLC execution, create a concise, source-linked obligation ledger from the accepted commitments, full PR diff including additions/deletions, existing models and affected implementation dependencies. Start with explicit unknowns and refine it as work proceeds. Account for the entire inherited catalog and governing commitment set; the selected execution suite must be derived from that accounting.

If the starting checkpoint already contains the feature, review the entire feature against its original requirements and the actual pre-PR product, not only edits made during this session. A defect introduced by the PR remains in scope even when present at this checkpoint. Include ordinary functional and integration review of affected UI, API, persistence and notification paths, using proportionate builds, tests and source review; the existing model catalog does not bound that review.

Original feature requirements and accepted clarifications remain governing inputs even when absent from the current ontology or model catalog. Add missing governing commitments and create or extend TLA+/TLC models and properties for important in-scope behavioral obligations, with implementation correspondence and checked evidence. Use appropriate additional evidence for obligations outside the models' scope, and keep limits explicit. Missing coverage for an original requirement of this PR is an in-scope gap, not an unrelated inherited exception.

Each obligation needs a stable ID; authority and required behavior; baseline status; affected producers, callers, consumers, competing writers and effects; model/property and correspondence evidence; required assurance level; current status; and the concrete evidence needed for closure. Split independent promises and boundaries into child obligations. A parent cannot close while a required child remains open. Reconcile both directions: commitments to evidence, and changed implementation/dependencies to affected commitments. Do not mechanically create one ontology block or model per ledger row.

2. Iterate through inspect → update → verify → challenge.

Work in coherent groups of obligations. Repeat this loop, expanding impact analysis whenever a repair or discovery changes dependencies:

a. Inspect the complete relevant operation. Follow authoritative inputs through preparation, authorization, shared helpers, consumers, persistence and external effects. Identify all relevant entry points and competing writers. Make coverage inspectable: name the actual entry points, adapters, competing writers and final consumers with source locations, and map supporting evidence to each distinct boundary. Broad area labels cannot establish coverage of those paths. For facts such as valid, authorized, current, associated, committed or retryable, establish their actual producer, caller premises and validity through use. Unchanged source is still affected when new callers, inputs, writers or assumptions change its role.

When the writers of a fact are unclear, start with the stored facts the invariant reads. Use existing schema, registrations or source search to find operations that can change those facts, then compare them with the modeled actions. Record any uncovered writer and the limits of a manual search in the same obligation.

b. Reconcile the governing ontology with accepted intent and preserved behavior. Keep it concise and consequential. Do not redefine a requirement to match the implementation, promote a model assumption into accepted intent, or silently narrow supported inputs. Resolve questions from available authority; retain genuine unresolved meaning explicitly.

c. Update models and correspondence together. Represent consequential state, ownership, transitions, interleavings, failures and required recovery. Connect relevant implementation behavior to model actions or a justified abstraction. Track missing connections as open obligations. Keep intended properties, current implementation behavior, negative controls and historical variants distinct. Check supported input-domain preservation separately from correctness inside model bounds: a stronger precondition, new size/depth limit or new refusal must not silently exclude previously supported behavior. A finite checking bound is not a product restriction or evidence that all supported inputs fit. Preserve legitimate success as well as refusal. Separate safety, reachability and conditional progress; record bounds, reduction arguments, fairness and operating premises.

d. Establish the required evidence. Reuse adequate proofs or correspondence evidence where applicable. At changed or unsupported boundaries, produce the necessary checked proof/refinement, static check, actual-path regression, fault injection or trace evidence, preserving its evidence level. A source hash or a model action that assumes the desired result is insufficient correspondence. Repair production defects within the repair authority above and correct in-scope model/correspondence errors, then revisit every guarantee affected by the repair. Qualify any necessary existing-checker repair separately; never weaken acceptance to obtain green results.

After removing a blocking failure, exercise the downstream required behavior that was previously unreachable or untested. A failed prerequisite, a skipped test or success at an intermediate step cannot establish the rest of that workflow.

Where repeated stateful cases benefit from a reusable comparison, consider [automated model-to-production replay](model-checking.md#optional-automated-model-to-production-replay) as correspondence evidence. Apply its mapping, adapter controls and coverage limits; this optional technique does not expand the PR scope or replace required proof or targeted actual-path checks.

e. Challenge closure. Ask whether the evidence could pass while this accepted commitment fails on a supported path. Challenge alternate entry points, absent/stale inputs, intervening writers, partial commits, retries, changed preconditions and previously valid behavior. Use a different derivation or independent check where useful; another agent is not required. Link each challenge to the particular obligation and call chain. Evidence for one transaction, caller or branch cannot close a different one by analogy. When the evidence for a consequential requirement stops at an intermediate step, describe one plausible implementation that would pass that check while violating the requirement. If one exists, check the remaining behavior at the consumer or effect named by the requirement, or keep that part open. Tie every relied-on premise to its real producer and enforcement through use, including absent values and actual commit boundaries. For each confirmed repair, retain a distinguishing failing-before/passing-after actual-path check where feasible. Also check representative previously accepted inputs, successful operations, required error/refusal behavior and compatibility on the affected paths; a new refusal or safety property alone does not establish preservation. Record any evidence limitation rather than replacing required proof with tests.

Apply the task's reverification risk criteria if supplied. Otherwise cover these dimensions: intent coverage; preserved contracts; abstraction/bounds; non-vacuity/progress; code correspondence; entry points/bypasses; caller premises; concurrency/failures; dependency closure; evidence identity; acceptance-control integrity; operating assumptions; build/migration/mixed versions; trusted tools; and completion claims. Record their consequences on individual obligations. A global “addressed” label does not close unresolved children.

3. Reconcile affected guarantees and carry-forward after each repair batch.

Refresh relevant inventories from current build/registration roots, including added/deleted files, collector configuration and generated inputs. Checking only previously bound files misses new dependencies. Account for relevant dynamic or unknown edges through wider investigation, qualified evidence, or an explicit unresolved obligation.

In the initial catalog accounting, audit every inherited configuration, including runs hidden behind binding-precheck failures and relevant unregistered configurations. Record active, historical/superseded, applicable-reused, inherited-exception or unresolved dispositions. After each repair batch, revisit entries whose dependencies, callers, inputs or premises changed; retain justified unaffected dispositions without restarting the foundation audit. Retiring a configuration must not strand its required guarantee.

Reexecute changed, stale and newly required formal checks. Reuse mathematically unchanged results only after establishing current contract, implementation dependency closure, assumptions and execution integrity. Full-system revalidation can use incremental execution; executing the entire catalog cannot substitute for semantic applicability.

Use evidence from the actual pre-PR product to establish a baseline defect; failure at the PR-containing start, or unchanged source text alone, is insufficient. A relevant baseline product defect remains reported under the repair-scope rule above. Correct misleading in-scope models or bindings without silently repairing the product or weakening valid intent. A model accurately exposing a defect does not establish the intended guarantee. Keep baseline findings separate from explicit owner waivers, and count neither as a verified guarantee.

Where existing tools cannot enforce a coverage check, perform the reconciliation explicitly and identify it as reviewed evidence. Do not treat a hashed explanation as proof of its truth. Missing tooling must remain visible rather than becoming a silent waiver.

4. Apply the completion gate on final inputs.

The [ontology, model and implementation review brief](../ontology-model-review.md) can be used within this acceptance review.

At the final gate, re-read the original accepted requirements and inspect the full PR paths to derive an acceptance review independently of the obligation ledger. Compare that review with the claimed closures and resolve omitted criteria or paths. Include ordinary functional criteria as well as modeled guarantees, using evidence appropriate to each; this does not require a model for every minor UI detail. Then reconcile the original commitments, final ontology, obligation ledger, current implementation inventories and full catalog. Bind all relied-on results to final source, model/configuration, dependencies, tools and applicable premises. Preserve actual outcomes, failures, skips, timeouts and superseded attempts. An expected counterexample to a required current guarantee remains a violation; a successful negative control does not prove production safety.

The gate distinguishes completion of authorized review/reverification work from establishment of product guarantees. Work completion requires the required investigation, in-scope model/correspondence work, authorized repairs and checks to be complete, with baseline findings adequately investigated and reported. It does not require unauthorized baseline repairs. A baseline defect that invalidates a required guarantee leaves that guarantee unestablished even when the authorized review is complete. Missing required investigation or unavailable required evidence leaves the work incomplete; finish independent work and identify the remaining dependency or authority needed. An unqualified assurance claim still requires every new/affected obligation to be supported at the stated level and unaffected guarantees to have justified carry-forward. No unresolved dependency, unsupported premise or uncovered required child may disappear into a green total. Keep ontology coverage, semantic model coverage, implementation correspondence and execution status separate.

Continue while independent authorized work remains: unfinished in-scope models, correspondence, repairs and required checks are actionable work. A counterexample caused by an adequately investigated baseline product defect is not itself authorization for another repair. Do not stop because one suite passed, one review found no further bugs, or a report was written. Use a reasonable, documented assumption when it lets work proceed. Ask the owner when a missing decision or dependency blocks required work and no such assumption suffices. Continue all independent in-scope work. End with incomplete work only when no further meaningful authorized progress is possible without external input or authority, or an actual execution limit prevents continuation. State that reason and preserve the exact next actions; do not loop on an unauthorized baseline repair to obtain a passing guarantee.

Before stopping on a question or external dependency, name the accepted outcome and the exact choice or evidence still missing. Check whether a later authorized answer actually changed the outcome, and complete any independent local repair or check that holds under the remaining reasonable answers.

5. Continue across sessions without losing the goal.

Maintain a durable checkpoint with pinned inputs, ledger/evidence locations, changed files, completed checks, unresolved obligations, valid exceptions, pending processes and the exact next actions. Use an available continuation loop for this same task when it needs multiple sessions. If a session must end, save this checkpoint and report IN PROGRESS or BLOCKED with the remaining work. Session termination is not goal completion. On continuation, read the checkpoint, check for intervening changes, invalidate affected evidence and resume the loop. If automatic continuation is unavailable, leave the checkpoint ready for manual continuation. Do not restart the assessment, discard open obligations or launch a separate verification task.

Base the final report on the ledger and actual checker results. Include [Human decisions](model-checking.md#human-decisions-in-the-run-report), with the source of each settled decision and the effect of each open assumption. State whether authorized review/reverification work is COMPLETE or INCOMPLETE, with the exact scope and reason. Separately state which product guarantees are established, conditional or unestablished, distinguishing violations, baseline limitations, owner waivers and missing evidence. A complete review is not a feature-acceptance or merge-readiness verdict. Explain ontology/model changes, justified carry-forward, implementation correspondence, repairs, final checks and remaining limits. Claim only the guarantees the evidence establishes.

## 4. Conflicts between assertions and docs, spec or CHANGELOG

**C1. `commit` inside an open transaction.**
- Contract ledger-api.md:26 lists `LedgerTransactionOpenError` among `commit`'s errors.
- The 4.7.0 test (embedded.py:30-48) asserts the commit *joins* the transaction: "4.7.0 (row 4): the commit nests in
  the transaction open on its server process … It used to be refused (FR-047)".
- Supporting the test: CHANGELOG.md:80-82 ("Before the fix an engine on the caller's connection raised
  `LedgerTransactionOpenError` … `ledger.commit` now runs nested in the caller's transaction"), USER_GUIDE.md:288-290,
  and errors.py:83-84 ("`commit` no longer raises it: since 4.7.0 it joins the open transaction").
- The contract, CHANGELOG.md:5296 (v2.16.0, "`$TLEVEL>0` fail-closed") and the file's own docstring line 1 ("Spec 213
  FR-047 — fail-closed atomicity when a transaction is already open") are stale.

**C2. `enable` errors.**
- Contract ledger-api.md:22 lists only `LedgerLockTimeoutError` for `enable`.
- embedded.py:55-56 expects `LedgerTransactionOpenError` ("`enable()` is still refused").
- CHANGELOG.md:37 supports the test: "The ledger's `enable()` and `redact()` refuse an open transaction
  (`LedgerTransactionOpenError`) on every engine."

**C3. Replay without an idempotency key.**
- USER_GUIDE.md:1102: "**Retries.** Committing the same actor and operations again returns the first revision with
  `replayed=True`."
- The tests disagree in substance. Every replay in us04 and observability carries `idempotency_key`.
  us04::test_key_from_rejected_commit_is_reusable:87 commits a keyless `_cs()` that "advances head".
- The server replays only `If (tKey '= "") && $Data(^IVG.Ledger("idem", tKey))` (Ledger.cls:457).
- USER_GUIDE no longer mentions `idempotency_key` anywhere (grep finds 0 hits), though CHANGELOG.md:4974 says spec
  215 added a USER_GUIDE "Idempotency subsection".
- No test commits the same keyless changeset twice, so the doc claim is untested and, per the code, false.

**C4. Metrics hook "whatever the outcome".**
- ledger-prometheus-hook.md:35-36: "`engine.ledger.commit()` calls it once per call, whatever the outcome."
- `commit` runs `changeset.validate()` (client.py:392) before `_send`/`_emit`, so `EmptyChangesetError` and op_ref
  errors raise without a hook call. us01:33 asserts the `EmptyChangesetError` but checks no hook, so this is a gap
  between doc and code that no test covers, not a failing test.
- The doc's outcome enum (:23-24) also lacks the codes `_emit` can pass through from spec 256
  (`idempotency_redacted`, `redaction_in_progress`).

**C5. Which `NodeNotFoundError`.**
- USER_GUIDE.md:1103: "fails the commit with `NodeNotFoundError`".
- API_REFERENCE.md:3123-3125 documents `from iris_vector_graph import NodeNotFoundError` as a "subclass of
  `IVGError`". That is a **different class** (iris_vector_graph/errors.py:90) from the one the ledger raises and test
  217 imports (`iris_vector_graph.ledger.errors.NodeNotFoundError`, ledger/errors.py:91, a subclass of
  `ChangesetOperationError`). Code following API_REFERENCE would not catch the ledger's error.
- CHANGELOG.md:4984 (v2.18.8) says `NodeNotFoundError(LedgerError)` was a sibling; CHANGELOG.md:4630-4635 (v3.1.0)
  changed it to a `ChangesetOperationError`.
- us02:74-77, observability:82 and embedded:87 expect `ChangesetOperationError` for the same missing-endpoint failure.
  They pass only because of the v3.1.0 subclassing.

**C6. `history(source=...)`.**

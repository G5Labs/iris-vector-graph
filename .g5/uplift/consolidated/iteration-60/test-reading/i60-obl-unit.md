## 3. Conflicts and tensions (test vs docs/spec/CHANGELOG, or docs vs code the tests exercise)

All findings are static readings. None was checked at runtime against IRIS.

**C1. `history(source=...)` takes a plain string, but the ledger stores `source` as a JSON object (U60).**
- Test, t216:33-37: `fetch_history(conn, "Graph_KG", source="auto-ingest")` ... `assert "source = ?" in sql` / `assert "auto-ingest" in params`.
- client.py:613: "source: Filter to revisions tagged with this source string."
- schema:190: `"source": { "type": ["object", "null"] }`; api:43: `source={"system": "cmms", "batch": "2026-09-05"}`.
- Server, iris_src/src/Graph/KG/Ledger.cls:522: `If tCs.%IsDefined("source") && (tCs.%GetTypeOf("source") = "object") Set tSource = tCs.%Get("source").%ToJSON()`.
  A string `source` is never stored, and an object is stored as its JSON text.
- Result: `source = 'auto-ingest'` matches no revision written through `commit()`. Only the exact `%ToJSON` text of an object could
  match. The unit test pins SQL text only, so it cannot catch this. Suspected functional gap, not verified at runtime.

**C2. ledger-api.md does not list the spec-216 filters.** api:27 gives `history(*, after_seq, limit, actor, actor_type, since_ms,
until_ms, descending)`, without `correlation_id` or `source`. CL:4978 ("`history(correlation_id=..., source=...)` — new filter params pushed to SQL")
and t216 pin them. The contract was not updated after the additive change.

**C3. ledger-api.md's error lists are out of date for 4.7.0 and for transport failures.**
- api:26 lists `LedgerTransactionOpenError` among `commit()` errors. errors.py:83-84 says "``commit`` no longer raises it: since 4.7.0 it
  joins the open transaction", and CL:80-85 says "`ledger.commit` now runs nested in the caller's transaction". err::test_transaction_open:95
  pins only the wire-code mapping, which still serves `enable`/`redact`.
- api:22 lists only `LedgerLockTimeoutError` for `enable()`. CL:37 says "The ledger's `enable()` and `redact()` refuse an open transaction
  (`LedgerTransactionOpenError`)" (client.py:268-284).
- api:26 does not list `LedgerInconsistencyError`. Under U24, any transport exception or non-JSON answer reaches `commit()` callers as
  `"inconsistent"` → `LedgerInconsistencyError`, even when the server may already have committed.

**C4. CHANGELOG history disagrees with r137 (superseded, resolved in the test's favour).** CL:4979 (v2.18.8): "`idx_ledger_correlation`
added to `ensure_indexes()` as an optional index." r137::test_ensure_indexes_no_longer_asks_for_it:152 asserts the opposite. CL:2190-2192 (4.6.0 R137)
supersedes the old entry: "On a fresh namespace the index was asked for before its table existed, so only the second run added it".

**C5. The NodeNotFoundError base class changed (superseded; both statements still hold).** CL:4984 (v2.18.8): "`NodeNotFoundError(LedgerError)` — new
exception". The t217:11 docstring says "NodeNotFoundError is a subclass of LedgerError". ec:54 asserts
`issubclass(NodeNotFoundError, ChangesetOperationError)`, per CL:4630-4635 ("Changed — `NodeNotFoundError` is a `ChangesetOperationError`").
It is still a LedgerError through the chain, so the tests no longer contradict each other. Older docs that describe it as a sibling are stale.

**C6. hook.md overstates "once per call, whatever the outcome" (U8, U9, U20, U40).**
- hook:35-36: "`engine.ledger.enable()` writes the genesis revision without calling the hook; `engine.ledger.commit()` calls it once per
  call, whatever the outcome."
- client.py:392 runs `changeset.validate()` before `_commit`/`_emit`. An empty changeset or a bad `op_ref` raises with no hook event.
  cli:206-224 assert that no `Commit` is sent, but say nothing about the hook. A failing `$TLEVEL` probe (`_write_txn.py:82-83`) also raises before `_emit`.
- `enable()` with `adoption_needed` calls `verify(adopt=True)` → `commit(kind="adoption")` (replay.py:857), which does emit an event. cli:185 mocks
  `verify`, so it cannot see this. The doc is literally right about the genesis revision, but a hook registered before `enable()` can see an
  adoption event.

**C7. hook.md's outcome list does not cover every code `_emit` passes through.** hook:23-24 lists `success | replayed | stale_head | unknown_head |
idempotency_conflict | failed_op | too_large | disabled | not_enabled | lock_timeout | inconsistent`. `_emit` (client.py:410-411) passes on
whatever the wire code is: `transaction_open`, the spec-256 `redaction_in_progress`, or `"error"` when the code is missing. grd:215 pins only that
`outcome == "stale_head"` equals the wire code.

**C8. FR-008 promises a zero-based index; the client uses -1 as a sentinel (U32, U34).** api:105-106: "`ChangesetOperationError.op_index`
is zero-based (FR-008)", and schema:308 allows `"op_index": {"type": ["integer","null"], "minimum": 0}`. ec:107 (`err.op_index == -1`) and ec:170
(`op_index == -1` when the server omits it) pin -1 as "the server did not say". This is a client-side sentinel, not a wire value, so it is
consistent with the schema, but FR-008's "identify the index" is not met in that case.

**C9. t215's test data does not match the schema (harmless).** t215:89-90 uses `expected_head="rev-aaa"` / `"rev-bbb"`. schema:192 requires
`"pattern": "^[0-9a-f]{32}$"`. The client never validates `expected_head`, and these changesets are never sent.

**C10. The spec-224 diff entity kind is in neither the schema nor the replay code.** CL:4802: "Temporal edge entries appear in `ledger.diff()` as
`entity_kind="temporal_edge"`." schema:317 limits DiffEntry `entity_kind` to `["node","rel"]`, and `compute_diff`/`GraphState.apply`
(replay.py:170-209, 453-536) handle only node and rel. No unit test covers temporal_edge in diff. rep:597-598 (TestTemporalExclusion) concerns
canonical reads. Peripheral, but it is a three-way disagreement.

**C11. The contract says "4-tuple"; a 3-tuple is accepted.** api:70-72: "Relationship addressing is exactly one of `stmt_id`, a 4-tuple, or an `OpRef`".
chg:94-96 accepts `("s","P","o")` with `graph None`, and changeset.py:88-89 also accepts a bare `str` as `stmt_id` (untested). Minor relaxation.

**C12. The implemented auto_stub rule is wider than CL/t217 describe (U14).** CL:4987-4988: "`create_relationship(s, p, o)` auto-prepends
`upsert_node(s)` and `upsert_node(o)` if not already in the changeset." The implementation (changeset.py:206) suppresses a stub when ANY earlier op
carries that `"id"`: `delete_node`, `set_prop` or `add_label` as well. So `delete_node("B")` followed by `create_relationship("A","R","B")` gives no
stub for B. The stubs go immediately before the rel op, not at the start of the changeset. t217 tests only the create_node/upsert_node cases.

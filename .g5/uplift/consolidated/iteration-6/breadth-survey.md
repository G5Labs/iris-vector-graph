## Frozen expectations before implementation/foundation inspection

Authorities first read: `docs/USER_GUIDE.md:790-831`, `docs/ADMIN_API.md:201-218`, `tests/unit/test_470_call_yield_where.py`, `tests/e2e/test_470_call_yield_where_e2e.py`, `tests/unit/test_460_proc_yield_alias.py`, `tests/e2e/test_460_proc_yield_alias_e2e.py`, `tests/unit/test_463_api_health_check.py`, `tests/unit/test_r108_health_status_only.py`. These supplied the exact neighboring outcomes before implementation or current ontology/models were examined. Existing test bodies were read; no tests were yet run.

- P1, procedure aliases and a real caller filter: with persisted labels A and B, `CALL db.labels() YIELD label AS l WHERE l = $wanted RETURN l` must yield only A when wanted=A, and no row when wanted=C. Without the filter both labels are visible. The alias is the name consumed by WHERE and RETURN, not an unrelated store column or the original unaliased name. A translating `ivg.ppr` neighbor binds `node AS n, score AS sc`; a MATCH on n must stay on the yielded node rather than range over every node. Producer scores are a separate premise, not supplied evidence of numerical correctness.
- P2, handled CALL continuation: `CALL db.labels() YIELD label WITH label WHERE label = 'B' RETURN label` must return B. Replacing that supported continuation by `MATCH (n:X)` must raise naming MATCH rather than silently discard the clause and return every label. Supported comparisons/parameters/NULL use the product's three-valued WHERE rules; unsupported functions/arithmetic/STARTS WITH on a Python-handled CALL must raise rather than be treated as true.
- H1, ordinary HTTP health at `iris_vector_graph.cypher_api`: a successful probe query gives HTTP200/body `{"status":"ok"}`; an engine-factory exception or a query failure folded into `IVGResult.error` gives HTTP503/body `{"status":"unavailable"}`. Operational status must follow the deciding probe result rather than presence of an engine object. This survey does not test authentication.
- H2, the separate `api.main` application: an injected engine whose SELECT1 returns1 is healthy; a failed/wrong SELECT1 result is HTTP503. Even with SELECT1=1, an actual IRIS connection whose namespace's IVG Schema record differs from the configured schema (case insensitive comparison) is HTTP503; matching record is healthy. Startup without an engine remains callable and reports503. The server's response schema differs from cypher_api's and must not be merged into one canonical statement accidentally.

Selection rationale: procedure handlers cross a producer-to-consumer boundary that front-end translation alone cannot settle; HTTP health crosses startup, database liveness/schema identity and load-balancer observation. The latter includes `api/`, which is outside the historical scoped-member denominator; it remains a real product workflow, and evidence there must not silently change that census.

## Implementation trace and current foundation comparison

### Procedure producer through the caller's actual result

The real parser `CypherParser.parse_procedure_call` (`cypher/parser.py:105-172`) records each alias as `(column,name)` and its YIELD WHERE expression. `IRISGraphEngine._SYSTEM_PROCEDURES` (`engine.py:944-966`) selects the metadata producer; `_try_system_procedure` (`:1676-1722`) dispatches while forwarding only the parameters/graph its handler accepts. `_proc_db_labels` (`:1315-1319`) executes `SELECT DISTINCT label ... ORDER BY label` and returns an `IVGResult` with physical column `label`.

`QueryMixin._execute_parsed` (`_engine/query.py:2032-2053`) first asks `_handler_may_answer` (`:1448-1488`), then invokes the real producer, validates the allowed continuation with `row_where.handler_tail`, applies `where_rows`, projects and applies ORDER/SKIP/LIMIT. `row_where.yield_names` maps alias names to physical producer columns; `_value`, `_boolean`, `_eq` and `_order` decide comparisons, parameters and three-valued results; only True passes. `_project_onto_names` (`query.py:1519-1532`) maps RETURN names back to physical columns. `_apply_handler_tail` (`:1535-1577`) consumes the **result's** column names for ORDER BY. The public `execute_cypher` path calls `_execute_parsed`, applies error/empty-column handling and returns that result (`:1913-1948`).

The SQLite probe exercised this complete metadata producer, parser and consumer; it also replayed four cases through public `execute_cypher` with a recently checked connection, so the observed column behavior is not an artifact of stopping at `_execute_parsed`. The fixture inserted A twice and B once; the real DISTINCT producer yielded A,B. P1-A returns columns `[l]` and row A; P1-C returns no rows; P1-unfiltered returns both. P2's WITH returns B; MATCH and unsupported STARTS WITH raise named ValueErrors; `label = null` yields no rows. Removing the real `where_rows` consumer changes P1-A to A,B and is detected while the real producer remains intact.

**Additional source-derived consumer discovery, kept separate from the frozen cases:** `CALL db.labels() YIELD label AS l WHERE l = 'A'` returns the right row but columns `[label]`; adding `RETURN l` gives columns `[l]`. `CALL db.labels() YIELD label AS l ORDER BY l` raises `ORDER BY reads a returned column by name` because no RETURN projected the alias. These same outcomes reproduce through public `execute_cypher`. The cause is the actual continuation: `handler_tail` returns no projection names without RETURN, `_project_handler_answer` projects only GDS/weighted-path procedures, and the db handler's raw column survives to `_apply_handler_tail`. This is a concrete formal/canonical boundary candidate, not yet a newly adjudicated product bug or owner decision.

Canonical owner `query.system-procedures` already lists supported/refused continuations but does not state alias projection, filter truth rules or the standalone alias exception. The ordinary allowed/refused P2 distinction is represented in prose; the precise P1 prediction and discovery need more detail. Existing imported `proofs-d1d/cys_l2::labels2/step2` models graph scope of the label producer (reviewed; F-0816 control) and `nread_l2` models native/SQL route fidelity. Neither represents YIELD names, filtering, result columns or tail consumption. `node_read` supplies unrelated property typing, and AQL frontend/threshold models cannot answer these handler cases. No active declaration/crosswalk binding was found for `row_where`, `_project_onto_names` or `_apply_handler_tail`. A bound producer alone therefore cannot establish this end result.

Translating ivg alias tests were retained as a positive/limited neighbor: the source uses `yield_where_as_with`, `_yield_pairs` and `_yield_renames`, and all table-driven unit cases passed. The survey did **not** execute real PPR/IVF/degree producers or JSON_TABLE SQL, and cannot promote their numerical membership, joins or provider semantics from those tests. The unscoped db.labels producer is inherited F-0816; it is not a new finding here.

### HTTP startup, probe and load-balancer observation

`api.main.create_app` (`api/main.py:68-143`) tries engine construction once when no engine is supplied and captures either that engine or None in the health route closure. `database_problem` (`:40-65`) derives liveness from actual SELECT1 result/exception, then for an IRIS connection derives schema health from `schema_name.read_record` and case-insensitive `same_schema`. The route maps None/no problem to HTTP200; all enumerated problems map to HTTP503. The probe ran actual ASGI routing with substituted SELECT1 and schema-record providers, including matching/mismatching/missing records.

`iris_vector_graph.cypher_api._get_engine` (`cypher_api.py:201-206`) installs a cache only after `_make_engine` succeeds. `_engine` (`:220-225`) holds the engine lock over the health query. `health` (`:268-285`) executes the real query call and checks **IVGResult.error**, not just exceptions or engine presence, before selecting HTTP200/503. The ASGI probe covers success, folded query error and engine-factory error.

H1/H2 match their frozen expectations and the existing `access.health` canonical owner, including the two servers' different schema checks. This is useful reproduced agreement, **not a new ontology gain**. The formal platform notes explicitly leave `/health` out. Imported `auth_l2` and its public-route witness distinguish whether a route runs; `Status::Ran` does not derive operational readiness from SELECT1, schema identity or an `IVGResult.error`. No active formal contract found supplies that producer-to-HTTP mapping.

**Additional state-history discovery, separate from H1/H2:** after initial engine construction fails and the provider is then ready, the captured sample API remains HTTP503 on the next health request (factory called once), while cypher_api retries and returns HTTP200 (factory called twice; observed statuses `[503,200]`). `api.main` observed `[503,503]`. The probe uses a provider sequence whose second result is a functioning fake engine; it is an observation of the app's retry/capture decision, not of a database recovering. The current owner does not explain this history-dependent recovery boundary. No requirement to auto-recover was established, so this is a missing prediction/policy candidate rather than a confirmed defect.

There is a third generated GraphQL app health route, already inherited F-1611; it was not run in this survey and is not counted as a fresh discovery. No authentication, authorization, listener binding, remote target or sensitive-error scenario was tested.

## Prioritized feedback, misses and convergence

1. **Strongest next tractable candidate: handled CALL aliases/filter/tail to final result columns.** Owning source: `_proc_db_labels` -> `_execute_parsed` -> `handler_tail/where_rows` -> `_project_onto_names/_apply_handler_tail` -> `execute_cypher`. Missing distinction: YIELD alias with versus without explicit RETURN, and ORDER on that alias, while the producer and rows remain fixed. Existing owner: `query.system-procedures`; existing label-scope model is insufficient. Closure would model actual yield-name mapping, the supported WHERE/refusal surface, projection and ordering, then bind both correct P1/P2 neighbors and the observed standalone exception through public result columns. The source-only SQLite path already makes this tractable without a native target. Any intended repair must preserve admitted filters, type/null rules, empty results and current raw provider columns; adjudicate the alias expectation rather than silently assume a new policy.
2. **Different underserved workflow: health construction/retry plus query/schema decision to HTTP status.** Existing owner: `access.health`, already accurate for H1/H2. Missing formal state: app-owned captured engine versus lazy cached engine, actual query/record result and provider error. Closure would prove/compare healthy and unhealthy provider neighbors, folded error, schema mismatch and the two recovery histories. Keep sample API `api/` outside the historical member denominator unless the frame is explicitly expanded; its workflow evidence is still material. A model of public-route admission alone earns no readiness credit. Whether the sample API must auto-recover remains unestablished.

Misses/deferred work retained: live IRIS query-procedure translations and numerical producer membership; GDS alias variations; handler row typing outside the tested expression subset; empty-result alias/projection edge cases; the generic GraphQL health route (known F-1611); real SQL schema-record failure and database recovery; engine-lock wait/cancellation and stale cached connections; FHIR domain projection typing and numerical eigenvector recurrence were not surveyed. No areas were labeled trivial to improve reach.

This survey makes **no new issue/simplification/question-register movement** and edits no canonical owner or formal family. It identifies candidate work for adjudication, preserving already-known F-0816/F-1611 and the positive H1/H2/translated-ivg results. The 419 passing tests and two correct canonical health neighbors do not justify convergence: a concrete, reachable, ordinary query-consumer outcome still lacks a formal distinction, and an independent operational workflow lacks its probe/recovery model. I therefore **do not believe the foundation has converged** on the evidence from this breadth check. Another iteration can materially improve these predictions and bindings without depending on the native temporal/history resources currently owned by others.

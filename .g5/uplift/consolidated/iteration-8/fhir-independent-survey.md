## Scope and independently retained neighbors

The task ownership contract is supported by docs/FHIR_GRAPH.md:287-295, Python method docstrings and `test_470_fhir_task_ownership_e2e.py`. Ordinary restored registration neighbors are own task versus existing foreign task versus stale task ID. Imported fhir_l2's one-graph prefiltered task set and supplied success/refusal decisions cannot derive the raw row check. Existing task-save/delete versus later registry SQL separation is inherited F-C1501, not a new bug.

The actual chain is registry row -> Open -> effective interval -> task map lookup -> opened task class/namespace/raw Settings -> AssignSettings/Save or Delete -> registry SQL -> response JSON -> Python _fhir_call caller. `FHIRGraphSyncTask.OnTask` is a separate final task invocation reader, driven by its saved GraphId, with SyncOnce result parsing and %Status conversion. Neither `scheduled` nor busy proves that a sync completed.

| Raw neighbor before operation | Expected source outcome |
|---|---|
| task_id absent / stale / own existing task | Schedule allocates / allocates / reuses exact task ID |
| own / class mismatch / namespace mismatch / GraphId mismatch | mutate own; every existing foreign row refuses before task or registry writes |
| no Settings GraphId / key GraphID / GraphId only in a value position | decoded graph empty, refuse |
| GraphId=foreign then GraphId=own / reverse | last matching key wins: admit / refuse |
| GraphId=own followed by trailing GraphId key with no value | last key reads empty, so refuse; silently zipping only complete pairs would be wrong |
| stale ID / own task, Unschedule | clear stored ID, removedfalse / delete and clear, removedtrue; reply.task_id is the OLD ID in both cases |
| None / explicit0,59,True /60/61 at Python caller | forward0 to retain registered interval / refuse before native call / minutes1/2 |
| registered interval59 with omission / positive60 override | server refusal / valid override |
| AssignSettings/save/delete failure before effect / later SQL failure | stop before subsequent SQL / preserve prior task effect with old registry state; actual partial provider failure requires a separate relation |
| OnTask reply ok/busy/other non-error status / error / thrown or JSON parser failure | successful invocation / failed %Status / exception converted to failed %Status |

These ObjectScript outcomes are source-derived expectations, not new native observations. Exact Settings/native provider behavior remains a correspondence boundary for the root-owned probe.

## Deciding and writing roles

- `_engine/fhir_graph.py::_fhir_graph`(:56), fhir_graph_schedule(:291), fhir_graph_unschedule(:302), _fhir_call(:183): actual caller validation, argument forwarding, JSON decode and exact status==error exception. Graph validation permits any valid nonempty named graph, including ordinary names, spaces and numeric string1; it does not require a fhir: prefix. It strips NUL; default/0/other controls refuse. Explicit interval omission differs from explicit0. The public caller accepts integer seconds>=60; direct ObjectScript Schedule uses a positive override or registered interval, a wider interface.
- `FHIRGraph.Open`(:1713): GraphKey.ForName and ForIndex, table/registration presence, persisted interval_s/task_id and JSON settings. A missing registration errors before Task access. It reads Adjacency.Indexed but not repository resource rows.
- `FHIRGraph.Schedule`(:667): computes interval and ceil minutes before task lookup. Existing nonempty ID plus ExistsId opens exact object and CheckOwnTask runs before assignments. Otherwise New. Assigns diagnostic Name truncated to50, Description, NameSpace, TaskClass, daily schedule fields, then definition.GraphId -> AssignSettings -> Save -> obtains ID -> registry SQL. Raw seconds remain stored; DailyIncrement is rounded minutes. Existing unassigned fields such as Suspended/StartDate are not reset, so a scheduled reply is not an active/background-execution guarantee.
- `FHIRGraph.CheckOwnTask`(:744): checks exact class first, namespace second, Settings third. Earlier mismatch avoids Settings decode entirely. Settings is scanned at positions1,3,...; only GraphId in a key position overwrites decoded graph. No Name, task ID pattern, graph prefix or minutes check determines ownership. An odd final key is valid $LIST data and ListGet supplies empty for its absent value. Invalid binary list decoding can raise and is not merely a supplied foreign-task boolean.
- `FHIRGraph.Unschedule`(:716): same ownership then DeleteId, then registry NULL; even absent/stale task still executes the registry clear. The reply reports the prior context ID and actual removed boolean.
- `FHIRGraphSyncTask.OnTask`(:14): calls real SyncOnce(saved GraphId), parses returned JSON, exact status error makes an error %Status; busy is success. Exceptions, including parse failure, are caught as status. Full FHIR sync, locking, background timing and provider fault internals are outside this task scope.
- `FHIRGraph.Status`(:303) and Python fhir_graph_status(:260): expose stored ID/interval rather than checking Task ownership. Status also reads graph counts, LoadColumns, interpretation and both feed tables. Full Status can therefore fail with registry-only Community fixtures, despite task operations succeeding. Use SQL registry readback plus reopened Task for the narrow task probe; do not call that a full Status execution.

Competing registry writers include Register(:166), which changes interval_s without changing an existing Task's DailyIncrement; snapshot restore imports persisted task_id but not the instance's Task objects; and direct registry DML used by the ownership E2E. Arbitrary initial registry/task maps must allow these mismatches. %SYS.Task and its normal APIs are the other persistence owner. Other graph entries/task objects must remain framed. Source Open failure, class/namespace short circuit, odd Settings, stale-vs-foreign distinction, old-ID response and post-task SQL failure are material branches that a new model could miss.

## Real API and Community feasibility check

Official [Tasks API index](https://docs.intersystems.com/irislatest/csp/docbook/DocBook.UI.Page.cls?KEY=ITECHREF_task) documents %SYS.Task availability in all namespaces. The [Task class](https://docs.intersystems.com/irislatest/csp/documatic/%25CSP.Documatic.cls?CLASSNAME=%25SYS.Task) provides inherited persistent New/OpenId/ExistsId/Save/DeleteId APIs. This supports feasibility on Community, not proof that the current target has all product classes deployed.

[Task.Definition](https://docs.intersystems.com/irislatest/csp/documatic/%25CSP.Documatic.cls?CLASSNAME=%25SYS.Task.Definition) documents public non-% properties as task settings, serialized as alternating names/values; GetSettings and SetSettings connect saved settings to OnTask. [TaskSuper](https://docs.intersystems.com/irislatest/csp/documatic/%25CSP.Documatic.cls?CLASSNAME=%25SYS.TaskSuper&LIBRARY=%25SYS) documents AssignSettings, default namespace %SYS, TimePeriod5 as on demand, and daily increment minute settings. [ListGet](https://docs.intersystems.com/irislatest/csp/docbook/DocBook.UI.Page.cls?KEY=RCOS_flistget) supplies empty for absent values and errors on invalid list format. [Native SDK IRISList](https://docs.intersystems.com/irislatest/csp/docbook/DocBook.UI.Page.cls?KEY=BPYNAT_refapi) provides binary-list construction/decoding and typed get methods. These current docs identify the real API, but target-version behavior needs a root-owned observation.

The product ownership E2E expressly runs without a FHIR server. Its world fixture creates lazy tables using GraphSchema.get_fhir_graph_schema_sql, seeds two graph rows with unused X0470 repository schemas, and exercises real Schedule/Unschedule. The lazy-table E2E establishes a different boundary: normal Register cannot succeed without HS_FHIRServer.Repo, and base initialization leaves those four tables absent. Thus direct test setup of registry rows is justified for task ownership, but must not be represented as a successful FHIR Register or real repository synchronization.

## Different underserved workflow retained

Patient ranking attribution is a distinct ordinary consumer, not settled by task ownership or the imported one-feed lifecycle proofs. Docs/FHIR_GRAPH.md:486 promises patient sums, via filtering, top contributors and unattributed mass. `test_235_patient_ranking_e2e.py` has an independent SQL compartment oracle. Source GroupPPR(:1574) produces positive PPR scores; Group(:1595) joins ^KG compartment membership with SQL qualifiers and sums full resource scores for each kept patient, ranks descending score/key ties, and separates unattributed count/mass. Python fhir_concept_ppr(:405) decides grouped versus raw-score route and wire arguments.

Neighbor predictions to preserve for future selection: one non-Patient resource score2 in two patient compartments contributes2 to each, while a scored Patient key has no compartment contribution and is unattributed; via subject retains a matching edge but drops a different-via edge, and empty via preserves all rather than an empty selection. Contributor truncation changes explanation length, not patient totals; top_k caps patients after aggregation. This needs raw adjacency/qualifier membership and actual ranking reader evidence, not another supplied valid-membership boolean. Native numerical PPR, cache/index correspondence and clinical FHIR construction remain separate provider boundaries. No current role/theorem deriving this full grouping chain was found in the scoped active model/crosswalk search; this is a next candidate, not a new bug or claim of zero FHIR formal coverage.

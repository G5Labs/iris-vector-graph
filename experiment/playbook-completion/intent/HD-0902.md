## Contradictions

- US1/FR-006 say shadow mode fails on any difference, while FR-007 says every native exception falls back. For a native exception in shadow mode the spec gives two answers. (specs/253-native-cypher-executor/spec.md:30,107; specs/253-native-cypher-executor/spec.md:109)
- Shadow mode treats a SQL failure where native answered as a mismatch, but a native failure where SQL answered as nothing (a log line). (iris_vector_graph/_engine/query.py:2230-2231; iris_vector_graph/_engine/query.py:2071-2073)
- TCK.md presents shadow runs as surfacing every difference. A natively planned query whose executor raises is answered by SQL and never compared, so the 3896/3896 shadow figure does not show that native answered those scenarios. (docs/dev/TCK.md:261-270; intent-a-hd0902-shadow-native-exception)

## As built

In shadow mode a native exception makes _try_native return None. The SQL path answers, nothing is compared, one WARNING per reason is logged, and the native-answer counter does not move (live, fault injected in the probe process). A wrong native answer raises NativeMismatch.

Evidence: live: intent-a-hd0902-shadow-native-exception; inspected: iris_vector_graph/_engine/query.py:2069-2077,2146-2152,2226-2249

## Intended contract

Ordinary mode: SQL fallback (FR-007). Shadow mode is a validation instrument (US1/FR-006, TCK.md). The repo's own asymmetry (a SQL failure counts as a mismatch) suggests that a native failure should not count as a pass. No source decides it. Status: **assumption**.

## Working assumption

Keep ordinary SQL fallback. In shadow validation, record a native exception as an unsuccessful comparison: raise in shadow mode, or count failures and report them at the end of the run. Require a clean comparison (not a fallback) before claiming parity. The FR-010 default flip and the 3896/3896 figure establish only that no compared answer differed.

## Alternatives

- (a) keep the fallback in shadow mode (today)
- (b) raise in shadow mode only
- (c) count native failures and report them at the end of a shadow run without raising

## Discriminating check

probe, run: intent-a-hd0902-shadow-native-exception

Result: pass against FR-007: native fault -> SQL rows, no raise, one warning; control wrong answer -> NativeMismatch

## What would change this

A maintainer statement that shadow mode is only a difference detector and that the native-planned share (US3) is the coverage metric would make (a) the contract. A shadow-run report of native fallbacks would make (c) the contract.

## Residual question for maintainer

In shadow mode, should a native exception count as a failed comparison (raise, or be counted and reported) the way a SQL-path error already does? Working answer: yes, in shadow mode only. Best alternative: count and report at the end of a shadow run (c).

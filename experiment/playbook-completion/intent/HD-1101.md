# HD-1101 What should a node change do when only a named graph holds the id?

Question ([decisions/11.md](../../playbook-uplift/decisions/11.md), finding F-1105): the ledger keeps nodes in the
default graph but `Graph.KG.LedgerApply.NodeExists` matches the id in any graph. For an id that only a named graph
holds, what should `create_node`, `upsert_node`, `set_prop`, `add_label`, `remove_*` and `delete_node` do? Options:
(a) refuse as not found for node changes, keep the graph-blind check for edge endpoints; (b) create the default-graph
row first, with a record; (c) keep today's behaviour and document it.

## Contradictions

- `c53c654a` keeps existence graph-blind on purpose while making every node write default-graph-only. For an id only
  a named graph holds, the ledger accepts changes it cannot apply to its own graph (live, below).
- ADR-0013:37 (2026-10-22) calls node operations graph-blind; R290 (`c53c654a`, 2026-11-04) makes their reads and
  writes default-graph-only. The ADR was not revised; its statement now holds for records and existence, not rows.
- Verification compares nodes by bare id across graphs (`replay.py:596-609`) while an accepted `delete_node` removes
  only the default graph's row (`LedgerApply.cls:354-371`): a ledger-only history then fails `verify()` (also F-1401,
  HD-1401).
- decisions.md wording ("cannot satisfy that mutation's existence precondition") reads as a scoped existence check,
  which `c53c654a` explicitly declined.

## As built

Live, `ib-HD1101-namedonly` (AUDITIB, ids only in graph `ib3_g1101`, genesis after): `create_node` refused
`node_exists`; `upsert_node` with no labels committed a revision with zero records; `set_prop` committed and wrote a
default-graph `rdf_props` row with no default-graph node row (orphan); `add_label` refused "insert label failed"
(`fk_labels_node`); `remove_label` refused `label_not_present`; strict `delete_node` committed a `delete_node` record
with prior `{"labels":[],"props":{}}` and removed nothing. `verify()` then answered `diverges`/`unrecorded_writes`
for the undeleted node after ledger-only commits. This is option (c), F-1105 reproduced live.

## Intended

Supported (by `c53c654a`, `LedgerApply.cls:92-94`, ADR-0013:37): a ledger node id is known graph-blind
(`node_exists`/`node_not_found` mean known/unknown anywhere) and ledger node writes go to the default graph's rows.
Not settled: what a change does when the default graph has no row for a known id. Status: **assumption**.

## Working assumption

Keep graph-blind existence. A node change that needs the default-graph row (`set_prop`, `remove_prop`, `add_label`,
`remove_label`, `delete_node`, `upsert_node` with labels or properties) refuses with nothing applied and no record when
that row is absent, under a reason distinct from `node_not_found` (the maintainer's meaning of that code stays). Model
edge endpoint lookup separately (`EnsureEndpoint`). Changed from decisions.md: **yes, refined**: the refusal outcome is
kept, but it is not an existence failure; the existence semantics are now supported by a maintainer commit.

## Alternatives

- (b) Materialise the default-graph node row with a recorded `create_node` before the change (consistent with
  graph-blind identity plus default-graph ownership; `delete_node` would still need a rule).
- (c) Keep the as-built behaviour and document orphan rows, FK refusals and no-op deletes.
- Graph-qualified node records (record-layout change, linked to HD-1304/HD-1401).

## Discriminating check

Probe `intent/probes/lane-b/hd1101_named_graph_only_node_ops.py`, run, registry `ib-HD1101-namedonly`, result
**fail**: neither (a) nor (b) is the pin's behaviour; (c) holds and violates replay == store after ledger-only commits
(ADR-0013:35, USER_GUIDE.md:1085-1108).

## Confidence and what would change it

As built: high (live). Intent: medium. A maintainer statement choosing materialisation, or a decision that ledger node
identity is the default-graph row (scoped existence), would change the working assumption.

## Residual question for the maintainer

For an id that only a named graph holds, should a ledger node change be refused (with a reason other than
`node_not_found`) or create the default-graph node first? Working answer: refuse. Best alternative: materialise with a
recorded `create_node`.

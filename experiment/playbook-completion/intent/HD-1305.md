# HD-1305 Should a replayed commit apply its post-commit properties?

Question ([original](../../playbook-uplift/DECISIONS.md)): F-1306 / F-1101. A replay currently re-applies them, which can revive erased content between erasure and redaction.

## Contradictions

- `ledger-api.md:26; test_ledger_us04_idempotency.py:52 ('applies nothing')` vs `client.py:430-435`: A replay re-runs the post-commit DELETE+INSERT: it overwrites later governed values (ib-HD1105-replay-reapplies) and revives an erased tenant's property row (ib-HD1305-retry-revives).
- `Ledger.cls:514 ('while a redaction runs, nothing may be written into its target'); ADR-0013:18` vs `Ledger.cls:454-462 (replay returns before the marker check) + client.py:430-435`: A retry whose revision is not yet tombstoned is replayed during a run and writes a property row into the marked target; the run then cannot finish (target_live).

## As built

Post-commit properties are applied on every successful commit response, replayed or not, as a separate SQL transaction outside the head lock. See probe results.

Evidence: live `ib-HD1305-retry-revives`; live `ib-HD1105-replay-reapplies`; inspected `iris_vector_graph/ledger/client.py:402-487`

## Intended

Status: **supported**. Supported: a replay returns the original outcome and applies nothing (spec 213 API contract, upstream test), and a retry must not re-create an erased tenant (ADR-0013:15, spec 256 edge case). The mechanism (skip on replayed=True, or record durable completion of post-commit writes) is not settled.

## Working assumption

Apply post-commit properties only on the first, non-replayed commit. Give a first attempt whose post-commit write failed (post_commit_error) an explicit recovery: the caller re-applies through a new changeset, or a durable per-revision completion flag lets a replay finish exactly the missing writes.

Changed from decisions.md: **no**. Same answer; now backed by two live failures in this audit (overwrite of a later value; revival between erase and redact and during a run).

## Alternatives

- (a) skip post-commit properties when replayed=True (lose them if the first attempt's write failed)
- (b) durable completion flag per revision; replay applies only missing writes
- (c) move post-commit properties into the revision (HD-1105 option a)

## Discriminating check

probe (run): `experiment/playbook-completion/intent/probes/lane-b/hd12_14_redaction_probes.py retry_revives -> $RUN_DIR/intent-b/ibR_retry_revives.log; registry ib-HD1305-retry-revives; also ib-HD1105-replay-reapplies`. Result: FAIL (live, ib-HD1305-retry-revives; also ib-HD1105-replay-reapplies): a replayed retry re-applies post-commit properties between erase and redaction (redaction then refused target_live) and during a run while the marker refuses ordinary commits (run stuck). Violates ledger-api.md:26 and the us04 test's 'applies nothing'.

## Confidence and what would change it

Confidence: high. A maintainer statement that post-commit properties are deliberately re-applied on retry (e.g. to repair a failed first write), which would then need an erase/redaction exception.

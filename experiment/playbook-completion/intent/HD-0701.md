# HD-0701 Must a BM25 Build (and Drop) exclude writers and be all-or-nothing?

Status: **assumption** · Confidence: medium (intent), high (as-built) · Changed from decisions.md: no (evidence now live; status unchanged)

## Question

`Graph.KG.BM25Index.Build` kills `^BM25Idx(name)` and rewrites it with no lock and no transaction; `Drop` kills with no
lock. May an Insert, Delete, second Build, Drop or Upgrade on the same index run during a Build, and may a stopped Build
leave a partial (or no) index?

## Contradictions

- ADR-0007:5 "every write under an index-level lock" vs FR-019/FR-021 (Insert/Delete only) and the code: Build and Drop
  take no lock (live: both complete while another process holds `^BM25Idx(name,"lock")`).
- FR-016/FR-018 "at every committed point" vs Build: it is not in a transaction, so every intermediate `Set` is committed
  at once; mid-Build `tf/df/doc/len` exist without `N`, and an Insert racing a Build leaves `N` overwritten by Build's
  final `Set` (F-0701).
- ADR-0007 has no Status line; ADR-0001..0006 and 0008..0016 all say "Accepted".

## As built

Build: `Kill ^BM25Idx(name)`, then per-document writes with no lock and no transaction, header and `schema=2` last;
neither Build nor Drop takes the writer lock or checks `upgrading`. Live (intent-a-hd0701-build-drop-lock): with the lock
held by process A, B's `bm25_insert` waited 2.0 s and raised "locked by another writer" (FR-019 holds), B's `bm25_build`
returned in 1 ms and `bm25_drop` in 0 ms (index gone under a held writer lock). `bm25_build(idx, [" "])` passes
`BM25BuildInput`, kills the complete previous index and returns `indexed 0` with no header (`Info` `{}`, search `[]`).

## Intended contract

Not settled. The only text covering Build is ADR-0007's "every write", in an ADR with no Status line whose options all
concern Insert; the accepted requirement text names Insert and Delete. Working reading: BM25 index modifications
serialize, and readers see a complete generation or an explicit unavailable result.

## Working assumption

Serialize Build, Drop, Insert, Delete and Upgrade per index and publish a complete generation or return unavailable,
including after a crash; a Build that is refused or indexes nothing must not destroy the previous index. Model the
as-built (unlocked Build/Drop, Kill-first) separately as the baseline. Same as decisions.md.

## Alternatives

1. Build and Drop take the writer lock and set a "building" flag that refuses writers (Search answers unavailable).
2. Build under a temporary name and swap it in under the lock (old generation stays visible; crash leaves the old one).
3. Keep today's behaviour with a documented, testable premise: no other writer on that index while Build/Drop runs.

## Discriminating check

Run: probe `intent-a-hd0701-build-drop-lock` (fail: Build/Drop proceed under a held writer lock; blank-property Build
destroys the index). Races that cannot be interleaved deterministically need a model (for the model lanes):

- State: per index `hdr ∈ {absent, (N, totalLen, schema)}`, `len`, `tf`, `df`, `doc` maps, `lock ∈ {free, p}`,
  per-process transaction buffers; crash flag.
- Actions: `Insert(p,d)` = lock → tx{RemoveDoc; add; create header if absent} → commit → unlock; `Delete` likewise;
  `Build(p)` = Kill → per doc unlocked `IndexDoc` → `SetHeader` → `schema:=2`; `Drop` = Kill; `Upgrade` = lock +
  `upgrading`; `Search` reads; `Crash` at any step (non-tx writes persist, open tx rolls back).
- Properties: P1 header present ⇒ `N=|len|`, `totalLen=Σlen`, `df(t)=|tf(t,*)|` at every state another process can see;
  P2 Search answers a complete generation or unavailable; P3 an acknowledged Insert is not lost.
- Distinguishing outcome: as-built admits `Build.Kill → Insert(header N=1) → Build.SetHeader(N=n)` (P1 broken
  permanently, N off by one) and `Crash after Kill` (postings without header; next Insert adopts them). Alternative 1
  satisfies P1/P3 and P2 as "unavailable"; alternative 2 satisfies P1–P3 with the old generation visible. Two processes,
  two documents, two terms suffice.

## What would change this

A maintainer statement scoping ADR-0007 to Insert/Delete (then alternative 3 with a documented quiet-index premise), or
an ADR/FR naming Build and Drop.

## Residual question for maintainer

May a BM25 Build or Drop run beside Insert/Delete/Upgrade on the same index (operator must quiesce), or must they
serialize with those writers and never expose or leave a headerless index? Working answer: serialize and publish
complete-or-unavailable. Best alternative: a documented quiet-index premise for Build/Drop.

## Consequence rank hint

medium: a Build racing an Insert leaves `N`/`totalLen` permanently inconsistent (FR-018) and a mistaken rebuild destroys a
working index; single-writer deployments are unaffected.

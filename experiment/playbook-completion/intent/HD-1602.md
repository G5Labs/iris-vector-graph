# HD-1602 Should admin work need a different key from reading?

Question ([original](../../playbook-uplift/decisions/16.md)): The Cypher HTTP server has one `IVG_API_KEY`; the same value runs reads and `/admin/schema/init`, `/admin/load`, `/admin/indexes/rebuild` and `DELETE /admin/queries/{id}` (KillProcess). One key, an admin key, or a kill route off by default?

## Contradictions

None found.

## As built

One key gates every route, admin and kill included. IVG_READ_ONLY=true refuses all /admin writes and DELETE /admin/queries/{id}, along with Cypher writes. The kill route can end any process that the server's IRIS user may kill.

Evidence: inspected `iris_vector_graph/cypher_api.py:95-108, 702-714`

## Intended

Status: **supported**. The documented contract is one key for every route. Admin writes, including kill, are disabled only through IVG_READ_ONLY, which also refuses Cypher writes. The privilege of IRIS_USERNAME bounds what the server can do. A separate admin credential has never been specified.

## Working assumption

Model the single key and the IRIS user's privileges as the authorization surface. Treat an admin-only key or a kill route that is off by default as a proposed strengthening. Record IVG_READ_ONLY as the existing, coarse lever.

Changed from decisions.md: **yes**. Status moves from assumption to supported. ADMIN_API and ADMIN_GUIDE (4.6.0) explicitly document one key on every route and the read-only lever. decisions.md did not cite IVG_READ_ONLY.

## Alternatives

- (b) a second, admin-only key for /admin/* writes and the kill route
- (c) kill route disabled unless an operator enables it

## Discriminating check

source (proposed): `optional no-IRIS TestClient check: with IVG_API_KEY=k, DELETE /admin/queries/1 passes the key gate; with IVG_READ_ONLY=true it gets 403`. Result: not run; the documented contract and code agree.

## Confidence and what would change it

Confidence: high. A deployment contract requiring role separation, such as an admin key or an RBAC mapping to IRIS roles.

## Residual question for the maintainer

Is one key acceptable for production servers that expose the kill route, or should the kill route be opt-in or behind a separate key? Working answer: keep the documented single key with a least-privilege IRIS user. Best alternative: (c), kill route off unless enabled.

Consequence rank hint: low (Documented. The exposure is bounded by the IRIS user's privileges and IVG_READ_ONLY.)

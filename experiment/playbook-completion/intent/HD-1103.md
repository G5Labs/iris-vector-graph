# HD-1103 Should strict mode be enforced by the server, or stay a Python-only check?

Question ([decisions/11.md](../../playbook-uplift/decisions/11.md), finding F-1108): strict mode is checked only by
`LedgerGuard` before engine writes, with a 5 s cache and fail-open probe; server writers, raw SQL, `BulkLoader`, the
GraphQL mutations and other clients are not held to it. Options: (a) keep a client-side fail-open guard and document
its surface; (b) a server-side check that refuses unrecorded writes while strict is on; (c) fail closed when strict
cannot be read.

## Contradictions

- USER_GUIDE.md:1107-1109 ("the other methods") versus the contract's explicit list (ledger-api.md:84-93), which omits
  `bulk_delete_adjacency` and the GraphQL mutations. Live, `bulk_delete_adjacency` writes under strict.
- None found between the contract and the guard's docstring.

## As built

Live, `ib-HD1103-guard-ttl` (pass): under strict, `create_node` is refused; an engine whose guard cached "not strict"
wrote immediately after another process set strict, and was refused after 5.5 s; raw SQL writes. Live,
`ib-HD1103-bulk-delete-adjacency` (fail): `bulk_delete_adjacency` deleted an edge row under strict and `verify()` then
diverged (F-1108).

## Intended

The published spec 213 contract settles the reading: strict mode is a client-side guard on the listed Python calls,
with `BulkLoader` and raw SQL explicitly outside it; the guard's docstring states the TTL and fail-open design. A
server-side barrier would be a new contract. Status: **supported** (within the contract's scope). The unguarded
`bulk_delete_adjacency`/GraphQL paths remain a defect against the user guide's wording (F-1108), not an intent
question.

## Working assumption

Treat strict mode as a client-side, cached (5 s), fail-open guard on the contract's listed calls at this pin; inventory
uncovered Python paths, server writers (Eraser, TemporalIndex, FHIR sync, SQL procedures) and external writers as
possible unrecorded writers. Changed from decisions.md: **no**.

## Alternatives

- (b) Server-side barrier in the ObjectScript writers or table triggers (changes operational compatibility).
- (c) Fail closed when the strict state cannot be read (changes behaviour for mocks and pre-deployment engines, which
  the docstring names as the reason for fail-open).

## Discriminating check

Probe `intent/probes/lane-b/hd1103_strict_guard_surface.py`, run, registry `ib-HD1103-guard-ttl` (pass: reading (a)
holds, (b) does not) and `ib-HD1103-bulk-delete-adjacency` (fail: F-1108 against USER_GUIDE.md:1107-1109).

## Confidence and what would change it

High. A maintainer statement that strict mode promises "no unrecorded writes" namespace-wide would make (b) the
contract.

## Residual question for the maintainer

None for the intent. (F-1108's remedy, guarding the two Python paths or narrowing the user guide, is a defect record.)

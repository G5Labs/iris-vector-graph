# HD-1201 Should a graph erasure take the ledger head lock?

Question ([original](../../playbook-uplift/DECISIONS.md)): EraseGraph/EraseNodes take no head lock (F-1201). Take it for the whole erasure transaction, or document that erasure needs a quiet graph? Also: may a redaction run start while an erasure of its target is open (its liveness check reads the erasure's uncommitted deletes)?

## Contradictions

- `docs/adr/0013-redaction-removes-content-from-history.md:17; spec.md:124 FR-005` vs `LedgerRedact.cls:206 (liveness read without lock, reads uncommitted deletes) + Eraser.cls (no lock)`: ADR-0013 says redaction only follows erasure and is refused while the target is live; a redaction started during an open erasure passes its check on uncommitted deletes and completes; when the erasure rolls back the target is live with its history redacted (live: ib-HD1201-open-erasure).
- `spec.md:86-88 (Story 3: refused while a commit is in flight; takes the head lock like a commit)` vs `Eraser.cls (an erasure in flight holds nothing a redaction waits on)`: The spec serializes redaction with in-flight commits only; erasure is a writer of the same stores and of the statement index but is not serialized with either commits or redaction.
- `ADR-0004:79-80 ('a write path that touches one store without the others is a bug')` vs `Eraser.cls:1117-1144 vs Ledger.cls:440 (F-1201 interleaving)`: A ledger commit that lands between the erasure's row pass and its statement pass loses its statement while its row survives (model erasure-as-built). Not reproducible live without instrumentation: the window is between two statements of one ObjectScript method.
- `commit 0cf1524f / USER_GUIDE.md:278-310 (join or refuse)` vs `nodes_edges.py:1514-1517`: erase_graph is listed neither as joining nor as refusing a caller transaction; it joins on an engine built on the caller's connection and runs outside it on a from_connect engine (the HD-1102 topology split, inspected only for erase_graph).

## As built

No erase path takes the head lock. Live: an erase_graph(gA) left open inside a caller transaction ($TLEVEL 1); a redact(gA) from a second process saw 0 live rows (uncommitted deletes), tombstoned 2 records, passed its final re-check (also a dirty read) and wrote its audit revision. The caller rolled back: gA has its 2 node rows and its edge again, its ledger statement entry is restored while the statement's create record is a tombstone, no record names gA, and verify() reports unrecorded writes on the gA relationship. The F-1201 commit/erase interleaving itself remains model-only (it lies inside one ObjectScript method).

Evidence: live `ib-HD1201-open-erasure`; inspected `iris_src/src/Graph/KG/Eraser.cls:47-261, 1117-1144`; inspected `iris_src/src/Graph/KG/LedgerRedact.cls:202-210, 409-415`

## Intended

Status: **assumption**. Outcome supported: a redaction must never complete against content whose erasure has not committed (ADR-0013:17, FR-005, CONTEXT.md:212), and an erasure must not leave a live row without its statement (ADR-0004:79-80 classifies such a write path as a bug). The mechanism is not settled: no source says erasure takes the head lock or that it needs a quiet graph.

## Working assumption

Serialize erasure with ledger commits and redaction on the same lock: the erasure holds the head lock until its outermost transaction ends (an IRIS lock released inside a transaction is held to its end, P-0003), AND the redaction's opening liveness check and marker run under that lock (HD-1301). Neither alone closes the open-erasure case: with only the erasure lock the dirty opening check still passes and the batches tombstone a target the erasure later restores; with only the locked opening check the erasure holds nothing to wait on. A liveness check that reads committed data only is an alternative to the erasure lock for the redaction half, but not for the F-1201 statement half.

Changed from decisions.md: **yes**. Refined. decisions.md proposed 'initially model the ledger head lock'. The new live probe shows the open-erasure case is reachable through the public API (erase_graph inside a caller transaction); the original premise P-1311 had no check and now has a live counterexample. Reasoning over the specified model (not yet model-checked) says the erasure lock must be paired with HD-1301's locked start. The 'quiet graph' alternative is weaker than stated: a caller transaction makes an open erasure an ordinary state the redaction cannot detect.

## Alternatives

- (a) erasure holds the head lock for its whole transaction (with HD-1301's locked start)
- (b) document that erasure needs a quiet graph (no concurrent commit, redaction, or open caller transaction) and refuse erase_graph inside a caller transaction, as 4.7.0 refuses redact()
- (c) a graph-scoped lock shared by erasure, commits touching that graph, and redaction of that graph
- (d) redaction's liveness checks read committed data only (covers the redaction half, not F-1201)

## Discriminating check

probe+model (run): `experiment/playbook-completion/intent/probes/lane-b/hd12_14_redaction_probes.py open_erasure -> $RUN_DIR/intent-b/ibR_open_erasure.log; registry ib-HD1201-open-erasure. Minimal model for the statement half (proposed, orchestrator): state rows(G) {committed, uncommitted-deleted}, stmt(G), head-lock owner, E txn {open, committed, rolled back}, marker, tombstoned(G); actions E.deleteRows, E.killStmts, E.end(commit|rollback), P.commitEdge(G) under head lock, R.check (dirty read), R.batch (head lock), R.final (re-check under lock); properties I1 'no txn open => every live G edge has a live stmt', I2 'R complete and no txn open => no live G row has tombstoned history'. Distinguishing outcome: as-built violates I1 and I2; erasure-lock-only violates I2 (stuck run, F-1302 state); locked-start-only violates I2; both hold.`. Result: FAIL (live, ib-HD1201-open-erasure): redact(gA) completed against an erasure that was still open and then rolled back; target live with redacted history; verify() diverges. Violates ADR-0013:17 / FR-005.

## Confidence and what would change it

Confidence: medium. A maintainer statement that erasure is an offline/quiescent operation (then (b) with an enforced refusal) or that erase_graph is not supported inside a caller transaction; evidence that IRIS SQL in the redaction's process reads committed data (would remove the redaction half).

## Residual question for the maintainer

May erase_graph and redact() wait or refuse (busy) when they overlap a commit, a redaction or an open caller transaction? Working answer: erasure holds the head lock to the end of its transaction and the redaction's start check runs under it. Best alternative: declare erasure a quiescent admin operation and make erase_graph refuse a caller transaction.

Consequence rank hint: high (history of live content is destroyed irreversibly (only digests remain) and verify() diverges; S1-class outcome reachable through the public API)

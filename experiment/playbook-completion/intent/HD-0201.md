## Contradictions

- USER_GUIDE says an omitted graph never means every graph. Eight id-only readers read every graph, as their docstrings say. (docs/USER_GUIDE.md:462-463; iris_vector_graph/_engine/nodes_edges.py:760-966,2590)
- get_nodes_by_label(L) returns a default-graph node whose labels do not include L and drops nodes only in named graphs (F-0206). This is wrong under either reading. (iris_vector_graph/_engine/nodes_edges.py:779-793; intent-a-hd0201-unscoped-readers)
- delete_node/bulk_delete_nodes use a third rule for an omitted graph: the unique holding graph, else refuse. (docs/USER_GUIDE.md:462; iris_vector_graph/_engine/nodes_edges.py:2227-2252)

## As built

get_node, get_nodes and the counters (R219/R249) read the default graph. get_node_ids_by_label, get_node_ids_by_property, get_property_pairs, get_property_values, property_value_exists, get_node_ids_like, count_subjects_with_property and nodes_exist read every graph. get_nodes_by_label and get_nodes_by_property mix the two scopes. delete_node with no graph acts on the holding graph or refuses.

Evidence: live: intent-a-hd0201-unscoped-readers; inspected: iris_vector_graph/_engine/nodes_edges.py:760-966,2227-2252,2590-2625

## Intended contract

General rule: an omitted graph in a Python read means the default graph (USER_GUIDE, glossary, maintainer tasks R219/R249). Whether the id-only readers are intended exceptions is not decided; only the HTTP /schema lists are an explicit exception. Joining ids from one scope with records from another is unsupported by any source. Status: assumption.

## Working assumption

For graph-aware Python reads, omission selects the default graph. Keep the all-graph id helpers as separate discovery operations with their scope visible. Never hydrate ids from one scope with another scope's records. Model delete_node's 'holding graph or refuse' rule as its own documented operation.

## Alternatives

- (a) every reader takes graph=, omitted is the default graph (USER_GUIDE rule)
- (b) omitted reads every graph and each row names its graph (Cypher all-graphs rule)
- (c) keep id-only readers all-graphs and document them as exceptions

## Discriminating check

probe (run): `intent-a-hd0201-unscoped-readers`. fail against USER_GUIDE:462-463. Three id-only readers answered ids held only by graph ia-0201. get_nodes_by_label('IA0201L') returned [('ia0201:y', ['IA0201D'])], a node without the label. get_node, get_nodes and count_nodes followed the rule.

## What would change this

A maintainer decision that the id-only readers are intended all-graph exceptions (c), or a fix that gives them graph= (a).

## Residual question for maintainer

Should the id-only Python readers (get_node_ids_by_label, nodes_exist, ...) take graph= and default to the default graph, or stay all-graphs as documented exceptions? Working answer: default graph for graph-aware reads; all-graph helpers only as explicitly named discovery operations; get_nodes_by_label must not mix scopes either way. Best alternative: (c) document the exceptions.

## Consequence rank hint

high: a public API compatibility choice affecting every multi-graph user; the mixed-scope hydration gives wrong answers today

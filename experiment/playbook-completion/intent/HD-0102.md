## Contradictions

- The guide calls a class-less namespace unready for writes. Setup still records it, and every engine is then accepted on first access. (docs/ADMIN_GUIDE.md:213-217; iris_vector_graph/_engine/schema.py:2309-2313)

## As built

initialize_schema writes ^IVG.Deploy('schema') after any non-dry run that has a Native API, including runs where the class deploy raised, a class failed, or auto_deploy_objectscript=False. The failure appears only in the reply (warnings / objectscript_failed). With the record present, the first-access check accepts every engine for that schema.

Evidence: inspected: iris_vector_graph/_engine/schema.py:2309-2313,2578-2596; inspected: iris_vector_graph/schema_name.py:220-235

## Intended contract

The record is a namespace-to-schema binding (data-model.md). Spec 262's edge cases put the record after the SQL objects. No source makes it attest ObjectScript readiness, and none decides whether a failed or disabled deploy may record. Status: assumption.

## Working assumption

Treat a stored schema name as a namespace binding only. Represent readiness of each deployed capability (classes, adjacency index, ledger, erase) separately. An engine accepted by the record check has no claim on feature readiness. A feature call on a class-less namespace must give a named failure, not silently degrade.

## Alternatives

- (b) record only when objectscript_deployed and objectscript_failed is empty
- (c) record, but mark it incomplete so the first-access check names the missing classes

## Discriminating check

probe (proposed): `needs an orchestrator scratch namespace (AUDITIA already holds a complete deploy, and probes may not call initialize_schema)`. Proposed: in a fresh scratch namespace run initialize_schema(auto_deploy_objectscript=False). Expect ^IVG.Deploy('schema') set, a new engine accepted, and status()/erase_graph/ledger.enable to give named failures or degraded results. Minimal model: state {record: absent|S, classes: none|partial|full}; actions setup(deploy on/off, outcome ok/fail), engine_access, feature_call. Property: an accepted engine's feature call succeeds or raises a named not-deployed error. As built reaches record=S with classes!=full and the engine accepted; (b) never reaches it; (c) reaches it with missing classes named.

## What would change this

A maintainer statement that the record attests a completed install (would favour b/c), or that DDL-only namespaces are a supported mode (would confirm a).

## Residual question for maintainer

Should a setup whose class deploy failed or was disabled record the namespace's schema, and should the first-access check then report the missing classes? Working answer: record as a binding only; readiness is separate and must be reported per feature. Best alternative: (c) record with an incomplete flag that first access names.

## Consequence rank hint

medium: deployment-level; a partially deployed namespace accepts engines whose erase/ledger/adjacency features are absent

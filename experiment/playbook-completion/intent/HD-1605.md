# HD-1605 Should the generated GraphQL server match the sample API's safety limits?

Question ([original](../../playbook-uplift/decisions/16.md)): `iris_vector_graph.gql.create_app` has the key gate but no depth limit (`Node.outgoing -> Relationship.node -> Node.outgoing` nests without bound) and a health route that always answers healthy; the sample API has `QueryDepthLimiter` (`IVG_GRAPHQL_MAX_DEPTH`, default 10). Leave as an example, bring to parity, or deprecate?

## Contradictions

- `CHANGELOG.md:2292 (api/ called 'the development GraphQL app')` vs `experiment/playbook-uplift/decisions/16.md HD-1605 (api/ called 'the sample API')`: The uplift's naming inverts the maintainer's: api/ is the development app, and create_app ships in the package and gets the security gates.
- `CHANGELOG.md:672-676, 685 (shared key and read-only gates applied to create_app)` vs `iris_vector_graph/gql/__init__.py:15-67 (no depth limiter; health always healthy)`: The parity work stopped short of the depth limit and the honest health check that the other app received (4.0.0, 4.6.3).

## As built

On AUDITIB, the generated app accepted a query nested 14 levels deep through outgoing/node and resolved all 14 levels. The api/ schema carries QueryDepthLimiter with a maximum depth of 10. With its connection closed, the generated app's /health answered 200 {status: healthy, database: disconnected}.

Evidence: live `ib-HD1605-gql-depth-health`

## Intended

Status: **assumption**. Undecided between (a) a developer server and (b) parity. The 4.6.0 releases already apply the shared HTTP gates (key, read-only) to create_app and fix its schema reading. That treats it as a deployable surface and makes (b) the better-supported direction. No source requires the depth limit or the 503 health response for it.

## Working assumption

Treat both apps as supported entry points subject to the shared HTTP safety constraints: key gate and read-only (already applied), a depth bound, and an honest health check. Record the generated app's missing depth limit and always-healthy /health as gaps against that parity, not as violations of a stated contract.

Changed from decisions.md: **yes**. Partial change. decisions.md left the choice open between 'distinct entry points' and parity. R097, R107 and R079 show the maintainer already hardening create_app as a deployable app, so parity (b) is now the working direction. decisions.md also used 'sample' for the app the maintainer calls the development app.

## Alternatives

- (a) leave create_app as an example/developer server and say so in its docstring and README
- (c) deprecate create_app in favour of api/

## Discriminating check

probe (run): `experiment/playbook-completion/intent/probes/lane-b/hd1605_gql_depth.py; ib-HD1605-gql-depth-health`. Result: expected-violation: a 14-level query was accepted and resolved, while the api/ schema limits depth to 10; /health answered healthy with no database.

## Confidence and what would change it

Confidence: medium. A maintainer statement of which GraphQL app is production-supported.

## Residual question for the maintainer

Is iris_vector_graph.gql.create_app a production entry point, so the depth limit and an honest /health apply, or a developer helper? Working answer: production-capable; bring it to parity. Best alternative: deprecate it in favour of the api/ app.

Consequence rank hint: medium (Unbounded nested queries from one request cause database load; a false-healthy probe keeps a broken server in rotation; the key gate already limits who can reach it.)

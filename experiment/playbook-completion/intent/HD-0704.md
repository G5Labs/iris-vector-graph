# HD-0704 Is `__stop__` a reserved BM25 index name?

Status: **supported** (outcome: `^BM25Idx("__stop__")` is the stopword list, not an index) · mechanism: assumption ·
Confidence: high · Changed from decisions.md: **yes** (outcome upgraded from assumption on a maintainer commit
statement; live probe shows a cross-index effect)

## Question

The stopword list lives at `^BM25Idx("__stop__")`, beside the indexes. Build, Insert, Drop and Search accept the name.
Should writers refuse it, or should the stopword list move out of the index global?

## Contradictions

- R165's "the stopword list, not an index" and the documented 77-word list vs public writers that accept `__stop__`
  (live: the list becomes 82 entries and an unrelated index stops indexing `doc` and `len`).
- After `bm25_build("__stop__")`, `List()` hides it while `bm25_info("__stop__")` reports an index (N=3).
- spec 044:281 puts stopwords out of scope; 6c21ed98, USER_GUIDE and API_REFERENCE document them.

## As built

`bm25_build`, `bm25_insert` and `bm25_drop` accept `__stop__`. Live: Build wrote `cfg`, `tf`, `df`, `doc`, `len`
subtrees under the stopword node; Tokenize then drops those five words from every index in the namespace (a fresh index
over "doc review cfg memo" / "len tf df notes" found nothing for `doc` or `len`, and `bm25_insert(..., "doc len")`
returned False). Drop deleted the stopword list (re-created by the next tokenize). Insert into `__stop__` again mixed an
index into the list. The node was restored exactly (it was undefined before the run).

## Intended contract

Supported for the outcome: the maintainer's R165 commit and code comment state that `^BM25Idx("__stop__")` is the
stopword list and not an index, and the user documentation fixes that list at 77 words. A state in which `__stop__` is
also an index, or is dropped as one, is therefore not a supported state. The mechanism that prevents it is not decided.

## Working assumption

Reserve `__stop__`: public BM25 entry points (`bm25_build/insert/delete/drop/upgrade`, `BM25BuildInput`, index
handles, `kg_BM25`/`ivg.bm25.search`) refuse it; the embedded registry walk skips it. Model the as-built acceptance as a
defect against the documented stopword list (cross-index). Moving the list to its own global is the compatible
alternative mechanism.

## Alternatives

1. Refuse `__stop__` in every BM25 writer and in `BM25BuildInput` (no migration).
2. Move the stopwords to their own global (needs a migration of existing namespaces).
3. Leave as is (as-built; the documented 77-word list can change silently).

## Discriminating check

Run: probe `intent-a-hd0704-stop-reserved` (fail: all three writers accept the name; documented tokenization changes for
unrelated indexes; drop deletes the list).

## What would change this

A maintainer statement that `__stop__` is a usable index name (contradicting R165), or a move of the stopword list.

## Residual question for maintainer

Mechanism only: refuse `__stop__` at the BM25 entry points, or move the stopword list out of `^BM25Idx`? Working answer:
refuse. Best alternative: a separate global with a migration.

## Consequence rank hint

medium: one accepted call silently changes the documented tokenization of every BM25 index in the namespace and a drop
removes the list namespace-wide; no cross-graph exposure.

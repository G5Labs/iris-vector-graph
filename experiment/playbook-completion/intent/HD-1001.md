# HD-1001 What should `random_walk` answer, and over which graph?

Question ([original](../../playbook-uplift/decisions/10.md)): `random_walk` answers `[]` unless the Arno library is detected, although the walk it calls (`Graph.KG.NKGAccel.RandomWalkJson` -> `NKGAccelTraversal.RandomWalkJson`) is ObjectScript; the walk reads the interned snapshot `^NKG`, which merges every graph (F-1002). Which graph should it walk, and what should it answer without the library?

## Contradictions

- `iris_vector_graph/_engine/algorithms.py:661-662 (docstring, 5ae90dbc)` vs `docs/ADMIN_GUIDE.md:651-653 (6df261d9); CONTEXT.md:263 (267aaff1)`: The docstring says random_walk returns [] without the library; the guides say every algorithm has an ObjectScript implementation that answers the same without it. The ObjectScript walk exists and is deployed.
- `docs/USER_GUIDE.md:767-769` vs `iris_src/src/Graph/KG/NKGAccelTraversal.cls:187-222 (the call random_walk makes with the library)`: No-graph methods answer the default graph; the walk reads ^NKG, every graph merged (live: a named-graph edge was walked).

## As built

Without the library (this container): random_walk answers [] (no error). With the library the engine calls NKGAccel.RandomWalkJson unchanged; that ObjectScript walk, called directly after engine.sync(), walked from a seed id shared by the default graph and graph ib1_rw_g to both graphs' neighbours. The library only gates the call; the walk is not the library's.

Evidence: live `ib-HD1001-random-walk`; inspected `iris_vector_graph/_engine/algorithms.py:658-678`; inspected `iris_src/src/Graph/KG/NKGAccelTraversal.cls:187-222`; tested `tests/integration/test_nkg_accel_no_library.py:89-92`

## Intended

Status: **assumption**. random_walk takes no graph, so it walks the default graph (USER_GUIDE), and it answers with or without the library (ADMIN_GUIDE, CONTEXT). Neither [] for a missing library nor a merged-graph walk meets both. No spec covers random_walk; the docstring describes the [] behaviour but was written as a description (R025), and the [] fallback predates the ObjectScript walk.

## Working assumption

Walk the default graph's adjacency (graph key 0) in ObjectScript, library or not (option (a)). Where only a merged ^NKG route is available and a named graph has edges, refuse visibly rather than answer [] or a merged walk. An explicit graph= argument (option (c)) is a compatible extension.

Changed from decisions.md: **yes**. decisions.md asked for a declared scope plus an observable 'unavailable' result. The deployed ObjectScript walk runs without the library (upstream test and live), and ADMIN_GUIDE says every algorithm has an ObjectScript answer. So a real default-graph answer is the better-supported reading. 'Unavailable' remains only for a route that cannot honour the scope.

## Alternatives

- (b) library-only, refusing once a named graph has edges (as the ^NKG procedures do)
- (c) add graph= and walk that graph's ^KG
- (d) retire random_walk
- keep [] without the library and document it as an Arno-only sampling helper (docstring as contract), still fixing the graph scope

## Discriminating check

probe (run): `experiment/playbook-completion/intent/probes/lane-b/hd1001_random_walk.py; ib-HD1001-random-walk`. Result: fail: [] without the library; the call random_walk makes reached a named-graph-only neighbour (ib1_rw_c) from a shared seed. With the library absent, the library-present route is inferred from source: the library only gates that call.

## Confidence and what would change it

Confidence: medium. A maintainer statement that random_walk is an Arno-only sampling helper, like ArnoAccel.KhopSampleJson, which answers empty without the library. That would make [] the contract and leave only the graph-scope defect. A spec for random walks would also settle it.

## Residual question for the maintainer

Is random_walk an Arno-only sampling helper (then [] without the library is its contract), or an algorithm IVG must answer without the library? Working answer: an algorithm that walks the default graph in ObjectScript either way. Best alternative: library-only, refusing once a named graph has edges.

Consequence rank hint: medium (Silent [] or a cross-graph walk feeds embedding/feature pipelines with no error; one public method, no spec.)

# HD-0705 Are `TextSearchEngine`, `RRFFusion` and `HybridSearchFusion` supported public API?

Status: **assumption** · Confidence: medium · Changed from decisions.md: no (refined per class; one factual correction to
the original question)

## Question

`TextSearchEngine` and `RRFFusion` are in `iris_vector_graph.__all__`; none of the three is in docs/API_REFERENCE.md.
`TextSearchEngine` uses `%FIND(col, ?)`, an unqualified table and no graph scope. Fix them to the product's rules,
deprecate them, or remove them?

Correction: `HybridSearchFusion` is **not** exported at top level at the pin (only `iris_vector_graph.fusion`); the
original question says all three are.

## Contradictions

- `__all__` exports vs API_REFERENCE:9's definition of the public Python API.
- USER_GUIDE:463 default-graph rule vs TextSearchEngine readers (live: another graph's rows for a call that names none).
- The v4.0.0 migration guide lists HybridSearchFusion as changed Python API though it is neither exported nor in the
  API reference.
- text_search.py module docstring ("native IRIS text search ... with relevance ranking") vs live SQLCODE -30 / invalid
  `%FIND` usage.

## As built

Live: `TextSearchEngine(conn, schema="Graph_KG").extract_entity_names` and `search_with_context` answered `ia0705:x` from
both `ia-0705a` and `ia-0705b` (2 and 4 rows; the label join on `s` alone duplicates) although the default graph holds
neither; `search_documents` failed with SQLCODE -30 (`SQLUSER.DOCS` not found), fell back, failed again and returned
`[]` while `kg_TXT(graph="ia-0705a")` found the row. `RRFFusion.fuse_results` gives a missing item 0. HybridSearchFusion's
text leg is graph-scoped (graph b: `[]`).

## Intended contract

No authoritative source classifies the helpers. The generated API reference excludes them; `__all__` exports two; the
v4.0.0 migration guide treats HybridSearchFusion as API; the maintainer keeps TextSearchEngine working (spec 262 tests,
security fixes) without giving it a graph. Reading: compatibility surfaces of unsettled support level.

## Working assumption

Treat the three as compatibility surfaces and qualify each: RRFFusion is a pure standard-RRF helper (document that its
rule differs from engine `kg_RRF_FUSE`, HD-0702); HybridSearchFusion is de facto public (migration guide) and
graph-scoped; TextSearchEngine is exported but reads every graph and its document search cannot reach the IVG Schema,
so it is not a supported reader of graph-scoped data. Prefer deprecation with migration advice (to `kg_TXT` /
`bm25_search`) or a `graph=` argument; do not remove without a compatibility decision. Same direction as decisions.md.

## Alternatives

1. Bring all three under the graph-scope and failure rules and list them in API_REFERENCE.
2. Deprecate (warning on construction) with migration advice.
3. Remove from `__all__` (breaking).

## Discriminating check

Run: probe `intent-a-hd0705-textsearch-scope` (fail against USER_GUIDE:463 if the export is public API: cross-graph
answers; `search_documents` cannot answer). The probe characterizes; whether the rule applies is the open question.

## What would change this

A maintainer statement of the public API scope (API_REFERENCE extended to exported classes, or a deprecation note).

## Residual question for maintainer

Are the exports `TextSearchEngine` and `RRFFusion` (and module-level `HybridSearchFusion`) supported public API under
the USER_GUIDE graph rules? Working answer: compatibility surfaces; deprecate TextSearchEngine or give it `graph=`.
Best alternative: bring all three under the rules and document them.

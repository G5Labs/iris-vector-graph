## Contradictions

- The sdist ships sql/operators.sql, yet the maintainer names initialize_schema() as the one schema path, and no shipped code loads the file. (pyproject.toml:181-183; tests/unit/test_setup_iris.py:1-8)
- decisions.md labels this 'Supported'. The cited deployment paths establish the as-built fact (unloaded), not the product-status decision. No ADR, spec decision or maintainer statement says the file is reference-only. (experiment/playbook-completion/decisions.md:125; sql/operators.sql)

## As built

operators.sql is shipped in the sdist and loaded by nothing. A namespace set up by initialize_schema holds schema.py's graph-scoped Graph_KG procedures, never operators.sql's (live). kg_GRAPH_PATH and kg_RERANK have no SQL routine. The legacy deployer loads operators_fixed.sql.

Evidence: live: intent-a-hd0803-operators-sql-deployed; inspected: pyproject.toml:181-183; inspected: scripts/deploy_production.py:65

## Intended contract

Not settled by an authoritative source. The 'one schema path' statement and doc removals point to historical material, while the 2026-03 maintenance and the sdist inclusion point to a still-shipped artifact. Status: **assumption**.

## Working assumption

Classify sql/operators.sql as shipped historical/reference SQL with no deployment path. It is outside the executed product surface, but stays in the inventory as a shipped artifact whose definitions are not graph-scoped. Trace operators_fixed.sql (legacy deployer) and the schema.py procedures separately. If anyone runs the file by hand, it creates unqualified, graph-blind procedures (F-0820-like behaviour).

## Alternatives

- (a) delete it (and other unloaded sql/ files)
- (b) keep as reference, mark as not deployed
- (c) regenerate from schema.py (graph-scoped) and load it

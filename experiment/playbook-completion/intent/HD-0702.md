# HD-0702 Which reciprocal-rank-fusion rule is the product's?

Status: **assumption** · Confidence: medium (intent), high (as-built) · Changed from decisions.md: no

## Question

Five surfaces fuse a vector list with a text list by rank, with three rules for an item one list lacks and two different
text lists. The engine method and the SQL procedure share the name `kg_RRF_FUSE`. Which rule, and which text list, is
the contract?

## Contradictions

- The engine method and the SQL procedure named `kg_RRF_FUSE` order the same inputs oppositely (live: X before Z vs Z
  before X).
- API_REFERENCE:999 says each hit scores `1/(c+rank)` and absent legs "contribute nothing"; the code adds `1/(2c+len)` for
  every item a leg lacks (with an empty text leg every row carries `+1/(2c)`), and the e2e test pins that.
- CHANGELOG:2090 "/hybridSearch fuses as `kg_RRF_FUSE` does" holds for the SQL procedure only.

## As built

Three rules on five surfaces: engine/operators `kg_RRF_FUSE` (missing at `len+c`, BM25-index text leg), SQL
`kg_RRF_FUSE` and `/hybridSearch` (missing at 10^9, kg_TXT term counts), `ivg.retrieve` and `RRFFusion` (missing adds 0).
Live (c=60; vector leg kg_KNN_VEC top 10 W, X, v3..v10; text leg only Z): engine W, X, v3, Z, ...; SQL W, Z, X, ...;
RRFFusion W = Z, then X. Each surface matches its own written rule.

## Intended contract

No authoritative source settles a product-wide rule; each surface's rule is defined only by its own code (and, for the
engine, a regression test written while fixing R086). Per-surface rules are the de facto contracts.

## Working assumption

Preserve and test each surface's rule, including missing-rank handling and which text list it reads; document that the
engine method and the SQL procedure of the same name differ. Introduce a single formula only with a versioned contract.
Same as decisions.md.

## Alternatives

1. Standard RRF everywhere (missing adds 0; matches RRFFusion, ivg.retrieve and, within 1e-9, the SQL procedure).
2. Per-surface rules, each documented (working assumption).
3. The engine rule everywhere (the only one pinned by a test).
4. A versioned common fusion API, old surfaces kept as-is.

## Discriminating check

Run: probe `intent-a-hd0702-rrf-surfaces` (pass: each surface follows its own rule; the surfaces disagree). The
construction (vector leg of 10 with X at rank 2, text leg holding only Z) separates the engine rule from both other rules
at the default c=60; it decides nothing about which rule is intended.

## What would change this

A maintainer choosing a common rule, or declaring one surface canonical (e.g. making the SQL procedure "the same as" the
engine method in fact as the operators documentation already claims for the shim).

## Residual question for maintainer

Must the engine method and the SQL procedure that share the name `kg_RRF_FUSE` rank identical inputs identically (with
which missing-rank rule and which text list), or are they distinct documented rankings? Working answer: distinct, each
documented and tested. Best alternative: standard RRF (missing adds 0) everywhere, released with a version note.

## Consequence rank hint

medium: silent ranking differences between same-named surfaces; no data loss or isolation effect.

## Contradictions

- The glossary says every node belongs to exactly one graph and USE GRAPH scopes a query to one graph. A mapped node has no graph, and its rows answer under USE GRAPH of every graph, including a graph with no content. (CONTEXT.md:27-32; docs/USER_GUIDE.md:401-402; intent-a-hd0802-mapped-label-scope)

## As built

table_mappings has no graph key. The translator applies the USE GRAPH predicate to the graph tables only, so a mapped label answers every row of its table under every scope (live: count 2 and both property values under USE GRAPH 'ia-0802-a' and 'ia-0802-none'). Native Cypher declines mapped labels.

Evidence: live: intent-a-hd0802-mapped-label-scope; inspected: iris_vector_graph/cypher/translator.py:719-779,14827-14830; inspected: iris_vector_graph/_engine/fhir.py:88-145

## Intended contract

Unsettled. The glossary's isolation rule argues for scoping. The mapping API's silence and its pre-graph origin (PR #8) argue for a namespace-wide projection. Status: **assumption**.

## Working assumption

Treat a mapping registration as namespace-wide (the as-built baseline). Under a named USE GRAPH scope, require either graph-aware mapping provenance or an explicitly documented exception. Model the current global visibility as a known deviation from the glossary's isolation rule. It is not a security breach, because the namespace is the boundary (USER_GUIDE:467-468).

## Alternatives

- (a) mapped labels answer under every scope, documented as an exception
- (b) a mapping names its graph; other scopes see no rows
- (c) refuse a mapped label under USE GRAPH with a named graph

## Discriminating check

probe, run: intent-a-hd0802-mapped-label-scope

Result: pass (as-built recorded): the mapped label answers 2 rows under every USE GRAPH; the ordinary-label control is scoped.

## What would change this

A maintainer statement or a spec giving table mappings a graph, or a USER_GUIDE line declaring mappings namespace-wide.

## Residual question for maintainer

Under USE GRAPH 'g', should a label mapped with map_sql_table answer its whole table (namespace-wide mapping, documented as an exception to graph isolation), or answer nothing / be refused unless the mapping names g? Working answer: namespace-wide, documented, with graph-aware mappings as the scoped option. Best alternative: refuse mapped labels under a named graph scope (c).

## Consequence rank hint

medium: a scoped (per-tenant graph) query silently includes another source's rows; the namespace stays the security boundary

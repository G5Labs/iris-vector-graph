# HD-1503 What happens when an erase runs during a FHIR sync?

Question ([original](../../playbook-uplift/decisions/15.md)): EraseGraph takes no lock, in particular not the sync lock ^IVG.FHIRGraph(graph). A sync running in another process can commit its next batch and move its watermark after the erase commits. What should happen?

## Contradictions

- `docs/FHIR_GRAPH.md:255-259 + test_erase_keeps_registration (erase then sync/rebuild re-projects everything)` vs `FHIRGraph.cls:1966-1974 + Eraser.cls (no lock)`: Interleaving Batch1; Erase; Batch2 leaves the graph holding only Batch2's keys with wm past keys it no longer has; later syncs apply nothing below wm, so the graph does not converge until a rebuild.

## As built

No coordination: erase runs in its own transaction without ^IVG.FHIRGraph; a running sync's later batches write absolute watermarks after the erase commits (IRIS row locks on the fhir_graphs row only order the two transactions, they do not prevent the interleaving). Reasoned from source, not observed.

Evidence: inspected `iris_src/src/Graph/KG/Eraser.cls:47-57`; inspected `iris_src/src/Graph/KG/FHIRGraph.cls:543-626,1920-1978`

## Intended

Status: **assumption**. The outcome is documented (after erase, syncs re-project the repository and converge on a rebuild); the mechanism under concurrency (lock, compare-and-set, or quiescence premise) is not stated.

## Working assumption

Keep decisions.md: erase of a FHIR graph must be serialized with an active sync (take ^IVG.FHIRGraph(graph) and answer busy, or have RunBatch abort when the watermark moved backwards); until then the quiet-sync premise must be explicit for erase.

Changed from decisions.md: no. Confirmed by source; added the documented convergence claim as the outcome anchor and the absolute-watermark write as the mechanism of the failure.

## Alternatives

- (a) erase takes the sync lock and refuses (or waits) while a sync holds it
- (b) RunBatch compare-and-sets the watermark (WHERE wm = expected) and stops when it went back
- (c) document that a FHIR graph must be unscheduled and idle before an erase

## Discriminating check

Kind: model; status: proposed.

Reference: Minimal model: repo keys k1..k4 with IDs 1..4, batch size 2; state {G, wm, sync position}; actions B1 (resync k1,k2; wm:=2), B2 (resync k3,k4; wm:=4), Erase (G:=empty; wm:=0), Sync' (a later SyncOnce from wm). Premise: each action atomic (IRIS transaction); row lock on fhir_graphs orders, does not exclude. Property P: after quiescence plus one Sync', G = rebuild(R).

Result: Trace B1;Erase;B2;Sync': as-built G = {k3,k4}, wm = 4, Sync' applies nothing -> P violated; (a) Erase busy while sync holds the lock -> P holds; (b) B2 aborts (wm went 2->0), Sync' replays from 0 -> P holds; (c) trace excluded by premise. Not run live: no FHIR repository in AUDITIB.

## Confidence and what would change it

Confidence: medium. A live interleaving on IRIS for Health (two processes, injected pause between batches) showing a different outcome; a maintainer statement making quiescence a premise.

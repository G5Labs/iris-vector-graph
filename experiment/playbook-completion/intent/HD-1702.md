# HD-1702 Should the HTTP client resend a write query after a server error?

Question ([original](../../playbook-uplift/decisions/17.md)): IVGClient._post retries POST /api/cypher up to max_retries (3) times on a 5xx, a connect error or a timeout. A CREATE whose first attempt committed and then failed to answer is sent again. Retry only reads, only connect errors, or keep retrying and require idempotent writes?

## As built

Probe (no IRIS, counting stub): a CREATE was executed 3x on persistent 500; 2x when the first attempt committed and then got a 502, with the caller seeing success and no sign of the duplicate; 3x when each attempt committed but answered after the read timeout (caller got IVGClientError). Reads and writes are treated identically. With the server's own retry (cypher_api._run_cypher) the worst case is 6 executions.

Evidence: live `ib-HD1702-client-retry (no-IRIS stub; client behaviour observed, server simulated)`; inspected `iris_vector_graph/sdk.py:209-228`

## Intended

Status: **assumption**. Retry on 5xx/connect/timeout is a deliberate, documented client feature (commit aaa54a44, docstrings, tests). No source addresses whether a non-idempotent write may be resent after an ambiguous outcome.

## Working assumption

Keep decisions.md: after an ambiguous outcome resend only a known read or an explicitly idempotent operation; report an unknown outcome otherwise; treat client and server retries as one protocol. Note that this narrows a documented feature (compatibility decision).

Changed from decisions.md: no. Probe confirms; added that the retry itself is a documented maintainer feature (so the working answer is a narrowing, not a bug fix) and that statement failures are 400 and not retried.

## Alternatives

- (a) retry only reads (client cannot tell; the server could mark replies)
- (b) retry only connect errors raised before the request was sent; never 5xx or timeouts
- (c) keep retrying everything and document that writes must be idempotent (MERGE) or carry a ledger retry key

## Discriminating check

Kind: probe; status: run.

Reference: experiment/playbook-completion/intent/probes/lane-b/hd1702_client_retry.py; ib-HD1702-client-retry

Result: expected-violation: writes resent in 3 of 3 ambiguous cases; one silent duplicate (502 then 200).

## Confidence and what would change it

Confidence: high. A maintainer statement accepting at-least-once write semantics over HTTP (then option c with documentation).

## Residual question for the maintainer

Should IVGClient resend a Cypher write after a 5xx or a read timeout? Working: resend only reads and requests known not to have been sent; otherwise surface an unknown outcome. Best alternative: keep retries and document that HTTP writes must be idempotent.

Consequence rank hint: medium (Duplicate CREATEs (up to 6 with the server retry) under ordinary network faults; one case is invisible to the caller.)

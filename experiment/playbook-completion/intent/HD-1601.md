# HD-1601 Should a server limit which graphs a caller may name?

Question ([original](../../playbook-uplift/decisions/16.md)): Every interface uses whatever graph a caller names (GraphQL `graph:`, FHIR event `graph`, REST `graph`, `USE GRAPH` over HTTP, Bolt and MCP). Keep the namespace as the only boundary, bind API keys to graphs, or build the planned Execution Context?

## Contradictions

- `specs/256-ledger-tenant-redaction/spec.md:17 (one named graph per tenant)` vs `docs/USER_GUIDE.md:467-468 (give each tenant a namespace)`: This is a tension rather than a contradiction. Spec 256 serves a deployment where one trusted service writes all tenants' graphs. That reconciles with the guide only if tenants are not direct IVG callers.

## As built

No interface restricts graph names. The code has no graph ACL: a grep of iris_vector_graph, api, iris_src and docs found none. One API key, or an IRIS login for the REST dispatcher and MCP, admits every graph in the namespace.

Evidence: inspected `iris_vector_graph/api_auth.py; iris_vector_graph/cypher_api.py:101-108`; inspected `experiment/playbook-uplift/decisions/16.md (HD-1601 inventory)`

## Intended

Status: **supported**. The IRIS namespace is the only isolation and authorization boundary. Graph ids scope data operations and confer no authorization. The Execution Context is a planned guard against accidental cross-graph writes, not an access-control feature.

## Working assumption

Same as decisions.md: namespace is the boundary; a graph name is never treated as authorization in models or claims; spec 256 tenancy assumes a trusted caller.

Changed from decisions.md: **no**. Same reading; maintainer commit cc546a29 is added as a further authoritative source.

## Alternatives

- (b) bind each API key to a list of graphs, refusing unscoped reads
- (c) implement the planned Execution Context with an authenticated principal per session

## Discriminating check

source (proposed): `none needed: documented and stated in commits`. Result: Source-only. A live check would only re-confirm that a named graph is readable with the one key.

## Confidence and what would change it

Confidence: high. A spec making the Execution Context an authorization feature, or a multi-tenant deployment contract in which tenants call IVG directly.

## Residual question for the maintainer

None.

Consequence rank hint: medium (Security-relevant, but settled by three maintainer sources. Misreading graph ids as a boundary would be an S1 error in any tenancy claim.)

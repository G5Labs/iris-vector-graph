# HD-1102 Should disable() and set_strict() refuse a caller's open transaction, as enable() does?

Question ([decisions/11.md](../../playbook-uplift/decisions/11.md)): 4.7.0 made `enable()` and `redact()` refuse a
caller transaction that holds a write; `disable()` and `set_strict()` run `Graph.KG.Ledger.Disable`/`SetStrict`
through `engine._iris_obj()`, which is the caller's own process for an engine built on a connection and another process
for a `from_connect` engine. Options: (a) refuse both inside a caller transaction; (b) join it (`WriteTxn.native()`, as
commit does); (c) keep and document the engine-dependent behaviour.

## Contradictions

- The 4.7.0 principle (`0cf1524f`) versus `disable()`/`set_strict()` on a `from_connect`-topology engine, which neither
  join nor refuse (live, below). T080's scope (`tasks.md:36`) names only enable/redact; no reason for leaving
  disable/set_strict out was found in commits, plan or changelog.

## As built

Live, `ib-HD1102-txn-rollback` (caller `START TRANSACTION` + INSERT, `$TLEVEL` 1): `enable()` refused
`LedgerTransactionOpenError` on both topologies. `disable()` and `set_strict(False)` were accepted on both. Plain engine:
the caller's ROLLBACK restored `state=enabled`, `strict=True` (joined). Second-process engine (from_connect topology):
`disabled` and `strict=False` survived the ROLLBACK (committed outside the caller's transaction). In both, another
process read the uncommitted `disabled` inside the transaction, and on the plain engine the guard cached the rolled-back
`strict=False` and let a guarded `create_node` write within its 5 s TTL.

## Intended

The 4.7.0 maintainer principle settles that an IVG call must not commit apart from a caller's open transaction (join
or refuse); option (c) is therefore not the intent for the class. Which of join or refuse applies to disable/set_strict
is not settled. Status: **assumption**.

## Working assumption

Refuse `disable()` and `set_strict()` inside a caller transaction on every engine, as `enable()`/`redact()`.
Changed from decisions.md: **no** (strengthened). The live run adds a reason: ledger lifecycle state is global and read
dirty by other processes, so a joined toggle that is later rolled back has already changed what other writers and
guards did.

## Alternatives

- (b) Join via `WriteTxn.native()`; preserves the plain engine's current behaviour but exposes the dirty-read window
  and stale guard cache seen live.
- (c) Document the engine-dependent outcome.

## Discriminating check

Probe `intent/probes/lane-b/hd1102_disable_in_caller_txn.py`, run, registry `ib-HD1102-txn-rollback`, result
**expected-violation**: as-built (c) confirmed; neither (a) nor (b) holds; the join-or-refuse principle fails for the
second-process topology. No stated contract names disable/set_strict.

## Confidence and what would change it

As built: high (live). Intent: medium. A maintainer choice of join for lifecycle calls would change it.

## Residual question for the maintainer

Should `disable()`/`set_strict()` refuse inside a caller transaction (as `enable`/`redact`) or join it (as `commit`)?
Working answer: refuse. Best alternative: join.

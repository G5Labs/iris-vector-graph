# HD-1703 Should the SQL adapter's capability list say what this namespace can run?

Question ([original](../../playbook-uplift/decisions/17.md)): IRISGraphStore.capabilities() returns _FULL_CAPABILITIES (every algorithm True) whether or not the classes are deployed; only *_arno keys vary. The engine uses it to choose store calls. Answer from what is deployed, or keep 'what the code supports' and point callers elsewhere?

## As built

Probe: over a stub connection on which every statement fails, capabilities() reports all 22 non-Arno keys True (static catalogue). On AUDITIB the engine's capabilities property reports objectscript_deployed=True, kg_built=False, nkg_built=False while the store dict is all True. Routing uses the static dict, then falls back to the same ObjectScript class on a store error.

Evidence: live `ib-HD1703-capabilities`; inspected `iris_vector_graph/stores/iris_sql_store.py:2991-3000`

## Intended

Status: **assumption**. Undocumented. The product keeps two facts: engine.capabilities (documented: what is deployed) and store.capabilities() (undocumented: what the adapter implements).

## Working assumption

Keep decisions.md: code support and namespace availability are different facts; treat store.capabilities() as a static catalogue (document it as such) and do not read it as availability; routing that needs availability uses engine.capabilities/status() or an explicit fallback.

Changed from decisions.md: no. Probe and source confirm; added that the product already separates the facts (engine.capabilities, a06e1f50) so option (b) is the existing design, missing only documentation.

## Alternatives

- (a) answer from what is deployed (classes compiled, procedures present)
- (b) keep the code-support catalogue and document it, pointing at engine.capabilities/status() for availability

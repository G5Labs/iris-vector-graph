## Contradictions

- The inventory claims to list every store holding graph content, graph-blind ones included; the vector index globals are absent. (`iris_src/src/Graph/KG/GraphStores.cls:1-16`; `iris_src/src/Graph/KG/GraphStores.cls:28-131`)
- An IVF index built by ivf_build(graph=g) still returns g's erased node ids and holds their vectors after erase_graph(g). (`CONTEXT.md:198-200`; `live intent-a-hd0601-index-erasure`)
- 'rebuild them from the tables': after the erase the source route table is dropped, yet ^IVF(name,cfg,table) still names it and the index answers. (`docs/ADMIN_GUIDE.md:322`; `live intent-a-hd0601-index-erasure`)

## As built

erase_graph removes rows, ^KG, temporal data and the graph's route table, but leaves ^IVF, ^VecIdx and ^PLAID untouched: ivf_search, vec_search and plaid_search keep answering the erased ids, and ^IVF keeps all their vectors.

Evidence: live `intent-a-hd0601-index-erasure`; inspected `iris_src/src/Graph/KG/Eraser.cls; iris_src/src/Graph/KG/GraphStores.cls:28-131`

## Intended contract

An index derived from a graph's own vectors (IVF via ivf_build(graph=)) holds that graph's content and falls under 'every store'; caller-fed indexes (VecIndex, PLAID: arbitrary ids and vectors) may be caller-managed but must be declared so in the inventory and docs. No source names these indexes either way. Status: assumption.

## Working assumption

Unchanged: model retained index contents as observable after erasure unless purged; graph-owned indexes require invalidation or deletion on erase; caller-fed indexes need an explicit owner/exposure statement. Refined with the graph-derived (IVF) vs caller-fed (VecIndex, PLAID) split.

## Alternatives

- (a) record each index's source graph and drop or prune it inside the erase
- (b) declare them caller-managed derived stores outside erasure; document and require a rebuild
- (c) refuse to build them over a named graph
- (d) erase marks dependent indexes stale and searches refuse until rebuilt

## Discriminating check

probe (run): `intent-a-hd0601-index-erasure`. fail: after erase_graph, IVF, VecIndex and PLAID each answered 3 erased ids; ^IVF still held 6 vectors.

## What would change this

A maintainer statement that vector indexes are caller-owned (then (b) plus inventory entries), or that ivf_build(graph=) makes the index part of the graph (then (a)/(d)).

## Residual question for maintainer

Is an IVF index built by ivf_build(graph=g) part of g's content for erasure (dropped or invalidated by erase_graph), and must VecIndex/PLAID be declared caller-managed in GraphStores and the ADMIN_GUIDE?

## Consequence rank hint

high: an erased tenant's node ids and vectors stay retrievable through search (retention/isolation), and a reused id can be attached to another tenant's node.

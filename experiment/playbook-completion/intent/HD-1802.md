# HD-1802 Should a snapshot be a point-in-time view?

Question ([decisions/18.md](../../playbook-uplift/decisions/18.md)): `save_snapshot` reads each table, then each
global, one after another, with no transaction, lock or ledger head check. Writes that land during a save can appear in
one store and not another. Options: (a) document that a snapshot is not a point-in-time view and should be taken while
writers are stopped; (b) take the ledger head lock (or a namespace-wide write lock) for the duration and record the head;
(c) read everything inside one transaction at a snapshot isolation level IRIS offers, if any.

## Contradictions

- `5fd382d5` (ADMIN_API "point-in-time snapshot") versus the code; resolved by `e146fc7a`, which removed the claim
  when the document was reviewed against the code. The divergent upstream branch `claude/python-rust-migration-rzf-2ec1u4`
  still carries the old wording (`docs/ADMIN_API.md:200` there).

## As built

Live, `ib-HD1802-torn-save` (expected-violation): a quiet save was consistent (ledger head 2, its node in the archived
table). With a commit from a second process forced between the table reads and the first global read, the archive's
`^IVG.Ledger` head was 3 and held seq 3's records while the archived `nodes` table lacked that commit's node:
replay(archived ledger) differs from the archived rows. Nothing in `save_snapshot` prevents the interleaving.

## Intended

No source promises a point-in-time view at the pin; the maintainer removed the only such claim when reviewing the docs
against the code, and the admin guide points to IRIS backups for backup. That removal is evidence, not an explicit
decision. Status: **assumption**.

## Working assumption

Claim a consistent snapshot only when writers are quiescent (an operator premise) or under a verified snapshot/epoch
protocol; for the current exporter declare the quiet-writer premise. Changed from decisions.md: **no**.

## Alternatives

- (b) Hold the ledger head lock (or a namespace write lock) for the save and record the head in `metadata.json`;
  covers ledger commits but not unledgered engine writers unless they take the same lock.
- (c) One IRIS transaction: IRIS SQL offers no MVCC snapshot read, so reads still see later commits; it does not close
  the window.

## Discriminating check

Probe `intent/probes/lane-b/hd1802_snapshot_interleaved_commit.py`, run, registry `ib-HD1802-torn-save`, result
**expected-violation** (no stated contract violated). Proposed minimal model: state {rows, ledger records/head,
archive}; actions Commit (atomic row + record), UnledgeredWrite (row only), SaveTables, SaveGlobals; property
replay(archive.ledger) == archive.rows restricted to ledger-governed content. Quiescence holds; (b) holds for Commit
but not for UnledgeredWrite unless that also takes the lock; (c) behaves like no lock.

## Confidence and what would change it

As built: high. Intent: medium-high. A maintainer statement that online saves must be consistent would make (b) the
contract.

## Residual question for the maintainer

May an operator be required to stop writers during `save_snapshot`, or must an online save be consistent? Working
answer: documented quiet-writer premise. Best alternative: hold the head lock and record the head in the archive.

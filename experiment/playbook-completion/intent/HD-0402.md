# HD-0402: May two adjacency rebuilds (sync()/BuildKG) run at the same time?

Status: **assumption** · Confidence: medium · Changed from decisions.md: no (Live check confirms the decisions.md reading (the cited lock protects only the ^NKG path); no new authority.)

## Question

May two adjacency rebuilds (sync()/BuildKG) run at the same time? BuildKG takes only the shared writer lock; only the ^NKG build has an exclusive lock (^IVG.NKGBuild), while ADMIN_GUIDE says 'One rebuild runs at a time'.

## Contradictions

- Read as describing sync(), 'One rebuild runs at a time' is false for the ^KG half: a second BuildKG completed (0.075 s) while another process held BuildKG's lock state. The sentence is literally true of ^NKG. (`docs/ADMIN_GUIDE.md:1049-1050`; `live intent-a-hd0402-two-rebuilds`)

## As built

Two ^KG rebuilds are admitted concurrently (shared lock only); two ^NKG rebuilds are serialized by ^IVG.NKGBuild (wait up to NKGBUILDWAIT=900 s, then raise). Not observed: the end state of two overlapping ^KG rebuilds. Non-indexed path: each kills and refills ^KG in its own transaction; an IRIS rollback of one restores pre-images (killing nodes the other set) - IRIS premise, not checked here. Indexed path: two %BuildIndices over the same index - IRIS behaviour not established.

Evidence: live `intent-a-hd0402-two-rebuilds`; inspected `iris_src/src/Graph/KG/TraversalBuild.cls:30-70,281-303`

## Intended contract

At most one publishing ^KG rebuild at a time, or concurrent rebuilds proven to converge to the rows even when one fails and rolls back. No source covers ^KG rebuild concurrency; the only explicit statement serializes ^NKG. Status: assumption.

## Working assumption

Unchanged: at most one publishing rebuild per adjacency structure; a second call waits or gets a documented busy result. Refined: ADMIN_GUIDE's sentence is literally about ^NKG and holds live; the ^KG half is unserialized.

## Alternatives

- A: allowed as today (last full fill wins) and documented
- B: serialize with an exclusive ^KG build lock like ^IVG.NKGBuild
- C: refuse a second call with a clear busy error
- D: prove convergence of concurrent rebuilds including rollback

## Discriminating check

probe (run): `intent-a-hd0402-two-rebuilds (plus a proposed model for the model lanes, in result)`. probe pass for the literal ADMIN_GUIDE claim (^NKG serialized: second BuildNKG waited 3.0 s until release); ^KG rebuild admitted concurrently (0.075 s). Proposed minimal model: rows R fixed; ^KG nodes with IRIS undo semantics (rollback restores the pre-image of each node the transaction set or killed, regardless of later writers); two rebuild actors with steps BeginRebuild(shared), TStart, RemoveAll-kill (non-indexed), fill(row i), chunk-commit at C rows, EndRebuild, and a fail step (TRollback). Property: when all actors finish, ^KG = derive(R) if none failed, and ^KG is derive(R) or the previous ^KG (no hole) if one failed. Distinguishing outcome: A (unserialized) has a counterexample where rebuild 1 rolls back after rebuild 2 refilled, leaving holes; B/C hold.

## What would change this

A maintainer statement that sync() is an operator action assumed single-flight (A documented), or a test/proof that two overlapping BuildKG runs (one rolled back) leave ^KG equal to the rows.

## Residual question for maintainer

Is a second sync()/BuildKG while one runs supported? If so, must the result equal one rebuild even when one of them fails and rolls back; if not, should it wait (B) or be refused (C)?

## Consequence rank hint

medium: an adjacency hole makes traversals and algorithms silently miss edges until the next sync; operator-triggered.

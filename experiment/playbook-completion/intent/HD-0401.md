# HD-0401: How should erase and rebuild retire a source generation?

Status: **assumption** · Confidence: medium · Changed from decisions.md: no (Live evidence confirms the ABA precondition; the spike's 'or kill' explains why the maintainer accepted the kill for stale entries, but neither source covers an in-flight reader, so the working answer stands.)

## Question

How should erase and rebuild retire a source generation? Adjacency.RemoveSource/RemoveGraph/RemoveAll kill ^KG("gen") instead of stepping it, so a generation can return to a value an in-flight degree reader already read (F-0401). Keep the kill (A), step with $Increment (B), or add an epoch (C)?

## Contradictions

- The accepted ADR and the implementing commit message say every adjacency write bumps the generation; the same commit's erase paths kill it, so the generation goes back (live: 2 -> undefined -> 2). (`docs/adr/0012-...md:31`; `commit 9c25eaab message`; `iris_src/src/Graph/KG/Adjacency.cls:376-377,437,461`)
- ADR says 'must bump'; its cited spike allows 'or kill the cache subtree'. (`docs/adr/0012-...md:31`; `docs/dev/notes/research/spikes/degree-cache/README.md:60-62`)
- Draft FR-004 'MUST move the source's degree generation'; a kill of a generation that is already 0 does not move it. (`specs/252-adjacency-functional-index/spec.md:111`; `Adjacency.cls:376`)

## As built

Erase paths (RemoveSource, RemoveGraph, RemoveAll) and the non-indexed rebuild kill ^KG("gen") with ^KG("degc"); later writes restart the counter, so it returns to earlier values. Adj.Degree stores a recount only if its lock probe succeeded and gen is unchanged, then re-reads gen. Live: gen 2 before erase, undefined after, 2 again after rewriting the same edges, on both erase_graph and delete_node; single-process degree answers stayed correct. The cross-process window (probe before the writer's lock, count after the kill, with tGen=0 or an ABA refill) was not exercised live.

Evidence: live `intent-a-hd0401-gen-return`; inspected `iris_src/src/Graph/KG/Adj.cls:55-90`; inspected `iris_src/src/Graph/KG/Adjacency.cls:376-377,437,461,824-830`

## Intended contract

A degree-cache entry must never be validated by a generation value that an erase or rebuild can recreate while a reader is in flight; how (step or epoch) is open. ADR-0012's text favours stepping, its spike and the code accept a kill, so no source settles the erase/rebuild case. Status: assumption.

## Working assumption

Unchanged from decisions.md: invalidation can never make an old degree-cache value valid again; model a monotone generation or a fresh graph epoch across erase and rebuild; keep as-built A (kill) as the baseline with its narrow window.

## Alternatives

- A: keep the kill and document the narrow window (erase/rebuild concurrent with degree readers)
- B: step the generation with $Increment and kill only degc (a residue counter per erased source remains)
- C: keep the kill, add a graph/namespace epoch stepped by every kill to each entry and to the reader's check

## Discriminating check

probe (run): `intent-a-hd0401-gen-return (plus a proposed model for the model lanes, in result)`. probe: generation returned to its pre-erase value on erase_graph and delete_node (fail vs the working property and ADR-0012's literal 'must bump'). Proposed minimal model: state gen[s], out[s], degc[s], per-transaction undo log, reader (pc, tGen, probeOk, count); reader actions R1 read gen, R2 no-wait exclusive probe (granted iff no writer holds the shared lock), R3 dirty count of out[s], R4 store (tGen,count) iff probeOk and gen=tGen, R5 re-read gen and kill entry if moved; writer actions Put (lock, set out, $Increment gen), RemoveSource/RemoveGraph (lock, kill out/gen/degc), rebuild (RemoveAll then refill through Put), commit, rollback restoring pre-images (not the reader's entry). Property: when no writer holds the lock, degc[s]=(gen[s],c) implies c = committed |out[s]|. Distinguishing outcome: variant A (kill) yields a counterexample (tGen=0 erase rolled back; refill ABA), B and C hold within bounds.

## What would change this

A maintainer statement that erase/rebuild require no concurrent degree readers (A becomes the documented contract), or that erasure must leave no per-node residue (rules out B, leaves C).

## Residual question for maintainer

Must a degree reader that overlaps an erase or rebuild never cache a wrong count (then step or epoch), or may erase/rebuild be documented as requiring no concurrent degree readers? If exact: is a residue counter per erased source acceptable (B), or is an epoch required (C)?

## Consequence rank hint

medium: a wrong out-degree served as current (degree, KHopCount, centrality, two-hop stats) until the next write to the source; narrow window; derived data, repaired by any write or rebuild.

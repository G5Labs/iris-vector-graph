## Contradictions

- ADR-0016's reason for refusal (two schemas sharing ^KG/^IVG.* globals) still occurs when the record is unreadable; the guide documents the skip (with a WARNING) rather than a refusal. (docs/adr/0016-one-ivg-schema-per-namespace.md:28; docs/ADMIN_GUIDE.md:516-519)
- Docstring and ADMIN_GUIDE scope the skip to a missing Native API privilege; the code skips on any non-IVGSchemaError exception (e.g. a transient driver error). (iris_vector_graph/engine.py:1853-1854; iris_vector_graph/engine.py:1863-1867)

## As built

A readable record naming another schema refuses the engine on first access (IVGSchemaError). If reading ^IVG.Deploy raises anything else, the engine logs a WARNING and is accepted unchecked, so an engine for another schema can run in the namespace.

Evidence: live: intent-a-hd0101-unreadable-record; inspected: iris_vector_graph/engine.py:1847-1868

## Intended contract

ADR-0016 fixes the binding (one IVG Schema per namespace, a mismatch is refused). No accepted source decides what happens when the record cannot be read. The guide documents fail-open as the result of a role missing a required resource, and R202 made that resource part of every documented role. Status: assumption.

## Working assumption

Supported deployments can read the record (premise: the ADMIN_GUIDE role table grants %Native_GlobalAccess:U). Under that premise a mismatch is refused. The documented fail-open path is a separate 'unchecked' outcome that admits a mismatched engine. It is outside the binding guarantee and should be modelled that way, not treated as an accepted engine.

## Alternatives

- (b) refuse like a mismatch until the record is readable (fail closed)
- (c) fail open for reads, refuse writes
- narrow the skip to the documented privilege error and refuse on any other exception

## Discriminating check

probe (run): `intent-a-hd0101-unreadable-record`. pass against the documented as-built (case 1 refused; case 2 WARNING and accepted). This separates as-built option (a) from (b) and (c). The policy question remains open.

## What would change this

A maintainer statement or spec clause that fail-open on an unreadable record is intended (would make the documented skip supported), or one that requires refusal (b/c).

## Residual question for maintainer

When IVG cannot read ^IVG.Deploy (a role without %Native_GlobalAccess, or another error), should the engine refuse, as for a mismatch, or warn and continue? Working answer: continuing is documented degraded behaviour outside the binding guarantee. Best alternative: refuse writes (or all access) until the record is readable.

## Consequence rank hint

medium: affects only misconfigured roles or read errors, but then two IVG schemas can share one namespace's globals and ledger

## Contradictions

None found.

## As built

/metaPath walks the default graph. A `graph` key in the body is ignored without error, so a caller who names a graph gets the default graph's answer.

Evidence: inspected `iris_src/src/Graph/KG/Service.cls:304-319; PyOps.cls:423-427`

## Intended

Status: **assumption**. Default-graph-only is consistent with the general rule that an omitted graph means the default graph. No source requires /metaPath to take a graph, and spec 230, which the search routes cite, is not available. Accepting `graph` would be a compatible extension. Ignoring a supplied `graph` silently is the weakest of the options.

## Working assumption

Treat /metaPath as default-graph-only and include that in its contract. A body naming `graph` should be refused or honoured, not ignored; until decided, model the silent ignore as the baseline.

Changed from decisions.md: **no**. Same reading. Added: spec 230 is absent from the repository and the mirror, and a supplied graph key is ignored silently.

## Alternatives

- (b) read `graph` from the body as the search routes do
- refuse a body that names a graph other than the default

## Discriminating check

probe (proposed): `live e2e: CreateWebApp in a scratch namespace (a web-application/role change reserved to the orchestrator), then POST /metaPath {srcId, graph:'g'} where g and the default graph differ`. Result: not run: the dispatcher needs a %CSP web application, which lane B may not create. Source is unambiguous.

## Confidence and what would change it

Confidence: medium. The text of spec 230, if it lists /metaPath, or a maintainer statement.

## Residual question for the maintainer

Should /metaPath accept `graph` like the search routes (spec 230 FR-014)? Working answer: default graph only, documented; a supplied graph should not be silently ignored. Best alternative: (b), read `graph`.

Consequence rank hint: low (One read-only route; the default-graph answer is consistent with the general rule.)

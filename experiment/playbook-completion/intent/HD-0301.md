## Contradictions

- The contract says the BulkLoader/raw-SQL exclusion is '(documented)', but the public guides never state it. A user reading USER_GUIDE could assume strict mode covers every IVG writer. (specs/213-graph-revision-ledger/contracts/ledger-api.md:93; docs/USER_GUIDE.md:1107-1121)

## As built

BulkLoader writes nodes, labels, properties and edges with no strict-mode check and no revision. verify() then reports those writes as unrecorded. Raw SQL is likewise unguarded.

Evidence: inspected: iris_vector_graph/bulk_loader.py; specs/213-graph-revision-ledger/contracts/ledger-api.md:82-93

## Intended contract

Strict mode is a client-side guard on the methods spec 213's contract enumerates. BulkLoader and raw SQL lie outside it by explicit statement in the spec contract. Status: supported.

## Working assumption

Exclude the standalone bulk loader and raw SQL from the strict-mode guarantee at this pin. Enumerate them as unguarded writers whose effects verify() reports. Do not count them as refused.

## Alternatives

- (b) BulkLoader reads Graph.KG.Ledger.Meta() and refuses in strict mode, as LedgerGuard does
- (c) server-side enforcement (a guard in the SQL path) covering raw SQL too

## Discriminating check

inspection (run): `iris_vector_graph/bulk_loader.py; ledger-api.md:82-93`. Decisive by inspection: the contract excludes BulkLoader explicitly and the loader has no guard. A live probe was not run because enabling the ledger in AUDITIA would create a namespace-wide genesis that the public API cannot undo, and other lane-A probes share the namespace. Proposed if wanted: scratch namespace, enable(strict=True), BulkLoader load, expect rows written, no revision, and verify() reporting them.

## What would change this

A later decision extending strict mode to the loader or to the server (would be a new contract).

## Contradictions

- `replay.py:588-606 + LedgerGenesis.cls:14-36 (a node is an id, across graphs)` vs `c53c654a R290 (a ledger node is the default graph's row)`: Verify and the apply path disagree on what a node is; a ledger delete of a node whose id is also (or only) in a named graph makes verify report unrecorded writes (F-1401; ib-HD1101-namedonly).
- `spec Decision 3 + client.py:691-692 (readers must not see a half-done redaction)` vs `client.py:720-728 + replay.py:231-269 (check once, then read lazily in pages)`: A redaction that starts, or wholly completes, between the reader's check and its last page gives a view that is neither the pre- nor the post-redaction history (ib-HD1401-reader-full-race; original reader_races_redaction).

## As built

(a) verify compares node ids across graphs while ledger node ops act on the default graph only. (b) readers check the marker once before a lazy paged read; see probe.

Evidence: live `ib-HD1401-reader-full-race`; live `ib-HD1101-namedonly`; inspected `iris_vector_graph/ledger/client.py:687-739; replay.py:231-269, 588-606, 806-835`

## Intended

Status: **assumption** (by part: (a) assumption, (b) supported (outcome)). (b) outcome supported: a reader returns a pre- or post-redaction view or refuses, never a half-done one (Decision 3, which replaced 'atomic from a reader's view', and the client's own message). The mechanism is not settled. (a) undecided at source level: nothing says whether verify or the R290 apply path defines node identity; R290's statement that the ledger keeps nodes in the default graph is the newer maintainer statement.

## Working assumption

(a) Compare the identity the ledger governs: default-graph node rows for node records (R290), with named-graph node rows either reported as outside node governance or recorded with their graph (linked to HD-1101/1304). (b) A reader takes a redaction epoch that every redaction start and finish advances, checks the marker, reads, and re-checks both; if either changed it refuses or retries. A post-read marker check alone is not sufficient (a whole redaction can complete inside one read); a shared lock or a genuine snapshot are alternatives. Verify additionally needs a coherent cut between its record read and its table read.

Changed from decisions.md: **yes**. (b) the mechanism changes: decisions.md left 'epoch validation, locking or snapshots' open and the original reviewed model used a second marker check; the new live probe shows a complete redaction inside one paged read (default page size), which a marker re-check cannot see, so the re-check must compare an epoch. (b)'s outcome is now cited as supported (Decision 3 history in 42907b21 and the client message).

## Alternatives

- (a1) verify becomes graph-aware for nodes (default graph for node records)
- (a2) R290 reverted to graph-blind node ops (rejected by R290's measured defects)
- (b1) post-read marker re-check (insufficient if a redaction completes inside the read)
- (b2) redaction epoch compared before/after (head or a redaction counter)
- (b3) readers hold a shared lock that redaction batches need exclusively
- (b4) snapshot reads

## Discriminating check

probe (run): `experiment/playbook-completion/intent/probes/lane-b/hd12_14_redaction_probes.py reader_full_race -> $RUN_DIR/intent-b/ibR_reader_full_race.log; registry ib-HD1401-reader-full-race`. A post-read marker re-check cannot detect this; an epoch comparison can. (a) side: ib-HD1101-namedonly shows verify() diverging after a ledger delete_node of a named-graph-only node.

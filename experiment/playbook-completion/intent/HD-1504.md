# HD-1504 Should one unreadable FHIR resource block its graph's sync?

Question ([original](../../playbook-uplift/decisions/15.md)): A resource whose body is not JSON, nests deeper than 64 levels, or has more than 10,000 json-link matches makes ResyncKey throw; its batch rolls back and the watermark stays, so every later sync fails on the same batch. Skip/quarantine, keep failing (documented), or skip after N failures?

## Contradictions

- `docs/FHIR_GRAPH.md:258-259 ('any sequence of syncs converges on the graph a rebuild would build')` vs `FHIRGraph.cls:2380-2397,2976-2988 + Rebuild:448-540`: With one unreadable resource every sync and every rebuild fails, so no sequence of syncs converges and the later changes never arrive; the guide states the failure of the batch but not the indefinite stall or a recovery procedure.

## As built

The batch containing the resource throws, rolls back with its watermark, and RecordError writes last_error naming the key; each later sync repeats the same batch and fails; a rebuild also fails on it. Progress resumes only after the resource is repaired or deleted in the repository, or json links are turned off (re-register with json_links=[], which triggers a rebuild that no longer reads bodies).

Evidence: inspected `iris_src/src/Graph/KG/FHIRGraph.cls:543-626,1920-1978,2039-2056,2380-2397,2976-2988`; tested `tests/e2e/test_231_fhir_graph_sync_e2e.py::test_crash_before_commit_leaves_nothing`

## Intended

Status: **supported**. Fail the batch, name the key, keep the watermark, repeat on the next sync (no skip). Stated for the walk limits (FHIR_GRAPH.md:196-199) and for any failed batch (:255-257). The resulting indefinite stall and its recovery are not documented.

## Working assumption

Failure without advancing the watermark is the documented contract (not a choice to revisit silently). Surface the offending key (already in last_error) and treat the missing recovery procedure (repair/delete the resource, or json_links=[]) as a documentation gap; do not assume silent skips.

Changed from decisions.md: yes. Status raised from assumption to supported for the failure semantics: FHIR_GRAPH.md:196-199 (maintainer commit 59286731) explicitly states that a walk limit fails the batch, and :255-257 that a failed batch repeats. Added that a rebuild fails too, and the json_links=[] recovery path.

## Alternatives

- (a) record the key in fhir_unresolved (new reason) and continue
- (b) keep failing and document how an operator finds and fixes the resource (last_error names it)
- (c) skip only after N repeated failures

## Discriminating check

Kind: model; status: proposed.

Reference: Minimal model: repo keys in batches b1,b2,b3 with k_bad in b2; actions Sync (applies batches in order, b2 throws), Change(k in b3), Repair(k_bad), RegisterNoLinks, Rebuild. Liveness property L: every Change is eventually reflected in G without Repair.

Result: As-built: Sync;Change;Sync leaves wm at end of b1 and the change absent; Rebuild also fails -> L violated without Repair or RegisterNoLinks; (a) quarantine -> b2 commits minus k_bad, L holds; (c) L holds after N attempts. Not run live: no FHIR repository in AUDITIB.

## Confidence and what would change it

Confidence: medium. A maintainer statement that partial indexing is acceptable (quarantine); evidence that HS.FHIRServer can hold a body that makes the walk fail in practice (otherwise the stall is mostly theoretical for non-JSON bodies).

## Residual question for the maintainer

Is a FHIR graph that stalls on one unreadable resource acceptable (operator repairs it, procedure documented), or should the key be quarantined so later changes keep flowing? Working: keep failing, document the recovery. Best alternative: quarantine with a reason in fhir_unresolved.

Consequence rank hint: medium (Liveness loss of the whole FHIR graph from one resource, visible only through last_error; no corruption.)

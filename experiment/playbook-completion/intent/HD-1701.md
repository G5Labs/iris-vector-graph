# HD-1701 Should the SQL adapter's pass-through refuse a write when called read-only?

Question ([original](../../playbook-uplift/decisions/17.md)): IRISGraphStore.execute_sql(sql, params, read_only=True) and the GraphStore protocol carry a read_only flag that nothing reads. Promise (refuse non-SELECT when True), leftover (remove), or documentation only?

## Contradictions

- `store_protocol.py:30-33 (an ignored protocol parameter answers the wrong question; raise instead)` vs `iris_sql_store.py:1522-1554 (read_only ignored)`: The protocol's own design rule for semantic parameters is violated by the read_only parameter.

## As built

Live on AUDITIB: with read_only=True an INSERT into Graph_KG.nodes and a CREATE TABLE both executed. Each also came back with IVGResult.error '<USAGE ERROR> ... did not return a result set' (fetchall on a statement with no result set), so a caller is told the write failed although it ran (new observation).

Evidence: live `ib-HD1701-readonly-flag`; inspected `iris_vector_graph/stores/iris_sql_store.py:1522-1554`

## Intended

Status: **assumption**. Undocumented flag; the protocol's design rule (raise rather than ignore a semantic parameter) and the enforced engine-level read_only point to 'a requested guarantee', but no source defines execute_sql's flag.

## Working assumption

Keep decisions.md: read_only=True is a requested guarantee; enforce it at a trusted boundary (refuse non-SELECT before it runs) or refuse/remove the unsupported flag in a versioned change. The engine's own use (reads only) makes enforcement compatible with internal callers.

Changed from decisions.md: no. Live probe confirms the flag is ignored; added the protocol's raise-not-approximate rule as supporting evidence and the misreported-error observation.

## Alternatives

- (a) enforce: refuse a non-SELECT statement with a clear error before it runs
- (b) remove the parameter from the protocol and the adapter
- (c) keep as documentation only and say so

## Discriminating check

Kind: probe; status: run.

Result: expected-violation: DML and DDL executed under read_only=True; the result reported an error for the executed write.

## Confidence and what would change it

Confidence: medium. A spec 156 text or maintainer statement on the flag; external GraphStore implementations relying on it.

## Residual question for the maintainer

Is GraphStore.execute_sql's read_only a promise (enforce) or a leftover (remove)? Working: enforce, since the engine only reads through it. Best alternative: remove it in a versioned protocol change.

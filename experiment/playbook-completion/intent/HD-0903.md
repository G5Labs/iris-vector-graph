## Contradictions

- The spec explains own-writes visibility by 'same process'. As built, it comes from IRIS's uncommitted reads (F-0909). (specs/253-native-cypher-executor/spec.md:91-92; experiment/playbook-uplift/findings/09.md:115-130)
- Possible tension for the ledger lanes: per-statement dirty visibility (observed) lets a reader see part of one transaction. The USER_GUIDE's 'at no moment' claim holds for a reader looking after the commit call returns, but was not shown for a reader running during the call. This is noted for HD-1401, not tested here. (docs/USER_GUIDE.md:263-265; intent-a-hd0903-native-read-open-txn)

## As built

Native reads take no lock or snapshot and read ^KG, the label and property stores at moments spread over the walk. Live: while writer A's transaction was open, B's native read and B's SQL-path read agreed at every step. Both saw A's uncommitted edge before its far node's label (unlabelled [b], labelled []), then the label, and nothing after A's ROLLBACK.

Evidence: live: intent-a-hd0903-native-read-open-txn; inspected: iris_src/src/Graph/KG/Cypher/Exec.cls:33-50

## Intended contract

Option (a): dirty, per-store moment reads, the same as the SQL path at IRIS's default isolation. The USER_GUIDE documents this for a second connection's MATCH/SELECT, and FR-002 requires native to equal SQL. No source promises transaction-atomic visibility for readers. Status: **assumption**.

## Working assumption

Allow the observed interleavings on both paths: a native or SQL read may see a writer's uncommitted writes, including part of one transaction, and loses them on rollback. Grant snapshot or all-or-nothing visibility only to paths with an explicit synchronization contract and evidence (none for Cypher reads). The ADR-0012 degree cache is the one guarded structure.

## Alternatives

- (a) dirty per-store reads, documented as equal to the SQL path's default isolation
- (b) readers wait on a lock writers hold (cost: every native read)
- (c) a version/epoch check before and after the walk, retrying when a writer committed in between (does not cover uncommitted writes)

## Discriminating check

probe, run: intent-a-hd0903-native-read-open-txn

Result: pass: native == SQL at each interleaving step; partial transaction visible; rollback removes it

## What would change this

A maintainer statement promising committed-only or atomic visibility for Cypher reads, or a change of the engine connections' isolation level (then native and SQL could diverge, F-0909).

## Residual question for maintainer

Is 'whatever each store holds when read, including part of another writer's open transaction' the promise for Cypher reads on both paths (as USER_GUIDE:260-262 says for MATCH/SELECT), or must a read see a writer's transaction all or nothing? Working answer: (a), documented as such for the native path too. Best alternative: (c), an epoch check for committed changes.

# HD-1704 Should the low-level vector helper refuse a vector of the wrong width?

Question ([original](../../playbook-uplift/decisions/17.md)): dbapi_utils.normalize_vector pads a short vector, truncates a long one and turns NaN/Inf into 0.0; insert_vector then writes it. The engine's writers refuse a width mismatch (ADR-0006). Which rule do the public helpers follow?

## Contradictions

- `docs/adr/0005:20-23 (column width is where enforcement lives)` vs `dbapi_utils.py:29-98 (pads/truncates before the column sees the vector)`: Not a contradiction of either decision's scope (ADR-0005 is about query vectors, ADR-0006 about registered engine tables), but used on a width-declared table the helper silently defeats the column's enforcement (probe: raw 3-wide INSERT refused with -104, helper stored it padded).

## As built

normalize_vector pads [1,2] to [1,2,0,0], truncates 6->4 and maps NaN/Inf to 0.0 (logged only under IRIS_VECTOR_DEBUG); insert_vector stores the coerced vector in a VECTOR(FLOAT,4) column that refuses the same 3-wide vector by raw SQL (SQLCODE -104).

Evidence: live `ib-HD1704-helper-coercion`; tested `tests/unit/test_dbapi_utils_unit.py:22-51`

## Intended

Status: **supported**. The helper contract is lossy coercion (docstring); registry-aware engine writes are strict (ADR-0006). Two boundaries, both stated.

## Working assumption

Keep decisions.md: normalize_vector/insert_vector keep their documented coercion; engine writes stay strict; test both boundaries separately. Strict validation for the public helper is a compatibility decision, and its lossy behaviour should be visible in the API reference.

Changed from decisions.md: no. Probe passes against the docstring; added the ADR-0005 tension and the absence of the helpers from API_REFERENCE.

## Alternatives

- (a) refuse a width mismatch and non-finite values, as the engine does
- (b) keep coercion and document it as lossy (current docstring)

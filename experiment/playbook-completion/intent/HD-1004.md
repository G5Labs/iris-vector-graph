## Contradictions

- `PageRank.cls:517-519 (cap)` vs `algorithms.py:749-752; PageRank.cls:403-405; COMMUNITIES.md:212-216`: The docs say every node is listed and the scores sum to 1; the owner lists 10,000 nodes.
- `PageRank.cls:517-519 (owner)` vs `iris_sql_store.py:2396-2399 and spec 236 spec.md:94-96`: Above 10,000 nodes the owner and native node sets differ, against the spec's equivalence rule. The gate's small fixtures cannot see this.

## As built

The owner, called exactly as _execute_pagerank calls it with 10,050 edgeless ids, returns 10,000 rows whose scores sum to 0.995025. The native-route ranking (_ranked_rows(rows, 0)) keeps all 10,050.

Evidence: live `ib-HD1004-pagerank-cap`; inspected `iris_src/src/Graph/KG/PageRank.cls:506-520`

## Intended

Status: **supported**. (a): every node of the default graph is listed on every route, and the scores sum to 1 over node_count(). The 4.6.0 R306 docstring (a node with no edge used to have 'no pair') and spec 236's same-node-set rule settle it. The 10,000 cap is an undocumented 2026-03 leftover.

## Working assumption

Every node on every route. Record the owner's cap as a defect against the docstring and spec 236. A top_k with a stated default would be a separate, versioned API change.

Changed from decisions.md: **yes**. Status moves from assumption to supported. The R306 docstring and spec 236 scenario 3 already state the contract; decisions.md waited for 'a documented limit', which does not exist.

## Alternatives

- (b) 10,000 on every route, documented
- (c) a top_k with a stated default (as leiden_communities: 10,000, top_k=0 for all)

## Discriminating check

probe (run): `experiment/playbook-completion/intent/probes/lane-b/hd1004_pagerank_cap.py; ib-HD1004-pagerank-cap`. Result: fail: owner returns 10,000 of 10,050+ nodes (sum 0.995); native ranking keeps all.

## Confidence and what would change it

Confidence: high. A maintainer statement that the 10,000 cap is intended, which would also need the docstring and the spec 236 equivalence rule amended.

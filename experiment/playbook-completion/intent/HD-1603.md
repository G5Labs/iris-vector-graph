# HD-1603 Should the Cypher HTTP server run a failed query a second time?

Question ([original](../../playbook-uplift/decisions/16.md)): `_run_cypher` resets the engine and runs the query again after any exception, writes included. A write whose commit reached IRIS before the error is applied twice. Retry everything once, retry only reads or pre-execution connection errors, or never retry?

## Contradictions

- `commit 9c683292 (v1.47.0): retry only on COMMUNICATION/LICENSE` vs `commit 7d62dbf5 (v1.48.0): retry on every exception`: The retry policy changed without a stated reason, in a commit about something else.

## As built

An in-process run of the pin's app on AUDITIB injected faults into the first engine only. In (A) the CREATE committed and then a ConnectionError was raised: HTTP 200 and the node was written twice. In (B) a ValueError was raised before execution: the query was retried on a fresh engine. Every exception type is retried once, writes included.

Evidence: live `ib-HD1603-server-retry`; inspected `iris_vector_graph/cypher_api.py:239-250`

## Intended

Status: **assumption**. No spec or doc states the policy. The earliest maintainer code retried only connection or licence failures, which is evidence for (b). The widening was not explained. Re-running a write whose commit outcome is unknown conflicts with the project's own idempotency design, which keeps it in the ledger.

## Working assumption

Retry a read, or a write known not to have executed (a connection error raised before the statement was sent). Never re-run a write whose outcome is unknown; return an error that says the outcome is unknown. A write carrying a verified idempotency key may be retried.

Changed from decisions.md: **no**. Same direction as decisions.md. New history evidence (9c683292 to 7d62dbf5) and a live duplicate write strengthen it.

## Alternatives

- (a) retry every query once [as built]
- (c) never retry; return the error

## Discriminating check

probe (run): `experiment/playbook-completion/intent/probes/lane-b/hd1603_server_retry.py; ib-HD1603-server-retry`. Result: expected-violation: one request, ambiguous first outcome, two nodes written; a ValueError is retried too.

## Confidence and what would change it

Confidence: medium. A maintainer statement that availability outweighs duplicate writes, with documentation that writes must be idempotent (MERGE). Or a server-side idempotency key.

## Residual question for the maintainer

Should the Cypher HTTP server retry a write whose commit outcome is unknown? Working answer: no; retry only reads or writes known not to have executed (as in v1.47.0). Best alternative: never retry. HD-1702 matters too: client retries multiply server retries.

Consequence rank hint: high (Duplicate writes with a 200 answer, silently; also reached through the Neo4j tx/commit route and composed with client retries (HD-1702).)

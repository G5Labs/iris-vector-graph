# HD-1502 Should erasing a FHIR graph stop its sync task?

Question ([original](../../playbook-uplift/decisions/15.md)): EraseGraph keeps the fhir_graphs row and zeroes both watermarks; a scheduled FHIRGraphSyncTask keeps running and its next run re-projects the whole repository. Should erase unschedule the task, leave it (documented), or should a separate deregister command exist?

## Contradictions

- `specs/256-ledger-tenant-redaction/spec.md:17-18 (tenant erasure = EraseGraph + redaction)` vs `Eraser.cls:1146-1180 + FHIRGraphSyncTask.cls (task survives, refills)`: For a FHIR graph erased for a tenant, the next task tick refills the graph and redaction then refuses target_live; nothing in spec 256 or FHIR_GRAPH.md says the task must be unscheduled first.

## As built

EraseGraph deletes content, unresolved/canonical rows, zeroes wm_rsrc/wm_ver and nulls interp_version; fhir_graphs (including task_id) is kept; the Task Manager task keeps running SyncOnce, which with watermarks at 0 re-projects the whole repository. No single-graph deregistration call exists (only EraseAll removes registry rows); after unschedule, a manual fhir_graph_sync or `ivg fhir sync` still refills.

Evidence: inspected `iris_src/src/Graph/KG/Eraser.cls:1146-1180`; tested `tests/e2e/test_231_fhir_graph_sync_e2e.py::test_erase_keeps_registration_and_resets_watermarks`; inspected `iris_src/src/Graph/KG/FHIRGraphSyncTask.cls:1-27`

## Intended

Status: **supported**. Erase of a FHIR graph is a transient content clear that keeps registration (supported: Eraser.cls comment, CHANGELOG 4.1.0, ADR-0015:29, upstream E2E test). Whether a durable tenant removal must also stop the feed is not stated anywhere.

## Working assumption

Separate transient clear from decommissioning. Ordinary erase keeps registration and task (supported). For durable tenant removal require, as a stated premise, unschedule before erase and no manual sync afterwards, and verify the graph stays empty before redaction; at the pin there is no single-graph deregistration, so 'deregister' is a new command, not an available step.

Changed from decisions.md: yes. Status raised to supported for the transient-clear half (ADR-0015:29 and the Eraser comment settle it). Refined the durable-removal half: decisions.md offered 'paused or deregistered', but no single-graph deregistration exists at the pin and an unscheduled graph still accepts manual syncs.

## Alternatives

- (a) erase also unschedules the task (clears task_id)
- (b) as built, plus documentation that an erased FHIR graph refills unless unscheduled
- (c) a deregister command removing registration, task and content together

## Discriminating check

Kind: model; status: proposed.

Reference: Minimal model: state {registered, task: none|scheduled, wm, repo R non-empty, graph G}; actions Erase, Tick (SyncOnce when scheduled), ManualSync, Unschedule, Redact (refuses when G non-empty). Property 'durable removal': after Erase;Redact, G stays empty.

Result: Trace Erase;Tick;Redact: as-built -> G = f(R), Redact refused target_live; (a) -> Tick no-op, Redact ok; (c) -> registry gone, Tick/ManualSync impossible. Trace Unschedule;Erase;ManualSync distinguishes (a)/(b) (refill) from (c) (refused). Not run live: no FHIR repository in AUDITIB; creating a %SYS.Task is a container-level change outside scope.

## Confidence and what would change it

Confidence: high. A spec 256 / FHIR_GRAPH statement about tenant removal of a FHIR graph; an erase that touches task_id.

## Residual question for the maintainer

For removing a tenant's FHIR graph, is erase+unschedule (with no later sync) the supported procedure, or should erase or a new deregister command stop the feed? Working: erase stays a transient clear; durable removal needs an explicit stop. Best alternative: erase unschedules the task.

Consequence rank hint: high (PHI-bearing tenant content returns automatically after erase and blocks redaction; spec 256's tenant-erasure story fails for FHIR graphs.)

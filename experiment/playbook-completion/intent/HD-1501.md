# HD-1501 Should a FHIR sync be governed by the ledger?

Question ([original](../../playbook-uplift/decisions/15.md)): A FHIR sync, rebuild and reinterpret write nodes, labels, properties and edges of the FHIR graph from ObjectScript (Graph.KG.FHIRGraph) with no ledger record, and strict mode does not refuse them. Should the FHIR graph be an exempt projection, refused under strict mode, or recorded as revisions?

## Contradictions

- `docs/USER_GUIDE.md:1107-1109` vs `iris_vector_graph/_engine/fhir_graph.py:251-258 + guard.py:75-80`: The guide says strict mode refuses writes outside the ledger made by 'the other methods'; FHIR sync/rebuild/reinterpret write structural rows unrefused.
- `CONTEXT.md:60-63 ('Subject to the revision ledger')` vs `docs/FHIR_GRAPH.md:255-259,567 (projection of the repository)`: Glossary puts every structural edge under the ledger; the FHIR guide treats the FHIR graph as a recomputable projection whose history lives in the repository.
- `ledger-api.md:84-93 (exhaustive guarded list + named exceptions)` vs `FHIR engine methods`: FHIR sync is neither in the guarded list nor in the documented exceptions: the contract is silent, not explicit.

## As built

fhir_graph_sync/rebuild/fhir_reinterpret run Graph.KG.FHIRGraph directly: no ledger record, no strict check (FHIRGraph.cls never reads ^IVG.Ledger); verify() reads every graph and would report the FHIR rows as unrecorded writes (verify(adopt=True) would record them).

Evidence: inspected `iris_vector_graph/_engine/fhir_graph.py:251-258`; inspected `iris_vector_graph/ledger/replay.py:806-849`; inspected `iris_src/src/Graph/KG/FHIRGraph.cls (no ^IVG.Ledger read; grep at pin)`

## Intended

Status: **assumption**. No authoritative source decides. The FHIR guide describes a projection that converges on the repository (supports exemption); the user guide and glossary describe strict mode/ledger coverage broadly enough to include it.

## Working assumption

Keep decisions.md: the FHIR graph is an external writer of a rebuildable projection at the pin. verify() keeps reporting its rows (never silently 'equal'); strict mode is not a guarantee for FHIR namespaces until FHIR writes are either refused under strict or recorded.

Changed from decisions.md: no. Sources confirm the working answer; added that ledger-api.md's exhaustive list is silent on FHIR (not an explicit exemption) and that verify() reads every graph.

## Alternatives

- (a) declare FHIR graphs ledger-exempt projections; verify() skips them and strict documents the exemption
- (b) refuse rebuild/sync/reinterpret while strict is on (needs a server-side check: the Python guard does not cover ObjectScript)
- (c) record each committed batch as a ledger revision

## Discriminating check

Kind: model; status: proposed.

Reference: Minimal model: state {ledger: off|on|strict, repo R, FHIR graph G, ledger records L}; actions Sync (G := f(R) for one batch), SetStrict, Verify. Property under test: after Sync with strict on, Verify = equal and L unchanged.

Result: Distinguishes: as-built -> Sync succeeds, Verify = diverges (G rows listed); (a) -> Verify = equal (G excluded); (b) -> Sync refused, G unchanged; (c) -> Verify = equal and |L| grows by one revision per batch. Not run live: AUDITIB (IRIS Community) has no HS.FHIRServer repository (checked: 0 HS.FHIRServer classes, no HS_FHIRServer tables), so a sync cannot be driven.

## Confidence and what would change it

Confidence: medium. A maintainer statement or spec text placing FHIR graphs inside or outside the ledger; a strict-mode check in FHIRGraph.cls.

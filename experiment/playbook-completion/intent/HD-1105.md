# HD-1105 Should post-commit properties be recorded by the ledger?

Question ([decisions/11.md](../../playbook-uplift/decisions/11.md), findings F-1101, F-1306): `post_commit_properties`
(spec 218, "Approach A: direct SQL, no new revision") write `rdf_props` rows outside the revision; `verify()` reports
them, redaction's liveness check sees them, replay never rebuilds them, and a replayed retry writes them again.
Options: (a) make them `set_prop` records of the same revision; (b) keep Approach A and document that every post-commit
property makes `verify()` diverge until adopted; (c) drop the feature.

## Contradictions

- The "intentionally unledgered" user-guide sentence (`69a4966c`) was dropped in `9b313a2c`; the pin's user guide no
  longer tells a reader that post-commit properties make `verify()` diverge. Code comments, the changelog and the 4.7.0
  test comment still state Approach A. Documentation gap, not a reversal.
- Approach A plus the replay contract: a replay re-applies the properties (live), contradicting "applies nothing"
  (F-1101; consequence handled under HD-1305).

## As built

Live, `ib-HD1105-approach-a` (pass): a commit with `{ib3_p1: {audit: $REVISION_ID}}` wrote the property with no
record in the revision; `verify()` reported it as `unrecorded_writes`. Live, `ib-HD1105-replay-reapplies` (fail): after a
governed `set_property(ib3_p1, audit, "manual")`, a retry with the first key returned `replayed=True` and wrote the old
value back over the governed one.

## Intended

Supported by the maintainer's spec 218 choice (changelog, `69a4966c` user-guide text, code comments) and its retention
through R281 and 4.7.0: post-commit properties are a deliberate unledgered direct write; their `verify()` divergence is
an acknowledged consequence. The replay contract separately requires that a replay apply nothing. Status:
**supported**.

## Working assumption

Treat post-commit properties as a separate direct write outside revision replay; `verify()` reports them until
adopted. Require that a replayed commit not re-apply them (idempotency contract), recording the pin's re-application as
a defect (F-1101). Changed from decisions.md: **no**.

## Alternatives

- (a) Record them as `set_prop` records of the same revision (server substitutes the revision id).
- Skip post-commit properties on `replayed=True` only (keeps Approach A; closes F-1101).
- (c) Drop the feature.

## Discriminating check

Probe `intent/probes/lane-b/hd1105_post_commit_properties.py`, run, registries `ib-HD1105-approach-a` (pass) and
`ib-HD1105-replay-reapplies` (fail).

## Confidence and what would change it

High. A maintainer decision to fold them into the revision would change the working assumption.

## Residual question for the maintainer

None for the intent. (Restoring the dropped user-guide sentence is a documentation item; the replay re-application is

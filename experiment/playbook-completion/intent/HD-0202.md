## Contradictions

- The guide says 'deletes one edge'. In a multigraph the designed and as-built behaviour deletes every parallel edge of the triple. The wording only fits single-edge graphs. (docs/USER_GUIDE.md:462; specs/234-multigraph-parallel-edges/plan.md:160-162)
- Side observation: FR-007 ('In a multigraph graph, create_edge MUST always create a new edge') is not met at the pin. The second direct create_edge returned False and wrote nothing (T033 open; spec marked partially implemented). Parallel edges come only from Cypher. (specs/234-multigraph-parallel-edges/spec.md FR-007; intent-a-hd0202-multigraph-delete)

## As built

delete_edge(s, p, o, graph=g) deletes every row of the triple in g (all parallel edges) and the ^KG entry, returning True. There is no edge_id/ekey argument. A single parallel edge can be deleted only through Cypher DELETE r.

Evidence: live: intent-a-hd0202-multigraph-delete; inspected: iris_vector_graph/_engine/nodes_edges.py:1382-1433

## Intended contract

Spec 234's plan (maintainer, 2026-09-26) settles the default. With no edge_id, delete_edge removes every parallel edge of the triple ('today's meaning'). An optional edge_id= for one edge is designed but unimplemented (T033). Status: supported.

## Working assumption

Triple-wide delete is the direct API's contract when no edge id is given. Single-edge targeting is a separate, planned operation (edge_id=) and is not available at the pin. Model Cypher's per-edge DELETE separately.

## Alternatives

- (b) refuse with an ambiguity error when the triple has several edges, unless an edge key or id is given (the ledger's ambiguous_tuple precedent)
- (c) as designed: add edge_id=/ekey= and keep triple-wide as the default (planned, T033)

## Discriminating check

probe (run): `intent-a-hd0202-multigraph-delete`. pass against the spec 234 plan: two parallel rows (ekey 0 from create_edge, ekey 1 from Cypher CREATE); one delete_edge left 0 rows and no ^KG out entry; edge_id= raised TypeError. Side observation: the second direct create_edge returned False (FR-007 unmet).

## What would change this

A later maintainer statement (e.g. for the 4.8.0 parallel-by-default change) that delete_edge must refuse ambiguous triples or delete one edge.

## Residual question for maintainer

When parallel relationships become the default (planned 4.8.0), should delete_edge(s, p, o) without an edge id still delete every parallel edge, or refuse as the ledger does (ambiguous_tuple)? Working answer: triple-wide per spec 234 plan, with edge_id= for one edge. Best alternative: refuse ambiguous triples.

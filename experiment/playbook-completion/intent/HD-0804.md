## Contradictions

- The USER_GUIDE says a query that does not parse raises; constraint/index DDL is not parsed but answers an empty success, and the guide does not mention it. (docs/USER_GUIDE.md:313; iris_vector_graph/_engine/query.py:1886-1895)
- Minor inconsistency: execute_cypher treats the DDL as harmless (no-op), yet read_only=True refuses it as a mutation/unparsed query. (iris_vector_graph/_engine/query.py:1886-1895; intent-a-hd0804-constraint-noop)

## As built

The nine DDL prefixes return an empty result with no error and no metadata warning, and create nothing. A duplicate of a declared-unique value is stored. SHOW CONSTRAINTS does not list the requested constraint, so a caller who checks can find out. With read_only=True the DDL raises PermissionError.

Evidence: live: intent-a-hd0804-constraint-noop; inspected: iris_vector_graph/_engine/query.py:1886-1895; tested: tests/unit/test_query_unit.py:101-106

## Intended contract

Accept constraint/index DDL as a no-op for Neo4j-tool compatibility. It establishes no uniqueness or index invariant (maintainer commit f4a13d75). Whether the no-op should also be signalled or documented is not settled. Status: **supported**.

## Working assumption

Treat the accepted DDL as an acknowledged no-op that establishes no invariant (supported by f4a13d75 and pinned by tests). Model no uniqueness guarantee from it. As a proposed strengthening, not a decision: document it in USER_GUIDE beside the parse-error rule and add a metadata warning. Refusal (option c) would reverse a maintainer decision.

## Alternatives

- (a) keep the silent no-op and document it
- (b) answer with a warning in metadata
- (c) refuse with an error saying IVG keeps no constraints

## Discriminating check

probe, run: intent-a-hd0804-constraint-noop

Result: pass: silent no-op confirmed live (empty result, no warning, duplicate stored); SHOW CONSTRAINTS omits it; read_only refuses it.

## What would change this

A later maintainer statement or spec requiring refusal or warnings for unsupported DDL. A TCK/compatibility requirement that conflicts with the no-op.

## Residual question for maintainer

Low priority: should the accepted no-op be documented in the USER_GUIDE (beside 'a query that does not parse raises') and signalled with a metadata warning? Working answer: document it and warn. Best alternative: document it only.

## Contradictions

- ADR-0014 says a compiled class answers exactly as the interpreter does and that the interpreter covers every non-compiled shape. A compiled class that raises where the interpreter would answer breaks that invariant, and nothing sets the entry aside, so every later read repeats the failure and is answered by SQL. (docs/adr/0014-native-plans-are-compiled-to-classes-at-run-time.md:19-20; iris_src/src/Graph/KG/Cypher/Exec.cls:198-199)

## As built

Exec.RunA calls the compiled Walk1 without a catch. A run-time error (a generator defect, or a class deleted outside DropAll while its entry stays 'ok') leaves Run. The engine answers the read on the SQL path with one warning per reason per engine, and the entry stays 'ok', so each later read of that shape fails natively first. Not run live: exercising it needs a compiled IVGC class, which lane rules forbid (Gen mode is off in every probe).

Evidence: inspected: iris_src/src/Graph/KG/Cypher/Exec.cls:153-199; inspected: iris_src/src/Graph/KG/Cypher/Gen.cls:61-106; inspected: iris_vector_graph/_engine/query.py:2146-2152

## Intended contract

ADR-0014's invariant (a compiled class answers as the interpreter) and spec 257 FR-004 (the interpreter is the fallback) point to the interpreter answering a shape whose compiled class fails, with the entry set aside like a failed build. The ADR's enumerated cases omit run-time failure, and FR-004 is draft. Status: **assumption**.

## Working assumption

Treat a run-time failure of a compiled entry as a fallback outcome: quarantine the entry for that plan generation (as a failed build already is), let the interpreter answer, and retry only after invalidation (a new stamp, DropAll or a deploy). SQL fallback for every later read (as built) is a correct-answer but degraded baseline that violates ADR-0014's 'answers exactly as the interpreter'.

## Alternatives

- (a) keep today's behaviour (SQL answers, one warning per reason per engine)
- (b) catch errors from Walk1 in RunA, mark the entry failed and re-run the walk interpreted
- (c) mark the entry failed but let SQL answer this read

## Discriminating check

model, proposed: Minimal model. State: entry(s) in {absent, pending, ok, failed}; class(s) in {present-good, present-faulty, absent}. Actions: Read(s), BuildOk, BuildFail, ExternalDelete(class), DropAll/Deploy (clear both). Property Q1 (ADR-0014): every Read(s) is answered by native (compiled or interpreter) whenever the interpreter would answer. Q2: after the first run-time fault of s, no later Read(s) invokes the faulty class until invalidation. As-built trace Read(ok, absent class) -> raise -> SQL, repeated, violates Q1 and Q2; (b) satisfies both; (c) satisfies Q2 only. Live probe design (needs a namespace where compiling is allowed): Gen.Mode('sync'); a one-hop read builds IVGC.P<h> ('ok'); $System.OBJ.Delete the class, leaving the entry; read twice; observe ^||IVG.CypherCompiledRuns, engine._native_answers, warnings and the entry status (as built: compiled run attempted each time, native counter unchanged, entry 'ok').

Result: not run: needs a compiled class (forbidden in AUDITIA); inspection shows no catch around Walk1 and no entry demotion

## What would change this

A maintainer statement that SQL fallback is the intended recovery for compiled failures, or an amendment of ADR-0014's invariant to exclude run-time faults.

## Residual question for maintainer

When a compiled plan raises at run time, should the entry be set aside and the interpreter answer (extending ADR-0014's list), or is SQL fallback on every later read acceptable? Working answer: quarantine the entry and let the interpreter answer (b). Best alternative: quarantine with SQL answering this read (c).

## Consequence rank hint

low: answers stay correct through SQL; cost is repeated failure, latency and log noise

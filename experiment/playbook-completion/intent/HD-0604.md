## Contradictions

- The maintainer designed the queue as single-processor, but the public API offers two workers (IRIS task and Python process_embed_queue) and no user document states or enforces the single-worker rule. (`commit 5bb149ed`; `iris_src/src/Graph/KG/EmbedQueue.cls:22-25`; `docs/API_REFERENCE.md:1387-1416`; `docs/ADMIN_GUIDE.md:737-740`)

## As built

ClaimPendingBatch is a read-only scan; two IRIS processes calling it were handed the same 3 entries, which stayed PENDING. Nothing prevents the IRIS task and a Python worker (or two Python workers) from working the same entries: double model calls, last-writer-wins vectors, DONE/ERROR status races.

Evidence: live `intent-a-hd0604-queue-claim`; inspected `iris_src/src/Graph/KG/EmbedQueue.cls:112-134`

## Intended contract

The queue is single-consumer by design (maintainer commit 5bb149ed, code comment); concurrent workers are not supported. Not settled: whether the product must enforce or merely document that. Status: supported.

## Working assumption

A single active consumer per namespace is the contract (supported by 5bb149ed); model both workers as independently schedulable, treat single-worker as an unenforced premise, and prefer enforcement (refuse a second worker) or documentation; atomic claims with recovery remain the multi-worker alternative.

## Alternatives

- (a) atomic claim (CLAIMED with owner and time, under a lock) used by both workers
- (b) refuse a second worker (namespace lock held while a worker runs)
- (c) document single-worker as an operator rule (premise P-0606)

## Discriminating check

probe (run): `intent-a-hd0604-queue-claim`. pass for the stated single-processor design: identical batches to both claimants; nothing enforces one worker.

## What would change this

A maintainer request for multi-worker throughput (then (a)), or a decision that documentation suffices ((c)).

## Residual question for maintainer

The queue is single-processor by design (5bb149ed). Should the product enforce one worker per namespace (refuse a second worker or task), or only document the rule for users?

## Consequence rank hint

medium: duplicate embedding calls and racing vector/status writes; no structural data loss, but wrong-model or stale vectors are possible.

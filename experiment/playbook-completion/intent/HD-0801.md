## Contradictions

- The contract says guarded calls raise and change nothing under strict mode; the guard caches strict for 5 s per engine and fails open on any probe error, and the maintainer's unit tests pin both. (specs/213-graph-revision-ledger/contracts/ledger-api.md:82-92; iris_vector_graph/ledger/guard.py:20,38-59; tests/unit/test_ledger_guard.py:93-124)
- The guard's docstring presents fail-open as deliberate (mocks, pre-deployment); the R206 commit fixes one fail-open path as a defect. The project has not said which fail-open cases are acceptable. (iris_vector_graph/ledger/guard.py:3-6; 3984854a)
- decisions.md speaks of the guard's 'documented failure modes'; the window and fail-open are documented only in guard.py's docstring and unit tests, not in ledger-api.md or the USER_GUIDE. (experiment/playbook-completion/decisions.md:117; docs/USER_GUIDE.md:1107-1121)

## As built

Strict mode is a client-side Python check (LedgerGuard) per engine, consulted on the Cypher SQL write route; it caches Meta() for 5 s and treats a failed probe as 'never-enabled'. Live: after another engine turned strict on (Meta strict=true), an engine whose cache was 0.13 s old accepted a Cypher CREATE and a create_node; a fresh engine and the same engine after 5.6 s were refused; verify() reported the bypassing rows as divergence.

Evidence: live: intent-a-hd0801-strict-cypher-window; run: intent-a-hd0801-unit-ledger-guard; inspected: iris_vector_graph/ledger/guard.py:20,38-80; inspected: iris_vector_graph/_engine/query.py:2299-2300

## Intended contract

Under strict mode a guarded Cypher write is refused and changes nothing (ledger-api.md:82-92). The window and the fail-open case are departures from that text. No source decides between documenting them and closing them. Status: **assumption**.

## Working assumption

Take the contract text as intended: strict refuses with no window. Record the 5 s cache window (reproduced live) and fail-open (tested) as product defects against ledger-api.md (F-0801), and keep their obligations open. Downstream modules (erasure, redaction, verify) may not assume that every graph-table change under strict mode has a ledger record. verify() detects bypass rows after the fact. Raw SQL and BulkLoader remain outside by the contract's own text (HD-0301/1103).

## Alternatives

- (a) keep the client check; document the 5 s window and fail-open in ledger-api.md and USER_GUIDE
- (b) fail closed and re-read strict on every guarded write (one class call per write)
- (c) server-side enforcement (Txn_Begin check or table triggers), which also covers raw SQL/BulkLoader (new contract; see HD-1103)

## Discriminating check

probe, run: intent-a-hd0801-strict-cypher-window; intent-a-hd0801-unit-ledger-guard

Result: fail: a Cypher CREATE was accepted 0.13 s after strict was set (same engine); refused by a fresh engine and after the TTL. The unit tests pin TTL and fail-open.

## What would change this

A maintainer statement accepting the TTL as the contract (amending ledger-api.md) would turn the live result into documented behaviour. A server-side check would move this to HD-1103's assurance target.

## Residual question for maintainer

Is the 5 s strict-mode cache window, and fail-open when the probe fails, acceptable (then document it in ledger-api.md/USER_GUIDE), or must strict refuse immediately and fail closed? Working answer: refuse with no window (contract text). Best alternative: document the window and fail-open.

## Consequence rank hint

high: erasure/redaction/verify rely on knowing which writes the ledger saw; a silent unrecorded write under strict is an integrity gap (S2)

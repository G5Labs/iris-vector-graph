# HD-0703 Is spec 044's kg_TXT-to-BM25 fallback still wanted?

Status: **assumption** · Confidence: medium · Changed from decisions.md: **yes** (was "Supported. Honor the documented
BM25 fallback"; see below)

## Question

Spec 044 FR-012 / US5 / SC-004 say that when iFind is unavailable `kg_TXT` uses a BM25 index named `default` before the
LIKE fallback. The pin has no such code. Is the requirement still wanted, and over which graph?

## Contradictions

- FR-012/US5/SC-004 and tasks T034/T035 `[X]` (re-committed 2026-10-08) vs the code (fallback removed 2026-05-09) and
  the generated API reference / kg_TXT docstring, which describe iFind-then-LIKE only.
- spec.md:13 "iFind is Enterprise-only" vs live: `idx_docs_text_ifind` exists and answers on Community 2026.1 (and
  v2.18.2 put it in the base DDL).
- spec.md:235 US7 AC5 "scores are BM25-ranked floats between 0 and 1000" vs the docstring (occurrence count; live 2.0, 1.0).
- tasks.md T035 `[X]` vs a test that never calls kg_TXT (F-0708).

## As built

`kg_TXT` tries the iFind index (scores = occurrence counts, graph-scoped) and on an iFind error falls back to LIKE
(score 1.0, WARNING). It never reads `^BM25Idx`. Live: with docs rows in `ia-0703` and a BM25 index named `default`
built for `ia-0703`, kg_TXT answered `[(d1, 2.0), (d2, 1.0)]` before and after the build (BM25 would give 0.69/0.38), no
fallback warning; the default-graph call answered `[]`.

## Intended contract

Not settled by a current authoritative source. FR-012 sits in a Draft spec and a merged PR from 2026-04; its
implementation was removed by the maintainer in 2026-05 with no statement, and every later maintainer description of
kg_TXT omits it. Best-supported reading: the current kg_TXT contract is iFind-then-LIKE; FR-012 is a stale requirement
pending a decision; if kept it must read only the index recorded for the requested graph.

## Working assumption

Model kg_TXT as iFind-then-LIKE (documented as-built). Record FR-012/US5/SC-004 and tasks T034/T035 as a spec/doc
conflict (S3, F-0708), not as a current obligation the pin fails. If the fallback returns, it applies only on the LIKE
path, only to an index whose recorded graph equals the requested graph, never across graphs.

Why changed: decisions.md called this Supported on spec 044 FR-012, SC-004 and PR #8. Those establish the 2026-04
feature, not that it is still wanted: the Draft spec is the only post-removal carrier, it was copied wholesale with the
schema-2 amendment, and the maintainer's later kg_TXT redesign (v2.18.2, US7, docstring, generated API reference)
excludes it. No source "supersedes" FR-012 explicitly either, so neither reading is supported; the assumption follows
the newer, user-facing contract.

## Alternatives

1. Implement FR-012 with the BM25 index recorded for the requested graph (decisions.md's former answer).
2. Strike FR-012/US5/SC-004 from spec 044 and fix tasks T034/T035 and the T035 test name.
3. Leave the spec as Draft (status quo; the conflict stays).

## Discriminating check

Run: probe `intent-a-hd0703-kgtxt-bm25-default` (incomplete: on the pinned Community deployment the iFind path answers,
so FR-012's precondition never occurs; a BM25 `default` index changes nothing; no cross-graph use). FR-012 can matter
only on namespaces whose iFind index is missing or broken; the probe cannot create that state without changing the
schema, which the audit forbids. Source inspection is decisive for "no BM25 branch exists".

## What would change this

A maintainer statement striking or reaffirming FR-012, or a spec amendment.

## Residual question for maintainer

Is spec 044 FR-012 (kg_TXT uses the BM25 index `default` before LIKE) still wanted after its implementation was removed
in v1.91.0, and if so must it use only an index built for the requested graph? Working answer: no current obligation;
record the conflict. Best alternative: restore it, graph-matched.

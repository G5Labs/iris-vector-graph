# Findings: 18 Snapshots

Every finding here comes from reading code and tests at pin `3eaa79cf`. None was run in this uplift; each says what
would close it.

### F-1801 A replacing restore lays the archive's ledger over the live one
- Evidence: `restore_snapshot` without merge calls `erase_all()` (`iris_vector_graph/_engine/snapshot.py:1139-1152`),
  whose `Eraser.EraseAll` kills only `^IVG.Ledger("stmt")` and `("tuple")`; `("rec")`, `("head")`, `("idem")`,
  `("revById")`, `("idBySeq")`, the redaction marks and the `LedgerRevision` storage survive
  (`iris_src/src/Graph/KG/Eraser.cls:806-812`). The restore then sets each archived global node one by one
  (`snapshot.py:1554-1588`, `:1679`) over whatever is there. A commit writes `^IVG.Ledger("rec", head+1, ordinal)` and
  moves `head` (`iris_src/src/Graph/KG/Ledger.cls:530-556`). The only ledger round-trip test wipes the ledger with
  `PurgeAll` before the restore (`tests/integration/test_ledger_snapshot.py::test_save_wipe_restore_preserves_head_history_and_statements`).
- Impact: restoring an older archive into a namespace whose ledger moved on leaves revisions past the archive's head in
  place while `head` goes back; the next commit reuses their sequence numbers and can mix its records with leftover
  ordinals. Restoring an archive made before a redaction overwrites each tombstone with the original record, so erased
  tenant content returns to history while `redactedRev` marks still claim it was redacted. Restoring an archive with
  no ledger keeps the live records but not their statement index.
- What would close it: decision HD-1801, then a live test that commits after the save, restores, commits again and
  runs `verify()`, plus a redact-then-restore case.

### F-1802 A merge restore guards plain tables on their first column only, and counts skipped rows as restored
- Evidence: for tables that are neither configuration nor FHIR bookkeeping, the merge insert is
  `INSERT ... WHERE NOT EXISTS (SELECT 1 FROM t WHERE <first column> = ?)` (`snapshot.py:1287-1292`), and
  `count += 1` follows whatever the insert did (`:1298`). The first column of `SELECT *` (minus row ids) is `graph_id`
  for `rdf_edges`, `rdf_labels`, `rdf_props` and `docs` (`iris_vector_graph/schema.py:34-45`, `:403-418`, `:474-479`)
  and `node_id` for `nodes` (`:395-401`). The same defect was found and fixed for the FHIR tables only
  (`tests/unit/test_snapshot_inventory.py::test_a_merge_restore_keeps_every_fhir_row_of_a_graph`, whose docstring
  says "a graph's second row matched its first").
- Impact: a merge into a graph that already holds one edge, label, property or document adds none of the archive's
  rows of that table for that graph; a node id present in any graph blocks the archive's node of the same id in
  another graph (the edge's endpoint registration partly hides this for nodes). `restored_tables` reports every line
  and `failed_rows` is empty, so the loss is silent. `tests/unit/test_snapshot.py::test_restore_merge_preserves_local`
  only checks that local rows survive.
- What would close it: guard each table on its primary or unique key (as `CONFIGURATION_TABLES` does), count only
  inserted rows, and add a live merge test into a graph that already has rows.

### F-1803 Edge vectors lose their graph and metadata in a snapshot
- Evidence: `save_snapshot` reads `SELECT s, p, o_id, emb FROM Graph_KG.kg_EdgeEmbeddings`
  (`snapshot.py:942-956`); the table has `graph_id` and `metadata` and is unique on `(graph_id, s, p, o_id)`
  (`iris_vector_graph/schema.py:455-464`). The restore inserts `(s, p, o_id, emb)` only, and its merge guard matches
  `s, p, o_id` with no graph (`snapshot.py:1510-1552`).
- Impact: a named graph's edge vectors come back in the default graph without metadata; two graphs' vectors for the
  same triple collide on restore (one fails, counted) and a merge skips a named graph's vector when any graph has one.
- What would close it: export and restore `graph_id` and `metadata`, match on the full key, and test with two graphs.

### F-1804 Native index values come back as text
- Evidence: each value is archived as `str(val)` (`snapshot.py:1644-1646`) and restored with
  `iris_obj.set(entry["v"], ...)`, a Python `str` (`:1679`). The window reader returns an attribute as a JSON number
  only when the stored value encodes as a number (`iris_src/src/Graph/KG/TemporalWindow.cls:268-283`), and
  `GetEdgeAttrs` builds a `%DynamicObject` from the stored value (`TemporalIndex.cls:1641-1648`).
- Impact: after a snapshot round trip a numeric temporal attribute (`{"amount": 20}`) reads back as `"20"`, breaking
  spec 255's "a value comes back with the type it was written with"; any other global value whose type matters is
  changed the same way. Weights print the same in JSON, so they look unaffected.
- What would close it: archive the type with the value (as the vector form already does) or read and write values on
  the server, and add an attribute-type assertion to the round-trip test.

### F-1805 A merge restore overwrites temporal aggregates instead of combining them
- Evidence: in a merge the archived `^KG` lines are set over the live nodes (`snapshot.py:1679`), including
  `^KG("bucket")`, `^KG("tagg")` count, sum, min, max and HLL, and `^KG("tlast")`. These are derived per bucket from
  the raw edges (`TemporalIndex.cls:96-125`), and the raw edges of both sides survive the merge.
- Impact: after a merge that overlaps a live time bucket the aggregates describe the archive's edges only while
  `^KG("tout")` holds both sets; `tlast` can move back to an older time than the live newest event. Whole-bucket
  aggregate reads and latest reads then disagree with the window.
- What would close it: rebuild the touched buckets and `tlast` after a merge (`RebuildBucketAggregate`,
  `RebuildLatest`), or refuse a merge that overlaps live temporal data, and test it.

### F-1806 Graph.KG.Snapshot.ImportGlobals loads any global file without the allow-list
- Evidence: `ImportGlobals(inputDir)` runs `$System.OBJ.Load` on every `*.gof` file in the folder
  (`iris_src/src/Graph/KG/Snapshot.cls:24-35`); `restore_snapshot` writes only the globals `restorable_globals`
  names (`snapshot.py:412-422`, `:1569-1572`), a guard added in 4.6.0 because "an archive is a file anyone can write".
  No product code calls `ImportGlobals` or `ExportGlobals`.
- Impact: a deployed, callable server method that loads arbitrary globals (and `.gof` items can carry more than
  globals' data) from a server folder, outside the restore's guard.
- What would close it: delete the unused methods, or apply the same allow-list.

### F-1807 The HTTP snapshot endpoint can write two snapshots to one path
- Evidence: `POST /admin/snapshot` names the file `ivg_snapshot_{int(time.time())}.snapshot`
  (`iris_vector_graph/cypher_api.py:672-673`) and `save_snapshot` opens it with `ZipFile(path, "w")`
  (`snapshot.py:1035`).
- Impact: two saves within one second overwrite each other; both responses report the same path.
- What would close it: add a finer or unique suffix and refuse to overwrite.

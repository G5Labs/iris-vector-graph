# Findings of module 02 (graph identity)

Cited from `ontology/02-graph-identity.md` as `finding:F-02kk`. Every finding here comes from reading the code at pin
`3eaa79cf`; none was reproduced on IRIS in this uplift. "What would close it" names the check or change that would.

### F-0201 A graph whose mode is off can hold two edges of one triple
- Evidence: spec 234 never renumbers an edge key, so after `CREATE` twice in a multigraph (edge keys 0 and 1) and a
  Cypher `DELETE` of the key-0 edge, the triple's one remaining edge sits at edge key 1
  (tests/e2e/test_234_multigraph_storage_e2e.py `test_one_to_two_when_the_first_edge_is_not_ekey_zero` builds this
  state on purpose). `GraphMode.Set(g, 0)` then succeeds, because `ParallelCount` counts only triples with two or more
  rows (iris_src/src/Graph/KG/GraphMode.cls:35-40, 48-61). In the now single-edge graph, `create_edge` guards its
  insert with `... AND ekey = 0` (iris_vector_graph/_engine/nodes_edges.py:1213-1219, 1257-1273) and `store_edge`
  inserts with the column default 0 (nodes_edges.py:2567-2572); the unique key is `(s, p, o_id, graph_id, ekey)`
  (iris_vector_graph/schema.py:44). Both add a second row for the triple and report a new edge. With the mode off the
  adjacency index keeps one unkeyed leaf per triple (`Adjacency.RowPut` -> `Put`, iris_src/src/Graph/KG/Adjacency.cls:
  477-489), and `Remove` kills that leaf whichever row is deleted (Adjacency.cls:147-153).
- Impact: the single-edge rule that FHIR sync, RDF import and the ledger's tuple refs rely on (spec 234 Context) is
  broken in a graph that says it is single-edge; deleting either row then leaves a live row with no adjacency entry
  (drift that `verify_graph` reports, and traversals miss the edge).
- What would close it: guard the single-edge writers on the triple whatever its edge key, or refuse to turn the mode
  off while any edge of the graph has a non-zero edge key (or renumber a lone edge to 0 as the mode goes off); plus an
  e2e test of create, delete key 0, mode off, `create_edge`.

### F-0202 The name check is not run at every entry that takes a graph name
- Evidence: ADR-0003 says the validator rejects new graphs named "0" (docs/adr/0003-two-graph-key-derivations.md:
  119-121). The check runs in `create_edge`, `delete_edge`, `delete_node`, the counts, `verify_graph` and the mode
  commands (nodes_edges.py:1197, 1411, 2206, 747, 2384; iris_vector_graph/_engine/admin.py:887, 904, 921), but not in
  `create_node` (nodes_edges.py:1019), `store_node` (2421), `store_edge` (2560), `bulk_create_nodes` for a node's own
  `graph` key (1806; the call's `graph=` is checked at 1697-1699 only when truthy), `bulk_create_edges` for either
  `graph=` or an edge's own key (1941-1967), `BulkLoader(graph=...)` (iris_vector_graph/bulk_loader.py:76), or a
  Cypher `USE GRAPH` name (iris_vector_graph/cypher/parser.py:186-192 takes the text; translator.py:429-438 binds it).
  `create_edge` also writes the raw name to `graph_id` (`gid = graph or ""`, nodes_edges.py:1213) while it keys
  `^KG` by the NUL-stripped name (1197), so a name with a NUL pad lands under two spellings.
- Impact: a graph named "0", or one holding a control character, gets SQL rows. Where the adjacency index is declared,
  its edge rows then fail late inside `GraphKey.ForIndex` with an IRIS `<THROW>`; where it is not, the rows sit with no
  adjacency, and a later rebuild throws on them. The Python counts and `delete_node(graph="0")` refuse the name, so the
  rows cannot be read or removed through the API that wrote them.
- What would close it: call `validate_graph_name` at each of these entries (and for `USE GRAPH` in `execute_cypher`),
  write the canonical name to SQL, and add a unit test per entry.

### F-0203 The Python name check refuses fewer control characters than the server check
- Evidence: Python refuses `ord(c) < 32 or ord(c) == 127` (iris_vector_graph/_validate.py:43); the server compares
  the name with `$ZStrip(name, "*C")` (iris_src/src/Graph/KG/GraphKey.cls:44), whose `C` mask also covers 128-159
  (premise P-0202).
- Impact: a name such as `"a\x85"` passes the Python check and then fails on the server as a `RuntimeError` carrying
  an IRIS `<THROW>`, the error shape the Python mirror exists to avoid (CHANGELOG.md:4618-4620). Low severity.
- What would close it: a live probe of P-0202; if it holds, widen the Python rule to `unicodedata.category(c) == "Cc"`
  or the explicit 0-31, 127-159 range, with a unit test.

### F-0204 The graph check reports a multigraph's parallel edges as missing adjacency
- Evidence: `GraphVerify.VerifyGraph` counts every `rdf_edges` row of the graph (`tSqlEdges`) but matches `^KG("out")`
  per triple (`tOutMatched`), then reports `tSqlEdges - tOutMatched` as missing (iris_src/src/Graph/KG/GraphVerify.cls:
  64-103). A triple with two rows and one correct keyed leaf reports one missing out-entry and one missing in-entry.
  Spec 234 SC-005 requires zero drift on a multigraph after random creates and deletes; task T036 (make GraphVerify
  descend into the keyed children) is unchecked (specs/234-multigraph-parallel-edges/tasks.md).
- Impact: `verify_graph(g)["ok"]` is false for every healthy multigraph with a parallel edge, so an operator cannot
  tell real drift from parallel edges.
- What would close it: count `^KG("out", g, s, p, o, "#")` (or the keyed children) as the triple's edge count, and an
  e2e test that a multigraph with parallel edges verifies clean.

### F-0205 Direct edge writes, the ledger and Bolt do not track parallel edges, and the user docs do not say so
- Evidence: `create_edge` never creates a parallel edge in a multigraph unless edge key 0 is free (nodes_edges.py:
  1213-1219, 1257-1273) and `create_edge_returning_id` does not exist (FR-007; tasks T030/T033 unchecked). The ledger
  finds an edge by triple and takes the first row (iris_src/src/Graph/KG/LedgerApply.cls:144-157), and its tuple index
  has no edge key (LedgerApply.cls:159-168), where FR-013 asks for an `ambiguous_tuple` refusal. Bolt gives a
  relationship the id `hash(f"{s}-{type}-{o}")` (iris_vector_graph/bolt_server.py:770), the same for parallel edges
  and salted per Python process, where FR-012 asks for the `edge_id`. The spec status line says ledger/restore (US4) is
  not done (specs/234-multigraph-parallel-edges/spec.md:5-6); the USER_GUIDE and API_REFERENCE describe the mode
  without these limits (docs/USER_GUIDE.md:470-473; docs/API_REFERENCE.md:2710-2716).
- Impact: in a multigraph, a ledger changeset that names a relationship by triple silently acts on one of several
  edges, so replay and redaction work on an arbitrary row; a Bolt client sees parallel relationships as one.
- What would close it: implement FR-007, FR-012 and FR-013, or document each limit in the USER_GUIDE multigraph
  paragraph and KNOWN_ISSUES.

### F-0206 Some Python readers join one graph's ids with another graph's data
- Evidence: `get_nodes_by_label(label)` takes the ids of every graph that has the label and hydrates them from the
  default graph (iris_vector_graph/_engine/nodes_edges.py:779-794, docstring says so); a node of another graph whose id
  also exists in the default graph comes back with the default graph's labels and properties, which may not carry the
  label. `get_nodes_by_property` does the same (833-844). `_filter_edges_by_properties` reads the qualifiers of
  `(s, p, o)` with no graph and takes the first row (584-619). `set_edge_weight` can only reach the default graph
  (1338-1342). The USER_GUIDE says Python methods that read or write take `graph=` and, omitted, mean the default
  graph, never every graph (docs/USER_GUIDE.md:466-467); SYS-I2 says content of one graph never shows up in an answer
  about another.
- Impact: a label query can answer a node that does not hold the label in its own graph; a BFS property filter can
  keep or drop an edge by another graph's qualifiers.
- What would close it: decision HD-0201, then scope the hydration to each id's own graph and give
  `_filter_edges_by_properties` and `set_edge_weight` a graph.

### F-0207 Turning the mode off races a write that adds a parallel edge
- Evidence: `GraphMode.Set(g, 0)` counts parallel triples with one SQL query and then kills the setting, with no lock
  and no transaction around the two (iris_src/src/Graph/KG/GraphMode.cls:26-45). A Cypher `CREATE` in another process
  can insert a second edge of a triple between the count and the kill.
- Impact: the graph ends with mode off and a parallel edge, the state the refusal exists to prevent (spec 234 FR-002);
  later unkeyed adjacency writes on that triple then disagree with its keyed children (see F-0201).
- What would close it: take the adjacency writer lock for the graph (or a lock the multigraph writers also take) around
  the count and the kill, and a concurrency test.

### F-0208 An engine keeps a graph's mode forever, so another engine's change is not seen
- Evidence: `is_multigraph` caches each graph's mode per engine with no expiry; only this engine's `set_multigraph`,
  `erase_graph` and `erase_all` clear it (iris_vector_graph/_engine/admin.py:917-936; nodes_edges.py:1525-1526,
  1585). The Cypher translator asks it once per statement and, when it answers on, drops the triple guard and writes
  `MAX(ekey) + 1` (iris_vector_graph/cypher/translator.py:441-457, 10368-10388). The adjacency index reads the live
  setting for each row (iris_src/src/Graph/KG/Adjacency.cls:477-503). The API reference documents the cache
  (docs/API_REFERENCE.md:2684) but not its effect.
- Impact: after an operator turns a graph's mode off from one engine (or process), a long-lived second engine keeps
  writing parallel edges into it through Cypher, and the index files them unkeyed: the single-edge graph holds parallel
  rows, as in F-0201.
- What would close it: read the mode per statement (one `$Get`), or expire the cache with the ledger guard's TTL, or
  have the server refuse a keyed insert into a mode-off graph.

### F-0209 An all-graphs walk can miss graphs
- Evidence: `_edge_graphs` stops listing `^KG("out")` after 10,000 graphs and answers `[]` on any error
  (iris_vector_graph/_engine/query.py:2408-2420). The variable-length route treats `[]` as "walk the default graph"
  (query.py:2474-2479) and the one-hop shortcut treats it as "only the default graph has edges" (query.py:4319-4321).
- Impact: an all-graphs read in a namespace with more than 10,000 graphs holding edges silently leaves the rest out, and
  a failed listing answers the default graph's rows as the union. Low severity at expected graph counts.
- What would close it: list without a cap (the other listing, iris_vector_graph/stores/lazy_kg.py:66-80, has none) and
  raise when the listing fails.

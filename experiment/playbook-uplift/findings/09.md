# Findings: module 09 (native Cypher executor)

All evidence is from reading code, tests and docs at pin `3eaa79cf`; nothing here was run. Probabilities are
arithmetic on the premise P-0901, not measurements.

### F-0901 Two plan shapes with one 32-bit checksum share one compiled class
- Evidence: `iris_src/src/Graph/KG/Cypher/Gen.cls:69` computes `tH = $ZCRC(tShape, 7)` (CRC-32, P-0901) and every
  compiled plan is the class `IVGC.P<tH>` (`:186`). `:71` uses an entry only if its stored shape equals the read's;
  otherwise `:80` overwrites the entry for the new shape and the build (`:96` or `:101`) recompiles the same class
  name with the new shape's walk. `RunA` asks `Gen.For` once per run (`Exec.cls:158`) and then calls
  `$ClassMethod(tGen, "Walk1", ...)` once per anchor (`Exec.cls:199`, `:258`). Nothing locks the class between For's
  check and the last Walk1 call.
- Impact: ADR-0014 and the seed promise that a compiled plan answers exactly as the interpreter and that no wrong
  plan runs. With two colliding shapes S1 and S2 in use, each read of one overwrites the other's entry and rebuilds
  the shared class; a read of S1 that is mid-walk when the class is rebuilt for S2 runs S2's code with S1's plan for
  its remaining anchors. S2's walk has other labels, types and checks written in, so the read can answer wrong rows
  silently, or raise and fall back to SQL. The overwrites also make `Build` refuse lines that are not its own
  (`:177-182`), writing a misleading security line to messages.log. Odds are low but grow with the number of shapes,
  which nothing prunes (ADR-0014): about 1 in 8,600 namespaces at 1,000 shapes, about 1 in 86 at 10,000.
- What would close it: name the class by a wider digest of the shape (the SHA-256 that `Digest` already computes, or
  a counter) and keep the shape check; a unit test that forces two shapes onto one hash and asserts each runs its own
  walk.

### F-0902 The interpreter tells relationships apart by a 32-bit checksum
- Evidence: `iris_src/src/Graph/KG/Cypher/Exec.cls:1243-1244`: a hop that must not reuse a relationship computes
  `tEdge = $ZCRC($ListBuild(tSrc, pP, tDst, ekey), 7)` and skips the neighbour when `pUsed` already holds that
  number. The compiled walk compares endpoints, type and key exactly (`Gen.cls:410-433`). Spec 257's plan
  (`plan.md:110-112`) states the difference ("The interpreter hashes each relationship into a string of used ones").
- Impact: two different relationships in one match whose CRC-32 values are equal make the interpreter drop a valid
  match that the SQL path and the compiled walk keep. Per pair the chance is about 2^-32; a read that compares 10^8
  pairs (large multi-hop counts on SF10-sized graphs) has about a 2% chance of one silent miscount. Compiled and
  interpreted answers then differ, breaking ADR-0014's "answers exactly as the interpreter does" in the other
  direction, and `off` mode (the shadow reference) is the wrong one.
- What would close it: keep used relationships as exact subscripts (a local array keyed by `$LB(src, p, dst, ekey)`)
  instead of a checksum in a string.

### F-0903 The namespace compile mode is not checked: any value but "job" or "off" acts as "sync"
- Evidence: `Gen.cls:41-44` `Effective()` returns `$Get(^||IVG.CypherGenMode, $Get(^IVG.CypherGen("mode"), "job"))`
  unchecked. `For` quits for `"off"` (`:64`), starts a job for `"job"` (`:92-99`) and builds in the caller for every
  other value (`:101`). `Mode()` validates a per-process value (`:28-39`); the namespace value is set by a plain
  `Set`, as docs/ADMIN_GUIDE.md:774-779 tells operators to do.
- Impact: a site under change control that types `Set ^IVG.CypherGen("mode") = "OFF"` (or `"none"`, `"disabled"`,
  or `""`) to stop run-time code gets the opposite: classes are written and compiled, synchronously, in every
  reader's process, with F-0904's risk on top. Nothing reports the bad value.
- What would close it: `Effective()` (or `For`) treats an unknown namespace value as `"off"` and logs it once; a test
  that sets `"OFF"` and asserts no entry is written.

### F-0904 In sync mode a failed build runs in the reader's own process
- Evidence: `Gen.cls:101` calls `Build` in the current process for `sync`; `Build` runs `$System.OBJ.Compile`
  (`:205`). The product's own test docstring
  (`tests/e2e/test_257_compiled_plans_e2e.py::test_the_broken_builds_leave_the_session_process_able_to_compile_sql`)
  records that on IRIS 2026.3 a failed class compile leaves its process unable to prepare any new SQL (P-0903), and
  the tests therefore fail builds on a separate connection. docs/ADMIN_GUIDE.md:746-752 offers `sync` with no warning;
  spec 257 promises "Compilation never costs a caller" (`spec.md:60-63`).
- Impact: with `sync` set for a namespace (as the TCK runs and benchmarks do, and as F-0903 can cause by accident), a
  shape the generator writes badly makes the reader's IRIS process unable to prepare new SQL. Where the engine's
  native calls share the caller's connection (no stored login, or EmbeddedConnection), the SQL path of that
  connection then fails for every new statement text; with a dedicated native connection, the native path's own SQL
  (anchors, the property reader's fallback) fails and every read falls back. Answers are refused, not wrong.
- What would close it: build in a job in every mode and have `sync` wait for the job; or document `sync` as test-only
  with this hazard.

### F-0905 A deploy's drop does not wait for builds already running
- Evidence: `Gen.cls:225-230` `DropAll` deletes the package and kills `^IVG.CypherCompiled` without the per-entry lock
  `Build` holds (`:166`). A build that is compiling when `DropAll` runs then compiles its class after the delete and
  sets `$List(^IVG.CypherCompiled(h), 1)` and `(h, 4)` on a killed node (`:207`, or `:210` on failure), which
  re-creates the entry as `$LB(class, , , "ok")` (P-0907). The next `For` for that hash evaluates `$List(tE, 2)`
  (`:71`) on an empty element, which raises; `RunA` catches it and interprets (`Exec.cls:157-166`).
- Impact: ADR-0014 says a deploy deletes every compiled class. Here a class compiled against the old code survives
  the deploy (it is never run: its entry has no shape), and the broken entry makes that hash's shape run interpreted,
  with one console line per process, until the next deploy or `DropAll`. Answers stay right; speed is lost on that
  shape. The same holds for any operator `DropAll` during job-mode traffic.
- What would close it: `DropAll` takes each entry's lock (or a namespace lock `Build` also takes), and `Build` uses
  `$ListGet` / re-checks that its entry still exists before writing to it; `For` reads entries with `$ListGet`.

### F-0906 The native gate checks the edge index but not the label index
- Evidence: `iris_vector_graph/cypher/native_plan.py:528-529` opens the gate on `engine._adjacency_indexed`, which
  asks only for `idx_edges_adj` on `rdf_edges` (`engine.py:703-723`, `Adjacency.cls:540-557`). The native path also
  reads `^KG("label")` for every label check and label scan (`Exec.cls:206-266`, `:908-918`), which only
  `idx_labels_adj` on `rdf_labels` keeps current (`schema.py:769-782`). `ensure_adjacency_index` declares the edge
  index first and the label index second (`schema.py:863-899`), so a failure between them leaves the edge index
  alone. CONTEXT.md:88-96 defines the index as declared "on the edge and label tables"; spec 253 FR-003 names
  `Graph.KG.Adjacency.Indexed()`, which is the edge check only.
- Impact: on a namespace with the edge index but not the label index, the engine's label writers write rows only, so
  `^KG("label")` drifts from `rdf_labels` until a rebuild (`Graph.KG.TraversalBuild`, `sync()`), and native reads answer from the stale labels (missing or extra nodes)
  while the SQL path answers from the rows. Shadow mode would catch it; default mode would not.
- What would close it: the gate (or `Indexed()`) also requires `idx_labels_adj` as a functional index; a unit test
  with the label index absent.

### F-0907 Shadow mode holds any ordered projection to a fixed row order, ties included
- Evidence: for a projection, `native_plan.py:194` sets `ordered = bool(order)`, whatever the ORDER BY leaves tied;
  for a grouped read it is true only when every grouping key is ordered (`:179-181`). `_shadow_compare` relaxes the
  check only when `limited and not ordered` (`query.py:2232-2238`), and `compare` checks rows one by one when
  `ordered` (`native_shadow.py:55-63`). Spec 253 FR-013 and docs/dev/TCK.md ("rows in the same order where the query
  orders them completely ... Where a LIMIT or SKIP keeps rows the query does not order completely, the row counts must
  match") ask for the relaxed check whenever the order is not complete.
- Impact: a projection like `RETURN m.sid, m.title ORDER BY m.title LIMIT 3` with ties at the cut, or the same with no
  LIMIT, can raise `NativeMismatch` in shadow mode when both paths are right but break ties differently. It costs false
  alarms in shadow runs, not wrong answers; the trim tests avoid it by ordering on a unique key
  (`tests/e2e/test_253_ordered_trim_e2e.py`).
- What would close it: compute `ordered` for projections from whether the ORDER BY keys determine the returned row
  (or compare tied runs as bags); a unit test with a tied ORDER BY.

### F-0908 The privilege check spec 253 puts in the executor is in the engine only
- Evidence: spec 253 FR-011 (`spec.md:124-127`): "Before reading natively, the executor MUST check that the caller holds
  SELECT on ... (`$SYSTEM.SQL.Security.CheckPrivilege`, cached per process and user)". The check is in Python
  (`engine.py:559-586`, gate `native_plan.py:532-533`); `Graph.KG.Cypher.Exec.Run` (`Exec.cls:32-72`) checks nothing.
  docs/ADMIN_GUIDE.md:565-575 states the database resource, not SQL rights, is the boundary for the native executor.
- Impact: a user with `%Native_ClassExecution` can call `Exec.Run` with a plan and read every graph's labels, edges and
  properties whatever their table grants. The ADMIN_GUIDE documents the boundary, so the risk is known; the spec's
  requirement is not what shipped, and engines cache the check for their life (HD-0901).
- What would close it: amend FR-011 to the shipped design (engine-side check, database resource as the boundary), or
  add the check to `Run`.

### F-0909 Spec 253's "same process" reason for seeing one's own writes is not what the code does
- Evidence: spec 253 edge case (`spec.md:91-92`): "A query planned natively inside an open transaction sees that
  transaction's own writes (it runs in the same process)". `engine._iris_obj` (`engine.py:1894-1942`) opens a dedicated
  Native API connection, a separate IRIS process, whenever the engine knows its login (`from_connect`), and
  `_run_native_plan` runs every native read on it (`query.py:2204-2209`). Workers are other processes too
  (`Exec.cls:465-475`).
- Impact: the read still sees the caller's uncommitted writes, but only because IRIS globals and SQL at default
  isolation read uncommitted data (P-0002), the same way it sees other writers' uncommitted data (HD-0903). If the
  native connection's isolation ever changed, or a write path deferred its globals to commit, native and SQL answers
  inside a transaction would differ with no test to catch it: no upstream test runs a native read inside an open
  caller transaction.
- What would close it: correct the spec's reason, and add an e2e test that writes in an open transaction and reads it
  back natively on an engine built with `from_connect`.

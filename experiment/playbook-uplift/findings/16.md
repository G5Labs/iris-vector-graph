# Findings: module 16 (interfaces)

All found by reading the code at the pin; none was run here.

### F-1601 Bolt BEGIN, COMMIT and ROLLBACK do nothing; every RUN commits at once
- Evidence: `iris_vector_graph/bolt_server.py:500-510` answers BEGIN and COMMIT with SUCCESS and only clears pending rows
  on ROLLBACK; `bolt_server.py:579-581` runs each RUN through `engine.execute_cypher`, which commits its own write
  transaction (`iris_vector_graph/_engine/query.py:1946-1967`). No test sends BEGIN or ROLLBACK
  (`grep TAG_BEGIN tests` finds none).
- Impact: a Neo4j driver's explicit or managed transaction (`session.execute_write`, a retried unit of work) is not
  atomic: a ROLLBACK, or a driver retry after a failure, leaves the earlier statements' writes in place, and a retry
  repeats them. Statement API-B9.10.
- What would close it: run a Bolt transaction's RUNs inside one engine transaction (`write_txn`) and commit or roll it
  back on COMMIT/ROLLBACK; or refuse BEGIN with a FAILURE that says explicit transactions are not supported, and
  document it in docs/ADMIN_API.md. A live driver test (begin, write, rollback, read) closes it either way.

### F-1602 Bolt PULL {n} drops every row after the first n
- Evidence: `iris_vector_graph/bolt_server.py:630-660` sends `rows[:n]`, then SUCCESS without `has_more`, then sets
  `_pending_result = None`.
- Impact: a driver that pulls in batches (the Python driver's default fetch size is 1,000) receives a result silently cut
  at the batch size. Statement API-B9.11.
- What would close it: keep the remainder and answer `has_more: true` until it is drained; a unit test with
  `PULL {n: 2}` over three rows.

### F-1603 The generated GraphQL server mixes graphs in one answer
- Evidence: `iris_vector_graph/gql/resolvers.py:101` and `:124` read `rdf_edges` by `s` or `o_id` with no `graph_id`;
  `resolvers.py:38-43` takes ids from every graph's `rdf_labels`, then reads them with `get_nodes` in the default graph;
  `iris_vector_graph/gql/engine.py:41-50` joins `rdf_props` to `rdf_labels` on `s` alone to discover each type's fields.
- Impact: a default-graph node's `outgoing`/`incoming` lists edges of every graph whose node has the same id, against
  SYS-I2 and the all-graphs rules in CONTEXT.md:38-48; `nodes(label:)` pages over ids it then cannot find, so pages come
  back short or empty. Statements API-B10.3, API-B15.8.
- What would close it: filter every SQL statement by `graph_id` (default graph unless a `graph` argument names one), as
  `api/gql/core/resolvers.py` does since spec 230; an e2e test like
  `tests/e2e/test_230_graph_scoped_node_reads_e2e.py` against `iris_vector_graph.gql.create_app`.

### F-1604 The sample API's biomedical fields and its update mutation ignore graphs
- Evidence: `api/gql/loaders.py:29-40` (and the other loaders, `:84-95`, `:138-149`, `:192-195`, `:231-233`,
  `:261-263`) select from `Graph_KG.rdf_props`, `rdf_labels` and `rdf_edges` by `s` only;
  `examples/domains/biomedical/resolver.py:262-275` runs `UPDATE Graph_KG.rdf_props SET val = ? WHERE s = ? AND key = ?`
  with no graph, after `node_exists(id)` checked the default graph.
- Impact: `protein`, `gene`, `pathway` and `interactsWith` merge the properties, labels and edges of every graph that
  uses an id; `updateProtein` rewrites that property in every graph, bypassing the engine (no ledger, no write
  wrapper) and committing the shared connection. Statements API-B6.6, API-B6.7, API-B15.8.
- What would close it: add `graph_id = ?` (the default graph) to every loader statement and route the update through
  `engine` with `graph=`; an e2e test with the same id in two graphs.

### F-1605 The sample API's `nodes` field names `Graph_KG` instead of the engine's schema
- Evidence: `api/gql/core/resolvers.py:172-175` and `:206-274` hard-code `Graph_KG.nodes`, `rdf_labels`, `rdf_props`;
  `iris_vector_graph/gql/engine.py:14-15` and `iris_vector_graph/gql/resolvers.py:13` use `engine._ivg_schema` (spec 262,
  R079). The loaders (F-1604) hard-code it too.
- Impact: on a namespace installed under another IVG Schema, `nodes` and the biomedical fields read a schema that does
  not exist (an error) or a stale `Graph_KG` left by an older install (wrong answers). Statement API-B6.5.
- What would close it: build the SQL from `engine._ivg_schema`; run the GraphQL tests on a namespace with a custom
  schema (as `tests/e2e/test_262_fresh_namespace.py` does for other surfaces).

### F-1606 The sample API's Cypher route accepts a timeout and a cache flag and uses neither
- Evidence: `api/models/cypher.py:41-58` declares `timeout` (1-300 s, "Query execution timeout") and `enableCache`;
  `api/routers/cypher.py:94-209` never reads them. The contract the code cites (`contracts/cypher_api.yaml`) is not in
  the repository at the pin.
- Impact: a caller who sets `timeout` believes a runaway query is bounded; it runs until IRIS finishes it. No server
  bounds request time (API-T1.13). Statement API-B5.7.
- What would close it: enforce the timeout (statement timeout or a cancel after the limit), or remove the fields and
  say so; a unit test that a slow stub is cut at the timeout.

### F-1607 Two Cypher entries of the sample API bypass the engine and can answer differently
- Evidence: `api/routers/cypher.py:118-166` and `api/gql/schema.py:170-215` call `parse_query` and `translate_to_sql`
  and run the SQL themselves. The engine applies `rewrite_ambiguous_param_unwind` first
  (`iris_vector_graph/_engine/query.py:1900`), and the Cypher HTTP server's explain route copies that step "so the SQL
  shown is the SQL that runs" (`iris_vector_graph/cypher_api.py:728-729`). They also skip the native executor and the
  engine's write wrapper.
- Impact: `UNWIND $p AS e ...` over a list of mixed kinds answers on these two routes as before 4.7.0 row 22 (for
  `['[2]', [2], true, '1']`, `[2], [2], '1', '1'`), unlike `execute_cypher`, `/api/cypher` on the Cypher HTTP server,
  Bolt and MCP. Statement API-B5.8.
- What would close it: call `engine.execute_cypher` from both (keeping the hop cap), or apply the same rewrite; a
  parity unit test across the five Cypher entries.

### F-1608 The sample API lets two threads use its one IRIS connection at once
- Evidence: `api/main.py:100-113` (`health`, a plain `def`, which FastAPI runs on a worker thread) and the async Cypher
  route and GraphQL resolvers (`api/routers/cypher.py:94`, `api/gql/core/resolvers.py:69-355`) all use the engine's
  single connection (`api/main.py:140-142`, `api/dependencies.py:10-22`) with no lock. CHANGELOG.md:304-310 records the
  same pattern in the Cypher HTTP server causing SQLCODE -400 and empty answers, fixed there with `_engine_lock` in
  4.6.5 only.
- Impact: a health probe during a query can make the query answer empty or fail (premise P-1605). Statement API-B4.5.
- What would close it: a lock around every use of the connection in the sample API (as `cypher_api._engine`), or one
  connection per request; the live probe test of `tests/e2e/test_465_api_engine_lock_e2e.py` run against `api.main`.

### F-1609 The FHIR event route's writes are not all-or-nothing
- Evidence: `api/routers/fhir_event.py:318-346` calls `create_node` (pointer), `create_node` (patient) and
  `create_edge_temporal` one after another, each its own transaction; a failure of a later call answers 500 and leaves
  the earlier writes (`tests/unit/test_fhir_event_sidecar.py::TestHandlerBehavior::test_create_edge_exception_returns_500`
  asserts the 500, not the rollback).
- Impact: a caller that retries after a 500 may find a pointer node with no edge, against SYS-I4. The route is
  deprecated (removed in 5.0), which limits the exposure. Statement API-B7.4.
- What would close it: wrap the three writes in one engine transaction (`write_txn`); a unit test that a failed edge
  write leaves no node.

### F-1610 The Neo4j HTTP commit route runs its statements one by one
- Evidence: `iris_vector_graph/cypher_api.py:391-400` runs each statement through `_run_cypher`, which commits it; a
  failing statement is recorded and the next one still runs.
- Impact: a client of `/db/neo4j/tx/commit` (Neo4j's "begin and commit in one request" endpoint, which is atomic in
  Neo4j) gets partial writes when one statement fails. Statement API-B8.6.1.
- What would close it: run the statements in one engine transaction and roll it back on the first error (Neo4j stops
  there too), or document that the route is not atomic; a unit test with a failing second statement.

### F-1611 The generated GraphQL server's health route always says healthy
- Evidence: `iris_vector_graph/gql/__init__.py:58-67` answers 200 `{"status": "healthy"}` whatever `SELECT 1` did; the
  sample API was fixed for exactly this in 4.6.3 (CHANGELOG.md:493-497, `api/main.py:100-113`).
- Impact: an orchestrator's probe keeps a server with no database in service. Statement API-B10.6.
- What would close it: answer 503 when the probe fails, as `api/main.py` does; a unit test with a failing cursor.

### F-1612 The REST dispatcher may read only the first chunk of a large request body
- Evidence: `iris_src/src/Graph/KG/Service.cls:321-327` reads `%request.Content.Read()` with no length and parses that
  as the whole body.
- Impact: if P-1607 holds, a `/vectorSearch` or `/hybridSearch` body over 32,000 characters (a 3,072-wide vector at full
  precision) fails to parse and answers 500. Statement API-B11.12.
- What would close it: read the stream in a loop (or `%FromJSON(%request.Content)`); a live test with a large vector.

### F-1613 The MCP vector lookup treats the client's text as a node id
- Evidence: `iris_src/src/Graph/KG/MCPTools.cls:189-192` documents `query` as "natural language description";
  `MCPTools.cls:209-214` uses it as `node_id` in a subquery that takes that node's vector.
- Impact: an AI client that sends a sentence gets no rows or an error, not evidence. Statement API-B12.9.
- What would close it: embed the text (as `engine.embed_text` or IRIS `EMBEDDING()`) before the search, or document the
  argument as a node id; an e2e test on an AI build.

### F-1614 The demo server's write routes need no key
- Evidence: `src/iris_demo_server/app.py:1-22` adds no `ApiKeyMiddleware`; `src/iris_demo_server/routes/fhir.py:503-533`
  writes a Condition to the FHIR repository and runs a graph sync; `app.py:503-504` binds 0.0.0.0:8200. CHANGELOG.md:994-996
  says every app needs the key and lists the fraud demo server but not this one.
- Impact: anyone who can reach port 8200 can write to the demo FHIR repository and start syncs, and read the status
  cards' IRIS error text. Statement API-B13.2.
- What would close it: add `ApiKeyMiddleware` (and bind 127.0.0.1 by default), or record the demo server as
  presenter-only in its README; extend `tests/unit/test_r097_api_key_every_route.py` to it.

### F-1615 The fraud server's vector lookup always falls back to zeros
- Evidence: `src/iris_fraud_server/app.py:256-279` runs `SELECT embedding FROM kg_NodeEmbeddings WHERE node_id = ?`;
  the table has `emb`, not `embedding`, lives in the IVG Schema, and is keyed by `(graph_id, node_id)`
  (`iris_vector_graph/schema.py:429-437`); it then calls `fetchone()` on an `iris.sql.exec` result, which the same file
  says has none (`app.py:211`). Every error returns a zero vector with only a log line.
- Impact: the fraud score's vector part is always computed from zeros, silently. Statement API-B13.7.
- What would close it: read `emb` from the schema-qualified table for the default graph and iterate the result; a test
  that a stored vector reaches the score.

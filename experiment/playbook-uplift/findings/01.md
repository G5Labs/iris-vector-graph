# Findings of module 01 (install, schema, upgrades)

None of these was run; each rests on reading the code at pin 3eaa79cf.

### F-0101 Legacy removal reports objects removed that may still be there
- Evidence: iris_vector_graph/_engine/legacy.py:670-672 sets `removed = True` after `_drop(conn, "DROP VIEW ...")`
  without reading its result (`_drop` returns False and only logs at INFO on failure, lines 689-698). Lines 679-684
  mark every later SqlProc item of a class `removed = True` once the class was handled, even when the first
  `_delete_class` returned False. tests/unit/test_remove_legacy_objects.py has no case with a failing DROP or delete.
- Impact: an operator who reads the reply believes a 4.5.x view or class is gone while it remains; the data model says
  `removed` is "whether it was dropped" (specs/262-ivg-owned-sql-schema/data-model.md:50-60). Statement INS-I7.6.
- What would close it: set `removed` from `_drop`'s result for views and from the class delete's result for every item
  of that class; add a unit case where DROP VIEW raises.

### F-0102 Some setup failures are only logged, not put in the reply's warnings
- Evidence: a base DDL statement failing for a reason other than "already exists" or a privilege is logged at WARNING
  and setup goes on (iris_vector_graph/_engine/schema.py:2508-2511); a failed `ALTER ... emb VECTOR` goes to
  `report["failed"]` and a log line only (1666-1671), and the reply carries only needs_manual_migration (2564, 2718);
  a failed ^KG bootstrap is a log line (2680-2681). ADMIN_GUIDE (docs/ADMIN_GUIDE.md:428) defines `warnings` as "what
  you must act on, each also logged at WARNING".
- Impact: a namespace can end setup with a table, index or vector width missing and a reply whose warnings are empty;
  a caller that checks the reply, as the docs advise, sees success. Statement INS-B1.12.
- What would close it: append each of these to status["warnings"]; a unit test that makes one CREATE TABLE fail with
  a non-tolerated error and asserts the warning.

### F-0103 The first-use check accepts a namespace with no schema record
- Evidence: iris_vector_graph/schema_name.py:226-235 returns without error when no record exists but the marker class
  `<package>.funcCYCMP` is defined. Spec 262 FR-006a (specs/262-ivg-owned-sql-schema/spec.md:245) requires a refusal
  when the namespace "has no schema record, or lacks the 4.6.0 objects". docs/KNOWN_ISSUES.md:787-809 records the
  consequence after an interrupted setup (accepted, edge writes fail until setup is rerun);
  tests/e2e/test_463_half_setup_writes_e2e.py::test_the_namespace_is_accepted_and_not_adjacency_indexed asserts the
  acceptance.
- Impact: an engine may work on a namespace whose setup stopped after its routines, before the classes, the adjacency
  index or the record; writes fail later rather than at the first call. Statement INS-I3.4.
- What would close it: either refuse when no record exists whatever the marker says (setup is exempt, so the way out
  stays open), or amend FR-006a and the ADMIN_GUIDE errors to say a namespace with the marker and no record is
  accepted.

### F-0104 Spec 240 says its design was not adopted, but it ships
- Evidence: specs/240-alt-migration-as-data/spec.md:6 "Status: Exploratory (alternative implementation; not
  adopted)". iris_vector_graph/migrations/statements.py exists at the pin and iris_vector_graph/migrations/
  docs_and_edge_vectors.py:53 imports it (commit b38b537b, reachable from the pin).
- Impact: a reader of the specs is told the shipped migration code is an unadopted branch. Statement INS-B9.12.
- What would close it: update the spec's status (adopted, with the release), or remove the module if it was not meant
  to ship.

### F-0105 The SQL files under sql/ describe an old schema and put objects outside the IVG Schema
- Evidence: sql/schema.sql:4-52 creates Graph_KG.nodes with `node_id` alone as key, rdf_labels/rdf_props/rdf_edges
  with no graph_id, `u_spo UNIQUE (s, p, o_id)` and VECTOR(FLOAT, 768); setup's DDL is
  iris_vector_graph/schema.py:395-570 (composite keys, graph_id NOT NULL DEFAULT ''). sql/globals_schema.sql:29,
  sql/graph_path_globals.sql:5, 143, 283 and sql/graph_walk_tvf.sql:18, 72 create unqualified procedures, which land in
  the default schema (SQLUser); spec 262 FR-001/FR-002 (spec.md:231-233) say IVG creates nothing outside the IVG Schema.
  sql/migrations/000_base_schema_iris.sql:9-30 creates unqualified tables. scripts/deploy_production.py:65 still runs
  sql/schema.sql.
- Impact: an operator who follows the scripts gets a namespace that setup then calls unfinished, with tables shaped for
  3.x; the ADMIN_GUIDE inventory does not mention these objects. Statement INS-I11.1; decision HD-0103.
- What would close it: HD-0103's answer; then delete, mark or update the files and the script.

### F-0106 Property keys of a label mix graphs
- Evidence: iris_vector_graph/_engine/schema.py:500-515, get_property_keys(label), joins rdf_labels to rdf_props on
  `rl.s = rp.s` with no graph_id. Since spec 227 a node id is unique per graph only, so a node `x` labelled L in graph
  A and a different node `x` in graph B make B's keys show up as L's. get_schema_visualization (2788-2843) samples
  property keys and edge-end labels by id alone in the same way. CONTEXT.md:38-43 says an all-graphs read is the union
  of each graph's own answer (SYS-I2).
- Impact: a schema view or a tool that lists a label's keys shows keys no node with that label has; content of one
  graph (its key names) shows in an answer about another's label. Statement INS-I12.4. Same family as F-1701.
- What would close it: join on `(graph_id, s)`; a unit or e2e case with one id in two graphs.

### F-0107 Every setup runs an unqualified DROP INDEX
- Evidence: iris_vector_graph/schema.py:656-657 puts `DROP INDEX idx_props_key_val` (no table, no schema) in
  ensure_indexes, which every setup runs; the SchemaCursor rewrite does not touch it (no Graph_KG token). Spec 262 FR-007
  (spec.md:246-248) says IVG's SQL names only objects in the IVG Schema, fully qualified.
- Impact: depends on P-0112. If IRIS resolves the name in the default schema, the statement never reaches the IVG
  Schema's rdf_props (so it does nothing for IVG) and would drop an application's own index of that name there.
  Statement INS-T9.3.
- What would close it: qualify it (`DROP INDEX idx_props_key_val ON Graph_KG.rdf_props`, rewritten for the schema), or
  remove the step if no supported release still has that index; a live check of which index IRIS drops.

### F-0108 The upstream test deploy does not follow setup's skip rules
- Evidence: tests/conftest.py:215-262 (_deploy_objectscript) loads and compiles every class under iris_src/src with
  "ck-d", one at a time, and raises if any fails; it does not use select_classes
  (iris_vector_graph/_engine/class_deploy.py:78-106), the functional-index-first order (267-277), or initialize_schema.
  Orchestrator observations (not runs of this builder): the fixture failed on Community 2026.1 for MCPService,
  MCPToolSet, MCPTools, NKGAccel and TraversalBuild, and the unit run saw 86 setup errors in
  tests/unit/test_203_tck_regressions.py; the same server accepted initialize_schema() with 66 classes deployed.
- Impact: the live suites cannot run on IRIS Community without replacing the fixture, though the product supports it
  (docs/ADMIN_GUIDE.md:353); test evidence then comes from AI Hub builds only, unless a harness substitutes setup, as
  this uplift's run-community-redaction.py does. Statement INS-B4.17; premise P-0106.
- What would close it: have the fixture call initialize_schema(), or apply select_classes and the same order; a CI job
  on Community.

### F-0109 The 4.0.0 upgrade does not follow the namespace's schema
- Evidence: iris_vector_graph/migrations/upgrade.py:57-58 and 140 default `schema` to "Graph_KG" and never read
  ^IVG.Deploy("schema"); its docstring (144-152) says the embeddings and ^KG steps address the default schema whatever
  is passed. ADR-0016 (docs/adr/0016-one-ivg-schema-per-namespace.md:10-12) says the name is chosen at install and
  followed by everything.
- Impact: an operator upgrading a namespace whose IVG Schema is not Graph_KG must know to pass `schema=` and still gets
  an embeddings step that reads Graph_KG. Statement INS-B9.11.
- What would close it: read the record (refusing a mismatch as setup does), or state in the API reference and the
  migration notes that the 4.0.0 upgrade supports Graph_KG only.

### F-0110 ADR-0016 lags the shipped design
- Evidence: docs/adr/0016-one-ivg-schema-per-namespace.md:5 "implementation pending: spec 262" while spec 262 says
  "Implemented in 4.6.0"; line 12 says the ObjectScript classes "read it there", while
  iris_vector_graph/schema_name.py:1-8 says the classes never read the record and the deploy rewrites their sources;
  line 26 names `remove_legacy_sql_objects(dry_run=True)`, while the shipped method is `remove_legacy_objects`
  (iris_vector_graph/_engine/admin.py:378). It also writes the name rule as `[A-Z][A-Z0-9_]*`; code and spec accept
  lower case.
- Impact: the decision record misleads a reader about the mechanism and the API name. Statement INS-T2.15.
- What would close it: amend the ADR's status and consequences.

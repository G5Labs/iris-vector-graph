# Findings: module 06 (vectors and vector search)

All evidence is from reading code, docs and tests at pin `3eaa79cf`; nothing here was run. "Live test" means an
upstream test that needs IRIS and that this uplift only read.

### F-0601 A registry read that fails for any reason lets a vector write through unchecked
- Evidence: `iris_vector_graph/_engine/schema.py:1042-1061` (`get_embedding_identity` catches every exception and
  answers None); `:1383-1385` (`enforce_embedding_identity` returns None, so the write goes on). The route read was
  fixed to raise for anything but a missing registry (`iris_vector_graph/_engine/embeddings.py:423-430`, 4.6.0 R161),
  but the identity read was not. Same pattern in `embedding_inventory` (`schema.py:1811-1831`, any error answers `[]`),
  `_route_row_count` (`:1900-1909`, 0) and `list_quarantine` (`:1945-1947`, `[]`). ADR-0006 requires a write to be
  "refusable before it happens"; FR-014 says the check is not opt-in.
- Impact: a transient error, a dropped connection or a user without SELECT on the registry turns the identity check
  off for that write. Route reads are cached for 30 s (`embeddings.py:305-336`), so a write can resolve its route from
  cache and then skip enforcement on a failing registry. The inventory and the quarantine list then read "nothing
  there", the answer an operator acts on by moving on. This weakens the seed claim that compatibility is checked on
  every write.
- What would close it: raise from `get_embedding_identity` (and the inventory and quarantine reads) unless
  `_registry_absent(e)`; a unit test with a cursor raising a non -30 error on the registry read.

### F-0602 Vectors from one model can be stored under another model's identity
- Evidence: `embed_text` falls back from IRIS `EMBEDDING()` to the engine's Python embedder, or auto-loads
  `all-MiniLM-L6-v2`, when the IRIS call fails, logging a warning only (`iris_vector_graph/_engine/embeddings.py:157-197`).
  The queue's `_encode_batch` never calls IRIS `EMBEDDING()`: it uses `self.embedder`, auto-initialised the same way
  (`:2033-2049`). The identity offered for the write is taken from `embedding_config` first
  (`iris_vector_graph/_engine/schema.py:1013-1018`), so it names the IRIS model either way.
- Impact: an engine configured with an IRIS embedding config and a local embedder (or whose IRIS call fails) stores
  local-model vectors in the route recorded for the IRIS model. At equal width nothing refuses it, and nearest
  searches rank meaninglessly: the exact failure ADR-0006 exists to prevent. With only an IRIS config and no local
  embedder, `_encode_batch` raises `TypeError` and every queue entry fails.
- What would close it: offer the identity of the model that actually produced the vector (or refuse to fall back
  across models); make `_encode_batch` use IRIS `EMBEDDING()` when the engine's identity is `iris-embedding-config`.
  A unit test with a fake embedder and a failing IRIS call.

### F-0603 The IRIS queue worker writes vectors with no identity check, and ignores the model for the default graph
- Evidence: `iris_src/src/Graph/KG/EmbedQueue.cls:280-286` sets the target to `Graph_KG.kg_NodeEmbeddings` for every
  default-graph entry whatever `config` it asked for, and looks up a route (`RouteTable`, `:220-235`) only for a named
  graph. Nothing in `ProcessBatch` (`:258-338`) reads `embedding_registry` for the model or width. `RouteTable`
  normalises the key with `$ZStrip(config, "<=>W")` and `$ZConvert(..., "L")`, which is not `normalize_model_key`
  (whitespace runs of mixed characters, casefold).
- Impact: a default-graph entry queued for model B lands in the legacy table claimed for model A; at equal width this
  mixes two models silently. The seed claim "compatibility can be checked on write" does not hold for this writer.
- What would close it: route default-graph entries through the registry like named graphs, compare the entry's
  config with the route's recorded model and width before writing, and share one normalisation rule; a live test that
  queues a default-graph entry for a second model.

### F-0604 The IRIS queue worker marks an entry DONE when no vector was made
- Evidence: `iris_src/src/Graph/KG/EmbedQueue.cls:307-328`: when `stmt.%Prepare("SELECT EMBEDDING(?, ?) ...")`
  fails, or `rs.%SQLCODE` is not 0, or there is no row, control falls through to `Set ^EmbedQueue(reqId, "status") =
  "DONE"`.
- Impact: on an IRIS without `EMBEDDING()`, or with an unknown config, every entry is reported done with no vector
  and no error; `clear_done` then deletes the evidence. The caller sees success.
- What would close it: set ERROR with the IRIS message on a failed Prepare, a negative SQLCODE or an empty result;
  a live test on a config IRIS does not know.

### F-0605 enqueue_for_embedding checks the default table's row, not the target graph's route
- Evidence: `iris_vector_graph/_engine/embeddings.py:1839-1842` always calls
  `enforce_embedding_identity("kg_NodeEmbeddings", config=...)` with graph `''`. The worker-side check was rewritten
  for spec 227 precisely because that row "is the default pair's row and nobody else's" (`:1992-1998`).
- Impact: queuing work for a named graph with model B is refused when the default graph's legacy table is claimed
  for model A, though B's route in that graph would accept it; and work for a graph whose route records another width
  is accepted and fails later on the worker.
- What would close it: resolve the target route (graph, config) and enforce against its row, or skip the check when
  the pair has no route yet; a unit test with two graphs and two models.

### F-0606 Erasure leaves IVF, tree and PLAID indexes holding an erased graph's ids and vectors
- Evidence: `iris_src/src/Graph/KG/Eraser.cls` names routes and the registry but not `^IVF`, `^VecIdx` or `^PLAID`;
  `iris_src/src/Graph/KG/GraphStores.cls:28-133` does not list them. `IVFIndex.Build` records the source table
  (`IVFIndex.cls:9`), not the graph. `docs/migration/v4.0.0.md:742-750` calls IVF a remaining gap. Same shape as F-0702
  for BM25.
- Impact: after `EraseGraph(g)`, `ivf_search`, `vec_search` and `plaid_search` still return g's node ids with scores,
  and the globals still hold g's vectors. A fused search can surface erased ids through its IVF leg.
- What would close it: decision HD-0601, then either scoped pruning inside the erase or documentation plus an
  inventory entry; a live test that erases a graph and searches its IVF index.

### F-0607 The IVF index's "cosine" metric is an unnormalised dot product
- Evidence: `iris_src/src/Graph/KG/IVFIndex.cls:75-78` and `:112-115` score `metric = "cosine"` as
  `$vectorop("sum", $vectorop("v*", q, v))`, the same as `dot`; neither the query nor the stored vectors are
  normalised in `ivf_build` (`iris_vector_graph/_engine/vector.py:1969-1994`) or in `Insert`. `VecIndex.Cosine`
  (`VecIndex.cls:83-90`) does normalise.
- Impact: for vectors that are not unit length, IVF ranks by dot product, so long vectors win; scores are not in
  [-1, 1] and do not match `kg_KNN_VEC` scores for the same data. Fused rankings mix two scales.
- What would close it: normalise at build, insert and query time (or divide by the norms), and a test with
  non-unit vectors comparing IVF and exact cosine order.

### F-0608 Vector index stores do not check width or duplicates
- Evidence: `IVFIndex.Insert` (`IVFIndex.cls:180-215`) writes `^IVF(name, "list", bestCell, nodeId)` without removing
  an entry for that id in another cell and always increments `indexed`; it reads `cfg dim` and never compares it.
  `VecIndex.Insert` (`VecIndex.cls:144-149`) overwrites `cfg dim` with the new vector's width and increments `count`
  on a replace; `VecIndex.Create` (`:42-52`) resets `count` to 0 and keeps old vectors. `PLAIDSearch.Insert`
  (`PLAIDSearch.cls:204-231`) leaves old `docCentroid` entries and increments `nDocs`; it also runs on an index with
  no centroids. Searches do not check the query width either.
- Impact: re-inserting a node with a new vector leaves the old one answering in IVF (best score per id wins, so a stale
  vector can rank the node); counts in `info` drift upward; a wrong-width vector changes a tree index's recorded width.
  What `$vectorop` does on two widths is not established here.
- What would close it: delete-before-insert across cells, count only new ids, refuse a width other than `cfg dim`;
  live tests that re-insert an id and insert a wrong width.

### F-0609 The fused search may read an IVF index built for another graph
- Evidence: `iris_vector_graph/_engine/vector.py:208-225` (`_fusion_leg_index`) falls back to an IVF index whose
  graph is unknown, with a WARNING, when no index built for the graph exists and IRIS cannot score vectors natively.
  An IVF index's graph is known only in the process that built it (`:149-185`). `search_nodes_by_vector` refuses the
  same situation (`:783-790`, FR-013 "a scoped lookup never widens").
- Impact: `kg_RRF_FUSE(graph="g")` can rank another graph's nodes (SYS-I2), and a log line is the only sign.
- What would close it: refuse the IVF leg for an index whose graph is unknown or different, as
  `search_nodes_by_vector` does; persist the graph with the index (`^IVF(name, "cfg", "graph")`).

### F-0610 The SQL kg_KNN_VEC answers no rows, without error, for a graph whose vectors are under a declared model
- Evidence: `iris_src/src/Graph/KG/GraphStores.cls:308-310` (`VectorRouteGuard`) looks only for a registry row with
  `COALESCE(model_key, '') = ''`; with none it returns 0 and the procedure reads `kg_NodeEmbeddings`
  (`iris_vector_graph/schema.py:2437-2483`), which holds no rows for that graph. `docs/KNOWN_ISSUES.md:702-714` says
  such a call raises. The live test (`tests/e2e/test_460_r265_vector_procedures_route_e2e.py`) builds its route with an
  engine that declares no model, so it does not cover this case.
- Impact: a named graph written by an engine with an `embedding_config` (route model key set) gets `[]` from SQL
  `kg_KNN_VEC` and `kg_RRF_FUSE`: "nothing matched", the answer 4.6.0 R265 meant to remove.
- What would close it: have the guard refuse when the graph has any node route other than `kg_NodeEmbeddings`;
  extend the R265 test with a declared model.

### F-0611 Edge vectors the upgrade places in a named graph are not found by edge search, and the edge and text quarantines have no API
- Evidence: the edge step places rows into `kg_EdgeEmbeddings` with the edge's `graph_id`
  (`iris_vector_graph/migrations/statements.py:203-240`) and writes no registry row; `kg_EdgeEmbeddings` is adopted for
  graph `''` only (`iris_vector_graph/_engine/schema.py:1312-1315`). `edge_vector_search(graph="g")` resolves
  `(g, model, edge)` through the registry and answers `[]` when no row exists (`iris_vector_graph/_engine/embeddings.py:672-679`,
  `iris_vector_graph/_engine/vector.py:355-358`). The node step, by contrast, moves other graphs' rows into new routes
  (`graph_scoped_embeddings.py:1048-1093`). The guide's manual fix for a quarantined edge vector inserts into
  `kg_EdgeEmbeddings` too (`docs/migration/v4.0.0.md:590-601`). `list_quarantine`/`place_quarantined` read only
  `embedding_quarantine` (`schema.py:1933-1934`); `edge_vector_quarantine` and `docs_quarantine` have no list or
  place call. CONTEXT.md:159-161 says an operator places each quarantined vector.
- Impact: after a 3.x upgrade every named graph's edge vectors are invisible to edge search; Eraser still removes
  them by graph_id. Quarantined edge vectors and texts can only be fixed by hand-written SQL.
- What would close it: route edge rows of named graphs into `kg_eemb_` tables (as the node step does) or register
  `kg_EdgeEmbeddings` for each placed graph; add list and place calls for the two other quarantines; an e2e test
  that migrates a 3.2.0 fixture with named-graph edge vectors and searches them.

### F-0612 The edge and table searches skip rules the node search keeps
- Evidence: `edge_vector_search` casts the query with `TO_VECTOR(?, dtype, dim)` (`iris_vector_graph/_engine/vector.py:368`),
  uses the engine's `vector_dtype` rather than the route's (kg_KNN_VEC fixed this in 4.6.0 R142, `:539-541`), counts
  commas to get `dim` for a string query (`:366`), and answers `[]` for any error whose text contains "-30", "not
  found" or "empty" (`:388-391`). `vector_search` uses the lengthed form too (`:1233-1242`), and its routed-table
  refusal tests only the `kg_emb_` prefix (`:1211-1213`), so an edge route (`kg_eemb_`) is searched with no graph.
  `VectorOptimizer.check_hnsw_availability` and `benchmark_vector_search` use the lengthed form
  (`iris_vector_graph/vector_utils.py:123-127`, `:320-324`), the benchmark with caller-supplied vectors of any width.
  ADR-0005 forbids the lengthed form for a query vector.
- Impact: the lengthed casts use the query's own width, so they do not pad today, but they defeat the ADR's
  regression guard; a FLOAT edge route fails at the engine's DOUBLE type; an unscoped `vector_search` over an edge
  route crosses graphs; a benchmark with wrong-width vectors times a silently reshaped query.
- What would close it: use the unlengthed form and the route's dtype everywhere; extend the routed-name refusal to
  `kg_eemb_`; unit tests in the style of `tests/unit/test_227_no_widening.py`.

### F-0613 VectorOptimizer.migrate_to_optimized writes vectors without the identity check and reports success with failures
- Evidence: `iris_vector_graph/vector_utils.py:151-280` inserts into `kg_NodeEmbeddings_optimized` row by row with
  `TO_VECTOR(?, DOUBLE, n)`, no `enforce_embedding_identity`, no transaction, no delete-before-insert, and returns
  `success: True` with a `failed` count (a re-run fails every row on the unique key).
- Impact: a public helper bypasses the registry ADR-0006 says every seam must consult; a partial copy reports success.
- What would close it: call `enforce_embedding_identity` for the target, run the copy as one transaction or report
  failure when `failed > 0`; a unit test.

### F-0614 embed_nodes and embed_edges count an identity refusal as an error and return normally
- Evidence: `iris_vector_graph/_engine/embeddings.py:1467-1480` (and `:1658-1671` for edges) re-raise only
  `CallerTransactionOpenError`; `EmbeddingIdentityConflict` is logged at WARNING and added to `errors`. ADR-0006:
  "Spec 226 requires it to raise".
- Impact: a bulk embed against a route that records another model or width returns `{"embedded": 0, "errors": N}`;
  nothing is mixed in, but a caller that does not inspect the counts reads success, and every batch repeats the model
  work before being refused.
- What would close it: re-raise `EmbeddingIdentityConflict` (it is decided before the first write); a unit test.

### F-0615 A store_embeddings batch refused for a missing node can leave a new empty route behind
- Evidence: `iris_vector_graph/_engine/embeddings.py:1064-1073` resolves the route with `create=True` (which creates
  the table, the index and the registry row and commits them, `:470-558`) before the per-item
  `_assert_node_exists` loop at `:1077-1084`. `store_embedding` checks the node first (`:967`).
- Impact: a refused batch changes stores (SYS-I3): the namespace gains an empty `kg_emb_` table and registry row
  whose width came from the refused batch, and the next writer of that pair is held to that width.
- What would close it: check every node before resolving the route; a unit test asserting nothing was created.

### F-0616 The embed selector's label filter crosses graphs, and its exclude pattern escapes without ESCAPE
- Evidence: `iris_vector_graph/embed_selector.py:98-101` (`node_id IN (SELECT s FROM rdf_labels WHERE label = ...)`)
  and `:156-164` (source and target labels) have no graph predicate, though `rdf_labels` carries `graph_id`.
  `_glob_to_sql_like` (`:71-72`) escapes `%` and `_` with a backslash, and the `NOT LIKE` at `:110-112`, `:166-168`
  names no `ESCAPE` (premise P-0603).
- Impact: `embed_nodes(label="X", graph="g")` also embeds g's nodes whose id carries label X only in another graph.
  An exclude pattern containing `_` or `%` (common in ids) excludes nothing, so nodes the caller asked to skip are
  embedded.
- What would close it: add the graph predicate to the label subqueries and `ESCAPE '\'` to the LIKE; unit tests on the
  generated text and a live test for the pattern.

### F-0617 The glossary and user guide say a second model's write is refused; the code routes it to its own table
- Evidence: CONTEXT.md:154-157 ("A write at another width or model is refused rather than mixed in") and
  docs/USER_GUIDE.md:958-960 ("a writer that declares a different model at the same width is refused"). The code
  routes a write naming another model to that model's own route (`iris_vector_graph/_engine/embeddings.py:755-792`),
  and `tests/integration/test_embedding_identity_refusal_e2e.py::test_same_width_different_model_gets_its_own_route`
  asserts it. Refusal now happens only for a mechanism clash on one key, a width clash on one route,
  `set_embedding_identity`, setup's claim and queue checks.
- Impact: readers expect `EmbeddingIdentityConflict` and get a new table; the seed's phrasing inherits the stale text.
- What would close it: update CONTEXT.md and USER_GUIDE to say a declared model gets its own route and a clash is
  refused only within one route.

### F-0618 The ledger's node delete does not reach a default-graph node's routed vectors
- Evidence: `iris_src/src/Graph/KG/LedgerApply.cls:353-370` (`DeleteNodeRows`) deletes from `kg_NodeEmbeddings` and
  `kg_NodeEmbeddings_optimized` only, then deletes the node row. A default-graph node can also have vectors in a
  `kg_emb_` route (a declared model), whose foreign key references the node (`iris_vector_graph/_engine/schema.py:255-263`).
  The engine's `delete_node` goes through `Graph.KG.Eraser.EraseNodeIds`, which reaches every route.
- Impact: under premise P-0608 a ledger `delete_node` of such a node fails with "delete node failed" and the
  changeset is refused, though the engine path would succeed; a caller cannot delete it through the ledger.
- What would close it: have `DeleteNodeRows` delete from every node route the registry names for the default graph;
  a live ledger test with a declared-model vector.

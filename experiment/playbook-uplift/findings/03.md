# Findings of module 03 (direct writes)

Cited from `ontology/03-writes.md` as `finding:F-03kk`. Every finding here comes from reading the code at pin
`3eaa79cf`; none was reproduced on IRIS in this uplift.

### F-0301 The bulk loader writes while ledger strict mode is on
- Evidence: every engine write method calls `ledger_check` first (iris_vector_graph/_engine/nodes_edges.py:396, 1005,
  1195, 1327, 1404, 1693, 1894, 2039, 2257, 2281, 2420, 2559; iris_vector_graph/_engine/query.py:2298-2300).
  `BulkLoader.load_nodes`, `load_edges` and `load_networkx` call no guard (iris_vector_graph/bulk_loader.py:252-272,
  380-402, 540-567). The USER_GUIDE says strict mode refuses `create_node`, `create_edge` "and the other methods"
  (docs/USER_GUIDE.md:1107-1121).
- Impact: with strict mode on, an operator's bulk load writes content that no ledger record names. For erasure and
  redaction this is content the ledger cannot account for; for `verify()` it is divergence.
- What would close it: decision HD-0301, then either a guard in `BulkLoader` or a sentence in the USER_GUIDE.

### F-0302 Strict mode reaches another engine only after its five-second cache expires
- Evidence: `LedgerGuard` reads `Graph.KG.Ledger.Meta()` at most once per 5 s per engine (iris_vector_graph/ledger/
  guard.py:20, 38-59); `set_strict` refreshes only the calling engine's guard (iris_vector_graph/ledger/client.py:
  305-309). The unit test pins the window: a write 4 s after a cached "not strict" passes
  (tests/unit/test_ledger_guard.py `test_cache_honours_ttl_and_refresh`). The guard also lets the write through when
  the probe fails (guard.py:55-56; `test_probe_failure_fails_open`). The USER_GUIDE says strict mode refuses the
  writes, without a window (docs/USER_GUIDE.md:1107-1121).
- Impact: for up to 5 s after strict mode is turned on, other engines (other processes, other app servers) still write
  without records; a namespace whose Meta read fails for an engine never gets strict mode from it.
- What would close it: document the window and the fail-open rule next to `set_strict`, or move the check to the server
  (where it also covers plain SQL).

### F-0303 A direct edge delete leaves the ledger's live link for the edge
- Evidence: `delete_edge` is a plain SQL `DELETE` (iris_vector_graph/_engine/nodes_edges.py:1418-1433). Only the
  ledger classes and `Graph.KG.Eraser` touch the ledger's live entries `^IVG.Ledger("stmt")` and
  `^IVG.Ledger("tuple")` (grep at the pin: Ledger, LedgerApply, LedgerGenesis, LedgerRedact, Eraser, GraphKey).
  `delete_node` goes through `Eraser.EraseNodeIds`, whose per-edge step kills the edge's live entry
  (iris_src/src/Graph/KG/Eraser.cls:641-680, 669-677). A Cypher relationship `DELETE` is plain SQL too.
  CONTEXT.md:198-205 states the erasure guarantee as "no live statement outlives its content".
- Impact: after a direct edge delete with the ledger enabled (not strict), the tuple index still maps the triple to a
  statement whose edge is gone. A later ledger change that names the triple of a re-created edge reuses that old
  statement id, so the history joins two different edges into one statement.
- What would close it: route `delete_edge` (and the Cypher relationship delete) through `Eraser.EraseEdges`, as
  `bulk_delete_adjacency` already does (nodes_edges.py:2332-2335), or state the gap next to "Writes outside the
  ledger" in the USER_GUIDE; an e2e test with the ledger enabled.

### F-0304 Storing an edge over a marked edge does not take the edge over
- Evidence: ADR-0009 (CONTEXT.md:66-73): an explicit structural create of a triple clears the temporal mark, so a
  temporal purge cannot remove the edge. `create_edge` (nodes_edges.py:1250-1252, 1275-1304) and `bulk_create_edges`
  (1992-2001) adopt the marked row. `store_edge` inserts, swallows the duplicate and stops (2567-2581).
- Impact: an edge a caller wrote with `store_edge` disappears when the temporal side purges the triple's last
  timestamp.
- What would close it: run `_ADOPT_TEMPORAL_ROW_SQL` after `store_edge`'s duplicate, plus an e2e test.

### F-0305 A bulk write larger than one chunk is not one transaction on the server-loader path
- Evidence: `bulk_create_nodes` and `bulk_ingest_edges` send batches of 1,000 rows to `Graph.KG.EdgeScan`'s server
  loader (iris_vector_graph/_engine/nodes_edges.py:1735-1750, 2056-2066). With no caller transaction they call it
  through `self._iris_obj()` (1726, 2054), which on an engine made by `from_connect` is a Native API connection of its
  own (iris_vector_graph/engine.py:1916-1942), so each call's own `TSTART` / `TCOMMIT`
  (iris_src/src/Graph/KG/EdgeScan.cls:277-307, 352-424) commits in another process; the `WriteTxn` opened on the
  cursor (1718, 2048) does not cover it. A failure in chunk k leaves chunks before it committed; the call then logs a
  warning and runs the SQL path over the whole batch (1755-1757, 2069-2071). The USER_GUIDE says each bulk write is a
  transaction of its own (docs/USER_GUIDE.md:238-241).
- Impact: if the SQL fallback also fails, the call raises with part of the batch written. Not seen on an engine that
  shares its connection with the Native API (the createIRIS(conn) path), where both run in one process.
- What would close it: use `txn.native()` (the cursor's own process) for the loader in both cases, or one loader call
  per transaction; an e2e test on a `from_connect` engine that fails the second chunk.

### F-0306 `create_node` answers False for a write IRIS refuses as invalid
- Evidence: the except clause treats any error text holding "validation failed" as a duplicate and answers False
  (iris_vector_graph/_engine/nodes_edges.py:1097-1102). The graph name is not width-checked (only the id, labels and
  keys are, 1006-1013), so a graph name over 256 characters fails the `nodes` insert with SQLCODE -104, whose text says
  "Field validation failed" (premise P-0307). 4.6.0 R203 says a refusal is not "already there" (CHANGELOG.md:1130-1137;
  the comment at 1103).
- Impact: the caller is told the node exists when nothing was written. Low severity (graph names that long are rare).
- What would close it: drop the "validation failed" match (widths are checked first now), or check the graph name's
  width with the others; a unit test.

### F-0307 The server path of `bulk_ingest_edges` skips a refused edge without an error
- Evidence: `Graph.KG.EdgeScan.BulkIngestEdgesSQL` skips an edge on any INSERT error other than -119, and on a failed
  endpoint registration, and does not count it (iris_src/src/Graph/KG/EdgeScan.cls:290-300). `bulk_ingest_edges`
  checks no field widths (iris_vector_graph/_engine/nodes_edges.py:2039-2045, unlike `bulk_create_edges` at 235-237)
  and returns the count (2058-2076). Its SQL path raises `GraphWriteError` for the same refusal (2104-2110). 4.7.0
  "row 14" made every other bulk writer raise for a refused row (nodes_edges.py:234, 1855-1858, 1982-1990).
- Impact: a 129-character predicate, or an id too long for the index, is dropped silently on the default (server)
  path; the call answers a smaller count and no error, and `bulk_load_session.add_edges` inherits it.
- What would close it: width-check the triples in Python before sending, and make the loader throw on a refused row;
  an e2e test with one too-wide predicate.

### F-0308 The bulk loader stores a NaN or infinite edge property as JSON no reader accepts
- Evidence: `BulkLoader.load_edges` writes qualifiers with `json.dumps(quals)` (iris_vector_graph/bulk_loader.py:453),
  whose default writes the bare tokens `NaN` and `Infinity`. `create_edge` and `store_edge` refuse such values because
  IRIS's JSON functions then fail every relationship read that meets the row (iris_vector_graph/_engine/nodes_edges.py:
  288-302, 4.6.0 R307).
- Impact: one such edge from a networkx load makes later Cypher reads of the graph's relationships fail.
- What would close it: use `_qualifiers_json` (or `allow_nan=False`) in the loader, with a unit test.

### F-0309 The bulk loader rebuilds the indexes of `Graph_KG` whatever schema it loaded
- Evidence: `BulkLoader(schema=...)` writes `<schema>.nodes` and the other tables (iris_vector_graph/bulk_loader.py:
  73-81), but `rebuild_all_indices` calls `%BuildIndices` on the fixed classes `Graph.KG.rdfedges`, `rdflabels`,
  `rdfprops` and `nodes` (bulk_loader.py:495). A namespace has one IVG schema, which may be other than `Graph_KG`
  (docs/adr/0016-one-ivg-schema-per-namespace.md; CONTEXT.md:20-24).
- Impact: in a namespace whose schema is not `Graph_KG`, a `%NOINDEX` load writes rows and then cannot rebuild their
  indexes; `load_networkx` raises after the rows are committed, and the rows stay invisible to indexed reads.
- What would close it: derive the class names from the schema (as `GraphSchema` does), with a unit test on a non-default
  schema.

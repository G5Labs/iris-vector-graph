# Findings of module 04 (ADJ, adjacency)

All findings below come from reading the code at pin `3eaa79cf`. None was reproduced on IRIS by this builder.

### F-0401 A killed source generation can let an in-flight reader store a wrong out-degree
- Statement: ADJ-I5.9, ADJ-I5.9.1 (a source generation never goes back; no count holding another process's open
  write is stored under a current generation).
- Evidence: `Graph.KG.Adj.Degree` (`iris_src/src/Graph/KG/Adj.cls:63-80`) reads the generation, probes the writer lock
  and lets it go at once, counts, then stores `$ListBuild(tGen, count)` if the generation still equals `tGen`.
  Soundness needs every writer whose change the count could include to move the generation after the change. Three
  writers kill it instead: `Adjacency.RemoveSource` (`Adjacency.cls:376-377`), `RemoveGraph` (`437-438`) and
  `RemoveAll` (`461-462`); `FillEdge` refills without stepping (`824-830`). A killed generation reads as 0, so it does
  not "move" when it was already 0 (after any rebuild without the row hook, or after a snapshot restore into such a
  namespace, which kills `gen` for every graph it wrote: `iris_vector_graph/_engine/snapshot.py:1685-1691`). Reachable
  sequence, no row hook:
  source S has out entries, no `gen` and no cache entry for the key (its warm fill was skipped because another writer
  held the graph's lock); reader R reads `tGen = 0`, its probe succeeds; `Eraser.EraseGraph` starts in its transaction,
  deletes the rows (no hook, so no per-edge `Remove`), and `RemoveGraph` kills out, gen and degc; R counts 0, sees
  generation 0 = `tGen`, stores (0, 0), and the re-read after the store still sees 0; the erase fails and rolls back.
  The rollback restores out and in but not R's new entry (premise P-0408), and nothing restores a `gen` that did not
  exist, so `Degree(S)` answers 0 from a "current" entry until the next write to S. With the row hook, an indexed
  `BuildKG` refills through `Put`, which steps `gen` once per row, so a source whose generation equalled its edge count
  returns to the same value; a reader that counted mid-refill and checks after S's refill completes stores a partial
  count under a current generation, which only the warm fill (`Adjacency.EndRebuild`) overwrites, and only if its own
  probe succeeds. The comment at `Adj.cls:46-48` names the reset but only guards a move between the check and the store.
- Impact: a wrong out-degree served as current (degree, KHopCount, centrality, the two-hop counts built from it) until
  the next write to that source. Narrow window: the reader's probe must precede the writer's lock and its count must
  follow the kill. The live race test (`tests/e2e/test_degree_cache_live.py::test_a_write_in_flight_is_seen_but_never_cached_and_rollback_is_clean`)
  takes the reader's probe after the writer holds the lock, so it does not exercise this order; the randomized test
  uses one connection.
- What would close it: decision HD-0401; then either step the generation instead of killing it, or add an epoch to the
  entry. A model check of the four reader steps against Put/Remove/RemoveSource/RemoveGraph/RemoveAll with rollback,
  or a live test that pauses a reader between probe and count, would show the window open or closed.

### F-0402 A rebuilt store or cached answer can stay current after the write it read is rolled back
- Statement: ADJ-I7.3, ADJ-I11.2.
- Evidence: writers step the graph-version token inside their own transaction (`Adjacency.cls:92`, `157`, `260`, `340`),
  and a rollback does not take the step back (P-0401). Every token-stamped build reads the token first and then reads
  the adjacency without a lock: the result cache (`Graph.KG.AlgoCache.Lookup`, `AlgoCache.cls:27-36`, then
  `iris_vector_graph/stores/iris_sql_store.py:966-982` stores under that token), the two-hop counts
  (`TraversalBuild.cls:948`, `992`), the interned snapshot rewrite (`TraversalBuild.cls:333`, `371`) and the Arno
  snapshot (`ArnoAccel.cls:305-316`). If writer W has written an edge and stepped the token to T but not committed, a
  build that starts then reads token T and W's uncommitted edge (P-0002), and is stamped T. When W rolls back, the token
  stays T, so the store reads as current and holds an edge that no longer exists until the next write moves the token.
  `AlgoCache.cls:5-7` says such an entry is "never wrongly fresh", and `freshness.py:14-16` says a rolled-back write
  "only costs a rebuild"; both cover a write that starts after the stamp, not one already open. ADR-0012 (lines 23-26)
  names this exact case as unsafe for the degree cache and closes it there with the lock probe; no rebuilt store has the
  probe. `tests/unit/test_freshness.py::test_a_rolled_back_bump_leaves_the_store_not_current_and_never_wrongly_current`
  models only a bump after the stamp.
- Impact: PageRank, PPR, WCC and CDLP answers (and the two-hop counts, the interned snapshot, the Arno snapshot) can
  include a rolled-back edge, served as current, until any later write.
- What would close it: give stamped builds the degree cache's rule (probe the parent writer lock exclusively with no
  wait before computing, and store only when the probe succeeded and the token did not move), or document the window in
  CONTEXT.md and the ADMIN_GUIDE. A live test: writer opens a transaction with `create_edge`, a second connection runs
  `kg_WCC`, writer rolls back, third call must not return the rolled-back component.

### F-0403 verify_graph reports drift on a graph with parallel edges whose index matches its rows
- Statement: ADJ-B9.7.
- Evidence: `Graph.KG.GraphVerify.VerifyGraph` counts one per row (`GraphVerify.cls:72-78`, `tSqlEdges`) but keys the row
  set by (s, p, o) and walks `^KG("out")`/`^KG("in")` only to the target level (`GraphVerify.cls:83-104`, `108-129`), so a
  triple with three parallel edges gives `sqlEdges` 3, one matched entry, and "missing" 2 for both stores; `ok` is 0.
  The keyed children and `"#"` count (`Adjacency.cls:197-207`) are never read. Spec 234 says GraphVerify reports the
  edges of a parallel pair (`specs/234-multigraph-parallel-edges/spec.md:78-80`) and sets SC-005 "GraphVerify reports
  zero drift on a multigraph graph after 1,000 random create and delete operations" (`spec.md:355-356`). No test runs
  `VerifyGraph` on a graph with parallel edges (`tests/integration/test_verify_graph.py` has none).
- Impact: every multigraph with a parallel edge fails the drift check; an operator following it runs `sync()` and the
  report still fails, which hides real drift in such graphs.
- What would close it: count rows per (s, p, o) and compare with the `"#"` count (or the keyed children), plus a live
  test for SC-005.

### F-0404 Snapshot restore writes the adjacency index outside the one writer where the row hook is not declared
- Statement: ADJ-I1.6.
- Evidence: `_import_global_from_ndjson` (`iris_vector_graph/_engine/snapshot.py:1654-1692`) sets archived
  `^KG("out")`/`^KG("in")` nodes over the Native API whenever the namespace has no adjacency index
  (`snapshot.py:1658-1662` skips them only when indexed), with no writer lock and no generation step; it then kills
  `degw`, `degc` and `gen` for each graph it wrote. ADR-0011 (lines 12-17) makes `Graph.KG.Adjacency` the only writer,
  ADR-0008 (line 46) and spec 252 FR-016 say `Snapshot.ImportGlobals` restores rows only. The guard
  `tests/unit/test_adjacency_single_writer.py` scans `iris_src/src/**/*.cls` only (`_writers`, lines 77-84), so a Python
  writer is invisible to it.
- Impact: on a namespace without the row hook, the restore is a second adjacency writer: readers can cache counts while
  the import runs (no lock), and the closing kill of `gen` can reset a generation under an in-flight reader (F-0401).
  Low in practice: indexed namespaces skip these lines.
- What would close it: route the restore's adjacency through `Graph.KG.Adjacency` (BeginRebuild/FillEdge/EndRebuild) or
  rebuild from the restored rows; extend the guard to Python Native API writes of `^KG("out"/"in")`.

### F-0405 Some weight refreshes do not move the graph-version token
- Statement: ADJ-B3.2.2.
- Evidence: `Adjacency.PutShadow` sets a new weight on an existing edge and steps neither the generation nor the token
  (`Adjacency.cls:128-136`); `PutKeyed`'s "same edge again" branch does the same (`Adjacency.cls:234-237`). `Reweight`
  and the multigraph row update do step the token (`Adjacency.cls:340`, `529`). CONTEXT.md:116-119 says every write
  path able to change what an algorithm answers moves the token. `tests/unit/test_degree_cache_writers.py::test_version_bumps_are_unchanged`
  fixes the counts as they are.
- Impact: low; a weighted reader of a token-stamped store (the interned snapshot holds weights, `TraversalBuild.cls:462-466`)
  can keep an old weight while reading as current. PutShadow runs only where the row hook is not declared
  (`TemporalIndex.cls:110-115`).
- What would close it: step the token whenever a stored weight changes; a unit assertion on both branches.

### F-0406 Clearing the degree cache alone gives zeros while the warm stamp holds
- Statement: ADJ-I5.17.5.
- Evidence: ADR-0012 (line 17): "The cache is derived: Kill it and every answer is still right." Since the warm stamp
  (`Adj.AllWarm`, `Adj.cls:207-217`), readers that visit every node read `$ListGet($Get(^KG("degc", ...)), 2, 0)` without
  a generation check while `^KG("degw", g)` equals the token (`Centrality.cls:79-91`, `TraversalKHop.cls:13-20`,
  `TraversalBuild.cls:846-847`, `972-975`). Killing `^KG("degc")` does not move the token or kill `degw`, so every
  such reader then answers 0 for every node. The restore knows this and kills `degw` first (`snapshot.py:1685-1691`);
  the ADR, ADMIN_GUIDE and the tests that kill `degc` alone and then call `Degree` (which recounts) do not show it.
- Impact: an operator (or a test) following the ADR's advice gets zero degree centrality and zero KHopCount until the
  next write; medium-low.
- What would close it: make `AllWarm` require an entry to be present for a node it treats as warm, or have the ADR and
  ADMIN_GUIDE say to kill `^KG("degw")` with `^KG("degc")`; a live test that kills `degc` alone under a warm stamp.

### F-0407 Reweight takes no writer lock and moves no generation, against ADR-0012 and spec 252 FR-004
- Statement: ADJ-T3.6.1.
- Evidence: ADR-0012 (line 31): "Every adjacency write must bump the generation and hold the shared lock"; spec 252 FR-004:
  "Every index change MUST move the source's degree generation". `Adjacency.Reweight` (`Adjacency.cls:323-342`) does
  neither, on purpose (comment at line 327, `tests/unit/test_degree_cache_writers.py` LOCK_EXEMPT_METHODS and
  `test_reweight_does_not_bump_gen`, `tests/e2e/test_degree_cache_live.py::test_reweight_does_not_move_the_generation`).
- Impact: none for out-degree answers (a count does not depend on a weight); the intent documents over-state the rule.
- What would close it: amend ADR-0012 and FR-004 to "every write that changes the set of out entries".

### F-0408 Comments and docs still describe adjacency behaviour that changed
- Statement: ADJ-T1.3, ADJ-B3.9.1.
- Evidence: `iris_src/src/Graph/KG/EdgeScan.cls:149` says `graph=""` is the default graph, while the same file
  (lines 15-19) says it never was and `Adjacency.Put` would write an empty subscript; `GraphVerify.cls:12-16` and
  `iris_vector_graph/_engine/admin.py:854-861` say `drop_graph` deletes rows and leaves the adjacency behind, but
  `drop_graph` is now `erase_graph` (`nodes_edges.py:1588-1595`), which removes it in the same transaction
  (`Eraser.cls:217-235`); `docs/adr/0010-degree-is-counted-never-stored.md` line 5 says "implementation pending" though
  `^KG("deg")`/`("degp")` are gone; `Adjacency.cls:527` calls `degw` "the weighted degree cache", but `degw` is the warm
  stamp (`Adj.cls:207-213`).
- Impact: low; a reader of the code or the docstring draws the wrong conclusion about defaults and erase.
- What would close it: correct the four texts.

### F-0409 A failed adjacency rebuild inside a caller's transaction rolls back the caller's work
- Statement: ADJ-B8.9.
- Evidence: `TraversalBuild.BuildKG`'s failure path runs `TRollback` with no argument (`TraversalBuild.cls:155-157`),
  which ends every level (P-0409). `engine.sync()` does not refuse a caller's transaction
  (`iris_vector_graph/_engine/schema.py:2859-2895`), unlike `initialize_schema()` and `retract_inference()`
  (`schema.py:2148-2156`, `3192-3201`). CHANGELOG 4.6.4 (`CHANGELOG.md:410-424`) states "An IVG write never commits or
  rolls back a transaction its caller opened", counts autocommit-off as a caller transaction, and lists the classes that
  now roll back to the level they found; `TraversalBuild` is not among them. Inside a caller transaction the rebuild lock
  release (`Adjacency.EndRebuild`) is also deferred to the caller's end (P-0003), so no other reader caches a degree
  until the caller commits.
- Impact: a `sync()` that fails (for example on a row whose graph id is not a legal subscript, the case in
  `tests/e2e/test_degree_cache_live.py::test_a_failed_buildkg_leaves_the_adjacency_and_releases_the_rebuild_lock`)
  silently discards the caller's earlier uncommitted writes.
- What would close it: roll back to the level found (`While $TLevel > tTxnLevel { TROLLBACK 1 }`), or refuse `sync()`
  inside a caller's transaction; a live test with autocommit off.

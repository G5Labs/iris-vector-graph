# Findings: module 17 (operations and runtime)

Each is a disagreement between the code at pin 3eaa79cf and a stated intent (a document, a docstring, the product
glossary). Evidence is inspection of the pinned source unless it says otherwise; nothing here was run.

### F-1701 The SQL adapter's unscoped node and label reads merge graphs
- Evidence: `IRISGraphStore.get_nodes(node_ids, properties, graph=None)` reads `rdf_labels` and `rdf_props` with no
  graph predicate when `graph` is None and folds every graph's labels and properties for one id into one row
  (`iris_vector_graph/stores/iris_sql_store.py:1116-1154`). `get_node_labels` (`:1156-1160`) calls it with no graph, and
  `query_nodes(label_filter=...)` (`:1162-1210`) has no graph parameter at all (labels, `nodes` and `rdf_props` of every
  graph). The Cypher path uses both without a graph: the start-node label check (`iris_vector_graph/_engine/query.py:245`),
  the label start set (`:266`) and the target label filter (`:3319`). The engine's own `get_nodes` says an unscoped read
  "merged their label lists and let one graph's property values overwrite another's" and is scoped since spec 227
  (`iris_vector_graph/_engine/nodes_edges.py:621-636`). CONTEXT.md "All-graphs read" (decided 2026-10-20): a node's
  labels and properties are its own graph's.
- Impact: with one node id in two graphs carrying different labels, a graph-scoped variable-length query can start
  from, or keep as a target, a node whose label exists only in the other graph. The answer then holds a node that does
  not match the pattern in the queried graph (a cross-graph leak of a label fact, SYS-I2).
- What would close it: a live test with node `x` labelled `A` in graph `g1` and unlabelled in `g2`, running
  `USE GRAPH 'g2' MATCH (s:A)-[*1..2]->(t) RETURN t` and the target-label form; then a graph argument on the three store
  reads, passed from the query path.

### F-1702 A caller transaction cannot be opened through an in-IRIS cursor
- Evidence: `EmbeddedCursor.execute` returns without running anything for `START TRANSACTION`, `BEGIN`,
  `BEGIN TRANSACTION`, `COMMIT` and `ROLLBACK` (`iris_vector_graph/embedded.py:312-321`); the unit test asserts the no-op
  (`tests/unit/test_embedded.py::test_transaction_statements_are_noop`). docs/USER_GUIDE.md "Writes inside your
  transaction" says a transaction is open after SQL `START TRANSACTION` and the user's `ROLLBACK` removes IVG's write,
  with no exception for `EmbeddedConnection` (which section 1 of the same guide offers for code inside IRIS). On a
  namespace whose classes predate 4.6.4, `WriteTxn`'s own fallback runs `START TRANSACTION` / `COMMIT` / `ROLLBACK` on
  the cursor (`iris_vector_graph/_write_txn.py:206-207`), so through this cursor that fallback has no transaction either.
- Impact: inside IRIS, the guide's example (`cur.execute("START TRANSACTION")`, `create_node`, `cur.execute("ROLLBACK")`)
  leaves the node committed; on an old namespace a multi-statement write is not atomic.
- What would close it: an irispython E2E running the USER_GUIDE example through `EmbeddedConnection`; then either pass
  the statements through (or map them to `TSTART`/`TROLLBACK`) or document the limit.

### F-1703 IVG_STRICT_NAMESPACE warns; two documents say it raises
- Evidence: with `IVG_STRICT_NAMESPACE=1` the store calls `warnings.warn(NamespaceMismatchWarning)` after logging
  (`iris_vector_graph/stores/iris_sql_store.py:836-838`); the unit test checks a warning
  (`tests/unit/test_namespace_aware.py::test_probe_strict_message_contains_both_namespaces`). `docs/ADMIN_GUIDE.md:1254`
  says "`1` raises", and the class docstring says "Upgrade to a hard error by setting IVG_STRICT_NAMESPACE=1"
  (`iris_vector_graph/exceptions.py:19-20`). docs/API_REFERENCE.md (`IVG_STRICT_NAMESPACE`) describes the code.
- Impact: an operator who sets strict mode to stop work in the wrong namespace gets a printed warning and the work runs.
- What would close it: raise when strict (the warning class could stay for the default), or correct ADMIN_GUIDE and the
  docstring.

### F-1704 The error root does not catch every IVG error
- Evidence: `iris_vector_graph/errors.py:1-17` says "All engine-side errors descend from IVGError ... the whole package
  ... shares a single catchable root". At the pin `IVGSchemaError` (`iris_vector_graph/schema_name.py:38`),
  `BulkLoadError`, `TemporalWindowError`, `FHIRGraphError`, `ClassesUnreadable` (RuntimeError),
  `EmbeddingIdentityConflict`, `NamespaceConsistencyError` (ValueError) in `iris_vector_graph/exceptions.py:62-157`,
  `HostError` (`iris_vector_graph/host.py:29`), `ArnoError` and `EmbeddedUnavailableError` (ImportError) do not descend
  from `IVGError`. `tests/unit/test_error_model.py::test_all_descend_from_single_root` checks six classes only.
  docs/API_REFERENCE.md lists the real bases.
- Impact: `except IVGError` misses the schema refusal on first access, a refused bulk batch and a failed temporal read.
- What would close it: re-base these on `IVGError` (keeping the current bases as mixins) or narrow the docstring; extend
  the test to every exported error.

### F-1705 vector_similarity_search ranks L2 results farthest first
- Evidence: `metric="L2"` maps to `VECTOR_L2` and the statement orders `score DESC`
  (`iris_vector_graph/dbapi_utils.py:256-272`); `VECTOR_L2` is a distance (P-1710). The docstring promises a similarity
  search; `tests/unit/test_dbapi_utils_unit.py` has no L2 case.
- Impact: `top_k` L2 search returns the k farthest rows.
- What would close it: `ORDER BY score ASC` for L2 (or negate it), and a test with three known vectors.

### F-1706 create_hnsw_index does not try ACORN first
- Evidence: the docstring says "Tries ACORN=1 first (faster build, IRIS 2025.1+), falls back to standard HNSW"; the code
  issues one `CREATE INDEX ... AS HNSW(M=..., efConstruction=..., Distance=...)` and returns False on any other error
  (`iris_vector_graph/dbapi_utils.py:170-204`).
- Impact: callers expecting a filtered (ACORN-1) index get a plain HNSW index, or `False` on a server that refuses it.
- What would close it: implement the two-step attempt or correct the docstring.

### F-1707 SHOW CONSTRAINTS and the index lists name keys the schema does not have
- Evidence: `_show_constraints` reports `node_id_unique` on `["node_id"]` owned by `pk_nodes`, and `edge_spo_unique` on
  `["s", "p", "o_id"]` owned by `pk_rdf_edges` (`iris_vector_graph/_engine/admin.py:266-278`); `_show_indexes` and the
  store's `list_indexes` add `pk_nodes` (node_id) and `pk_rdf_edges` (s, p, o_id) as UNIQUE ONLINE
  (`iris_vector_graph/_engine/admin.py:261-262`, `iris_vector_graph/stores/iris_sql_store.py:3079-3080`). The schema at
  the pin keys nodes on `pk_nodes_graph PRIMARY KEY (node_id, graph_id)` / `uq_nodes_graph_node (graph_id, node_id)` and
  edges on `u_spo_graph_ekey UNIQUE (s, p, o_id, graph_id, ekey)` (`iris_vector_graph/schema.py:399-400`, `:44`).
  `tests/unit/test_admin_unit.py::test_returns_builtin_constraints` asserts the old names.
- Impact: a Neo4j tool or an operator reading `SHOW CONSTRAINTS` is told a node id is unique across graphs and an edge
  triple is unique, both false since spec 227 and spec 234 (multigraph mode).
- What would close it: read the constraints from the dictionary, or list the real names and columns.

### F-1708 The bolt-on installer does not do what deploy/README.md says
- Evidence: deploy/README.md:24 says the installer "creates namespace, installs schema, outputs API key and start
  command", and :85 that the `ivg_service` user it creates "has access only to Graph_KG.* tables". `deploy/bolt-on/install.sh`
  generates a service password (:21-22) and writes it into `ivg-config.yml` (:71-91), but never creates the user or any
  grant; nothing in `iris_vector_graph` or `api` reads `ivg-config.yml` (README :100 "uses ivg-config.yml"). The printed
  start command (:97) passes the service password with no user name, and `ivg server start` has no user option
  (`iris_vector_graph/cli.py:419-434`), so the server logs in as `IRIS_USERNAME`, default `_SYSTEM`, with that password.
  The namespace step queries `%SYS.Namespace` in SQL and calls `%SYS.Namespace.Create` over the Native API (:36-49);
  docs/ADMIN_GUIDE.md section 1 says IVG creates no namespace and namespace creation (`Config.Namespaces.Create`) cannot
  be done over the Native API. Failures there only print a warning.
- Impact: the documented least-privilege service user does not exist; following the printed command fails to log in
  (or, if an operator exports `IRIS_USERNAME=_SYSTEM` and its password, runs as a superuser).
- What would close it: create the user and the ADMIN_GUIDE section 3 grants in the installer, pass the user name, and
  drop the config file claim; or rewrite deploy/README.md path 2.

### F-1709 deploy/README.md promises a refusal the server does not make
- Evidence: deploy/README.md:86 "The server refuses `auth: none` with `host: 0.0.0.0` unless `--force-no-auth` is
  passed." `ivg server start` defaults `--host 0.0.0.0` and has no such flag (`iris_vector_graph/cli.py:419-441`);
  authentication is off when `IVG_API_KEY` is unset (`iris_vector_graph/_api_key.py:21-23`), as docs/ADMIN_GUIDE.md
  section 5 states. No code reads `IVG_AUTH_MODE`, which `deploy/docker/compose.yml:34` sets.
- Impact: an operator relying on the deploy guide exposes an unauthenticated graph server on every interface.
- What would close it: decision HD-1705, then code or document to match.

### F-1710 The docker deploy recipe cannot build or log in as written
- Evidence: `deploy/docker/compose.yml:19-22` builds the `ivg` service from `context: ../..`, `dockerfile: Dockerfile`;
  the pin has no `Dockerfile` at the repository root (`git ls-tree 3eaa79cf`). The service logs in as `ivg_service`
  (:31), a user nothing in the recipe or its CPF merge (`deploy/docker/cpf/merge.conf`) creates. The IRIS image is the
  unpinned `iris-community:latest` (:3), while the root `docker-compose.yml:26-30` pins `2026.1` because a moving
  `latest-em` tag broke it.
- Impact: deploy/README.md path 1 ("5 minutes") fails at build; with a Dockerfile it would fail at the first IRIS login.
- What would close it: add the Dockerfile and a user-creation step (or use `_SYSTEM` for the demo and say so), and pin
  the image.

### F-1711 The deploy guide's SDK example reads a field IVGResult does not have
- Evidence: deploy/README.md:73-79 iterates `result.records` and indexes `r["node_id"]`; `IVGClient.execute_cypher`
  returns `IVGResult` (pydantic: `columns`, `rows`, `error`, `metadata`, `sql`, `params`, `bolt_column_types`), which
  has no `records` (`iris_vector_graph/result.py:9-16`, `iris_vector_graph/sdk.py:79-84`). `IVGRecord` exists in sdk.py
  but nothing returns it.
- Impact: the example raises `AttributeError` as written.
- What would close it: use `result.rows` / `result.columns` in the example, or give `IVGResult` a `records` view of
  `IVGRecord`s.

### F-1712 LazyKG.in_degree collapses parallel edges that degree() counts
- Evidence: `degree()` asks `Graph.KG.Adj.Degree`, which counts parallel edges (`iris_vector_graph/stores/lazy_kg.py:215-235`,
  docstring "counting parallel edges"); `in_degree()` and `in_degree_for_predicate()` count the keys of
  `^KG("in", g, node, p, s)` (`:237-269`), one key per (predicate, source) whatever the edge count. In multigraph mode a
  triple with two or more edges keeps one `^KG("in", g, o, p, s)` node with keyed children
  (`iris_src/src/Graph/KG/Adjacency.cls:197-209`). No test covers in_degree on a multigraph.
- Impact: in-direction degree centrality (and anything else reading in_degree) under-counts nodes with parallel inbound
  edges, while out-direction counts them.
- What would close it: count the keyed children (or the `"#"` count) for a multigraph triple, and a multigraph unit
  test.

### F-1713 STATUS_PARTS omits two parts that status() marks unknown
- Evidence: `STATUS_PARTS` ("What `EngineStatus.unknown` may name") lists graph, acceleration, sync, vector_index,
  fulltext_index, ivf_index, plaid_index and ledger (`iris_vector_graph/status.py:10-11`); `_status_probes` also appends
  `"adjacency"` (`iris_vector_graph/_engine/admin.py:551`) and `"routines"` (`:752-753`), which docs/ADMIN_GUIDE.md
  section 7 documents. The refused-namespace path sets `unknown=list(STATUS_PARTS)` (`:403-406`), so it leaves those two
  out.
- Impact: a caller iterating `STATUS_PARTS` to read the report misses two unknown parts; on a refused namespace the
  routines and the adjacency index are not marked unknown though nothing was probed.
- What would close it: add both names to `STATUS_PARTS` and a unit test that `set(status.unknown) <= set(STATUS_PARTS)`.

### F-1714 Two IVGClient calls and the async client do not map 401/403
- Evidence: `IVGClient._refused` is documented "401 and 403 as IVGClientError, for every request (R225)"
  (`iris_vector_graph/sdk.py:195-201`), and the class docstring of `IVGClientError` says the same (`:22-25`).
  `load_ndjson` and `explain` call `raise_for_status()` without it (`:166-182`), and `AsyncIVGClient` never calls it
  (`:254-281`), so they raise `httpx.HTTPStatusError`. The `ivg load` command uses `load_ndjson`.
- Impact: `except IVGClientError` around a refused load or any async call does not catch the refusal.
- What would close it: route those calls through `_refused` and add unit tests with a 401 transport.

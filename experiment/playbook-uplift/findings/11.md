# Findings: module 11 (ledger core)

All evidence is from reading code, tests and docs at pin `3eaa79cf`; nothing here was run.

### F-1101 A replayed commit writes its post-commit properties again
- Evidence: `iris_vector_graph/ledger/client.py:418-443`: after a successful wire answer, `_commit` applies
  `post_commit_properties` whenever the changeset has any, with no `not replayed` test (the staleness flag just above,
  `:424-428`, does test it). `Changeset.fingerprint()` covers only actor, actor type and ops
  (`iris_vector_graph/ledger/changeset.py:365-385`), so a retry with the same key may also carry different
  post-commit properties and still be replayed. Each property is a `DELETE` then `INSERT` on `rdf_props`
  (`client.py:469-480`), which has no foreign key on `nodes` (`iris_vector_graph/schema.py:411-417`;
  `tests/integration/test_218_post_commit_properties_e2e.py:81-99` accepts a write for a node that does not exist).
  Intent: a replayed commit "applies nothing" (`tests/integration/test_ledger_us04_idempotency.py:52-62`, without
  post-commit properties) and SYS-I6 "never saves twice".
- Impact: a retry overwrites any later governed `set_prop` of the same key with the old value, outside the ledger,
  so the live store and the ledger disagree (`verify()` diverges). After an erasure and before redaction, a retry
  whose post-commit properties name an erased node writes its property row back: the erased tenant is live again,
  redaction then refuses the target (its liveness check reads `rdf_props`), and an adoption would record the content
  again. The retry key is not redacted at that point, so the retry is replayed rather than refused.
- What would close it: skip post-commit properties when `replayed` is true (or make them part of the revision,
  decision HD-1105), and a live test that retries a committed changeset with post-commit properties after a later
  `set_prop` and after an erasure.

### F-1102 The stats row can lose counts
- Evidence: rejection and replay counts are added by `Graph.KG.LedgerStats.Bump` after the commit's
  `TCOMMIT`/`TROLLBACK` and after `Lock -^IVG.Ledger("head")` (`iris_src/src/Graph/KG/Ledger.cls:404-413`), in its
  own transaction with no lock (`iris_src/src/Graph/KG/LedgerStats.cls:65-88`). `Ensure()` reads the one row with
  `%OpenId` (`:51-61`) and every writer saves the whole row: `WriteRevision` (`Ledger.cls:559-565`, inside the commit
  transaction, which since 4.7.0 may stay open for a whole caller transaction), `Enable`, `Disable`, `SetStrict`,
  `RecordVerify` (`Ledger.cls:192-210, 274-276, 310-312, 344-346, 367-369`). Premise P-1103. Intent:
  "`ledger_stats` counts every process's commits, so it is the one to use for totals"
  (`docs/ledger-prometheus-hook.md:15-16`); FR-051 (`LedgerStats.cls:1-3`).
- Impact: two processes that count at the same time can save over each other's increment; a caller transaction that
  rolls back a nested commit restores the row's before-image and wipes counts other processes added meanwhile.
  `commits_ok`, `rej_*` and `replays_idem` are lower bounds under concurrency, not totals. `head_seq` in the row can
  also lag `^IVG.Ledger("head")`.
- What would close it: increment each counter atomically (`$Increment` on a global the table maps, or an SQL
  `UPDATE ... SET c = c + 1`), or document the counters as approximate; a live test with concurrent rejections.

### F-1103 An adoption is not tied to the head it compared
- Evidence: `verify(adopt=True)` reads the records up to the head it saw, reads the live tables, then commits the
  difference as `kind="adoption"` with no `expected_head` (`iris_vector_graph/ledger/replay.py:806-857`, the
  `Changeset` at `:849-856`). `Graph.KG.LedgerGenesis.Adopt` writes the items as records without checking them
  against the stores (`iris_src/src/Graph/KG/LedgerGenesis.cls:82-129`). The re-enable path sets the state to enabled
  first and then lets the Python client run the adoption (`Ledger.cls:271-286`, `iris_vector_graph/ledger/client.py:291-296`);
  every concurrent `enable()` of a disabled ledger is answered `adoption_needed` and runs its own adoption.
- Impact: a commit that lands between the read and the adoption can be adopted again (a `create_rel` for a tuple that
  already has a statement id from that commit is recorded a second time, `LedgerGenesis.cls:97-105`) or contradicted
  by an adoption record built from the older view; two concurrent re-enables can adopt the same writes twice. The
  history then no longer replays to the live store.
- What would close it: send the verified head as `expected_head` on the adoption (and retry the verify on
  `StaleHeadError`), or compute the adoption under the head lock on the server; a live test that commits during an
  adoption.

### F-1104 Two first enables at once: the second fails instead of returning the genesis
- Evidence: `Graph.KG.Ledger.Enable` reads the state at `iris_src/src/Graph/KG/Ledger.cls:254` and takes the head lock
  only at `:266`, inside the branch for a not-enabled ledger; it never reads the state again under the lock. The
  second caller then re-runs the genesis path (`:288-304`: resets `head`, `stmtNext`, writes records at seq 1) and
  fails when the seq-1 revision row exists (premise P-1106), answering `inconsistent`. Intent: `enable()` returns
  "current head (idempotent)" (`specs/213-graph-revision-ledger/contracts/ledger-api.md:22`).
- Impact: a deploy script or two services that both call `enable()` on a fresh namespace see
  `LedgerInconsistencyError` from one of them. The rollback restores the overwritten globals, so the ledger itself is
  intact; between the overwrite and the rollback a lock-free reader (`Meta`, `Head`) can see head 0.
- What would close it: re-read the state after `Lock +` and return the head when it is already enabled; a live test
  with two concurrent `enable()` calls.

### F-1105 Deleting a node that only a named graph holds records a delete that removed nothing
- Evidence: `NodeExists` matches the id in any graph (`iris_src/src/Graph/KG/LedgerApply.cls:79-84`), while
  `DeleteNodeRows` deletes the default graph's rows only (`:354-371`) and always appends a `delete_node` record
  (`:369`), with a snapshot read from the default graph (`:337-351`, empty here). `OpDeleteNode` therefore accepts
  the id (`:380`) and records the delete. The ledger and verify see nodes graph-blind
  (`iris_src/src/Graph/KG/LedgerGenesis.cls:17-36`, `iris_vector_graph/ledger/replay.py:599-609`).
- Impact: replay drops the node while the named graph's row is still there, so `verify()` reports a divergence right
  after a commit the ledger accepted; the record's prior value claims the node had no labels or properties. The same
  graph-blind check lets `set_prop` write a property row with no default-graph node and makes `add_label` fail on a
  foreign key (decision HD-1101). Untested: `tests/e2e/test_460_r290_ledger_node_ops_graph_e2e.py` only covers an id
  held in both graphs.
- What would close it: decision HD-1101, then a live test with an id only a named graph holds.

### F-1106 A replayed commit returns no statement ids
- Evidence: the replay branch answers `RevisionResponse(seq, 1, {})` (`iris_src/src/Graph/KG/Ledger.cls:459-461`), so
  `stmt_ids` is empty. Intent: `commit()` returns the "original outcome with `replayed=True`"
  (`specs/213-graph-revision-ledger/contracts/ledger-api.md:26`), and `CommitResponse.stmt_ids` maps each
  create/upsert edge change to its statement id (`specs/213-graph-revision-ledger/contracts/changeset.schema.json:273-285`).
  `tests/integration/test_ledger_us04_idempotency.py::test_replay_returns_original_outcome_and_applies_nothing`
  checks the revision id and op count only.
- Impact: a client that retries after a lost answer (the purpose of a retry key) cannot learn the statement ids of the
  edges its first attempt created, except by reading the revision's records.
- What would close it: rebuild `stmt_ids` from the revision's `create_rel` records (or store them with the key), or
  amend the contract; a test that compares the two answers' `stmt_ids`.

### F-1107 A commit accepts any revision kind
- Evidence: `GraphLedger.commit(changeset, *, kind="changeset")` passes `kind` through
  (`iris_vector_graph/ledger/client.py:381-405`); the server takes it from the meta JSON (`Ledger.cls:424`), runs the
  empty and size checks only for `changeset` (`:488-498`), sends `adoption` to `LedgerGenesis.Adopt` (records with no
  store change) and anything else to `LedgerApply.ApplyAll`, and stores the string as the revision's kind (`:523`,
  `Kind` up to 16 characters, `iris_src/src/Graph/KG/LedgerRevision.cls:20`). Intent: the revision kinds are an
  enum, `genesis | adoption | changeset` (`specs/213-graph-revision-ledger/contracts/changeset.schema.json:219`;
  spec 256 adds `redaction`).
- Impact: any caller can write a revision labelled `genesis` or `redaction`, skip the size limit by using another
  kind, or write adoption records that describe changes no store saw. History and audit readers that trust `kind` are
  misled.
- What would close it: refuse kinds other than `changeset` and `adoption` in `CommitInTxn` (and keep `adoption`
  for the client's own verify), with a unit test.

### F-1108 Two write paths skip the strict-mode guard
- Evidence: `bulk_delete_adjacency` deletes edge rows through `Graph.KG.Eraser.EraseEdges` with no `_ledger_check`
  (`iris_vector_graph/_engine/nodes_edges.py:2301-2339`), while its neighbours call it (`:1513`, `:1553`, `:2281`).
  The GraphQL mutations `create_protein`, `update_protein` and `delete_protein` write `nodes`, `rdf_labels`,
  `rdf_props`, `rdf_edges` and `kg_NodeEmbeddings` with raw SQL and no guard (`api/gql/resolvers/mutation.py:23-230`).
  Intent: strict mode refuses "`create_node`, `create_edge` and the other methods" (`docs/USER_GUIDE.md:1107-1109`);
  the contract lists the guarded calls and names only `BulkLoader` and raw SQL as unguarded
  (`specs/213-graph-revision-ledger/contracts/ledger-api.md:82-93`).
- Impact: with strict mode on, these calls make unrecorded writes that `verify()` later reports; the HTTP surface
  lets a remote client do so.
- What would close it: add the guard to both (or document them as unguarded), and extend
  `tests/integration/test_ledger_us05_compat.py::test_every_guarded_api_is_rejected_and_nothing_changes`.

### F-1109 The user guide says a retry replays without a retry key
- Evidence: "Committing the same actor and operations again returns the first revision with `replayed=True`"
  (`docs/USER_GUIDE.md:1102`). The server looks for a replay only when `idempotency_key` is set
  (`iris_src/src/Graph/KG/Ledger.cls:455-457`); without one a second commit is a new revision or a failed change
  (for example `node_exists`). The `CommitResult` docstring repeats the omission (`iris_vector_graph/ledger/client.py:85-91`).
- Impact: a reader who retries without a key gets a duplicate revision or an error, not a replay.
- What would close it: say "with the same `idempotency_key`" in both places.

### F-1110 The wire contract lags the code
- Evidence: `specs/213-graph-revision-ledger/contracts/changeset.schema.json` has no `create_temporal_edge` op
  (`:54-175`) though the builder and server accept it (`iris_vector_graph/ledger/changeset.py:309-345`,
  `iris_src/src/Graph/KG/LedgerApply.cls:43`); the record enums lack `create_temporal_edge` and entity kind
  `temporal_edge` (`:248-262`); `Changeset` is `additionalProperties: false` (`:180`) but `to_wire` adds
  `post_commit_properties` (`changeset.py:358-359`); `CommitError.error` (`:293-305`) lacks `idempotency_redacted`
  and `redaction_in_progress`, which a commit can answer (`Ledger.cls:471`, `LedgerRedact.cls:265`). The API contract
  still lists `LedgerTransactionOpenError` for `commit` (`contracts/ledger-api.md:26`), which 4.7.0 no longer raises
  (`iris_vector_graph/ledger/errors.py:82-84`), and its `history()` row lacks `correlation_id` and `source`
  (`:27`).
- Impact: a client validating against the published schema rejects valid changesets and answers; the contract is not
  a complete list of the errors a commit can raise.
- What would close it: update both contract files; `tests/unit/test_ledger_changeset.py::test_wire_validates_against_schema_if_jsonschema_available`
  could cover a temporal op and post-commit properties.

### F-1111 The metrics hook is not called for refusals made in Python
- Evidence: `docs/ledger-prometheus-hook.md:35-36`: "`engine.ledger.commit()` calls it once per call, whatever the
  outcome". `commit()` runs `changeset.validate()` first (`iris_vector_graph/ledger/client.py:392`), which raises
  `EmptyChangesetError` or `ChangesetOperationError` before `_emit` (`:408-416`), as does a failing `$TLEVEL` probe
  (`:395`).
- Impact: dashboards built on the hook under-count refusals; the stats row never sees them either.
- What would close it: emit before raising, or narrow the doc to "every call that reaches the server".

### F-1112 Two e2e fixtures read a meta key that does not exist and disable the ledger after them
- Evidence: `tests/e2e/test_460_r281_ledger_post_commit_graph_e2e.py:52` and
  `tests/e2e/test_460_r290_ledger_node_ops_graph_e2e.py:66` compute `was_enabled = bool(engine.ledger.meta().get("enabled"))`;
  `Graph.KG.Ledger.Meta` answers `state`, `strict`, `max_ops`, `recon_bound`, `head_seq`, `head_id` and never
  `enabled` (`iris_src/src/Graph/KG/Ledger.cls:143-156`).
- Impact: both fixtures always call `enable()` and always `disable()` at teardown, so a scratch namespace whose ledger
  was enabled before the run is left disabled, and their nodes written before `enable()` become unrecorded writes on
  an enabled ledger.
- What would close it: test `meta()["state"] == "enabled"`.

### F-1113 The history source filter matches stored JSON text, not a "source string"
- Evidence: `history(source=...)` is documented as "Filter to revisions tagged with this source string"
  (`iris_vector_graph/ledger/client.py:613`) and appends `source = ?` (`iris_vector_graph/ledger/replay.py:339-341`);
  a changeset's `source` is a map (`iris_vector_graph/ledger/changeset.py:102`) saved as IRIS's JSON text of it
  (`iris_src/src/Graph/KG/Ledger.cls:521-522`). The upstream e2e test notes the gap and tests `correlation_id` instead
  (`tests/integration/test_216_ledger_history_filter_e2e.py:65-82`). Spec 216 in `CHANGELOG.md:4976-4980` presents it
  as a source filter.
- Impact: `history(source="cmms")` never matches a revision committed with `source={"system": "cmms"}`; matching
  needs the exact JSON text IRIS wrote, key order included.
- What would close it: document the exact-text rule (or filter on a JSON field), and a live test.

### F-1114 Erasure changes the statement maps without the head lock
- Evidence: every ledger writer of `^IVG.Ledger("stmt")` / `("tuple")` holds the head lock (commit:
  `iris_src/src/Graph/KG/Ledger.cls:440`, `LedgerApply.cls:160-169`, `:680-682`; redaction batches:
  `iris_src/src/Graph/KG/LedgerRedact.cls:282`) except `Graph.KG.Eraser`, which kills statements and tuple entries
  in its own transaction and takes no lock (`iris_src/src/Graph/KG/Eraser.cls:665-678`, `:809-811`, `:1117-1145`;
  the class has no `Lock`). It also kills closed statements, not only live ones (`:1120-1128`). Intent: SYS-I1, one
  owner per fact; ADR-0004 keeps records and removes live statements.
- Impact: a commit and an erasure of the same graph can interleave on the maps. A commit that resolved a statement
  just before erasure killed it records a `delete_rel` and writes the statement back as closed; a commit that
  allocates a statement in the graph being erased can leave a tuple entry for a row erasure then deletes, or lose its
  entry to erasure's earlier dirty read. "No live statement outlives its content" then depends on timing.
- What would close it: take `^IVG.Ledger("head")` in the Eraser's transaction when it touches the maps (or document
  that erasure must not run beside commits), and a live test that commits into a graph while it is erased.

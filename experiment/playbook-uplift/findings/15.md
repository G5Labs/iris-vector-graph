# Findings of module 15 (INT)

Each finding is from reading the code at pin 3eaa79cf. None was run or observed live in this uplift.

### F-1501 PROV export raises on a failed window read; its docs say it logs and writes an empty file
- Evidence: since commit 2d1d6f46 (4.6.0) `_get_temporal_edges_window` has no `try` and raises
  (`iris_vector_graph/_engine/prov.py:181-207`), and
  `tests/unit/test_admin_rdf_prov_shacl_coverage.py::test_get_temporal_edges_window_no_iris_raises` asserts the raise.
  The `prov_export` docstring (`prov.py:114-115`: "A failed window read is logged and exports nothing") and
  `docs/SEMANTIC_LAYER.md:267-269` ("logged as a warning and exported as an empty file, not raised") still describe the
  pre-4.6.0 behaviour. `docs/API_REFERENCE.md` copies the docstring.
- Impact: a reader expecting an empty file on a too-large window gets an exception instead; the 4.6.0 behaviour is the
  intended one (CHANGELOG "A read whose query fails raises").
- What would close it: update the docstring and SEMANTIC_LAYER.md "Limits of the PROV-O export".

### F-1502 A reifier node is always in the default graph, and erasing the edge's graph leaves it
- Evidence: `reify_edge` calls `self.create_node(reifier_id)` with no graph and inserts its label and properties with no
  `graph_id` (`iris_vector_graph/_engine/schema.py:3304-3322`), so the reifier node of an edge in named graph G lives in
  the default graph. `Graph.KG.Eraser.EraseGraph(G)` deletes only the `rdf_reifications` rows of G's edges
  (`iris_src/src/Graph/KG/Eraser.cls:185-189`), not the reifier nodes; `erase_graph` adds nothing
  (`iris_vector_graph/_engine/nodes_edges.py:1512-1527`). `delete_node` does remove reifiers
  (`nodes_edges.py:2176-2199`), so the two deletion paths disagree.
- Impact: properties written on a reifier (for example a source, a confidence or an access policy about tenant G's
  edge) stay live in the default graph after G is erased: a breach of SYS-I2 (graph isolation) and of SYS-D26 (erasure
  removes a graph's content from every store). It challenges the seed "Live erasure". The reifier also answers default
  graph queries while its edge lives in G.
- What would close it: give `reify_edge` the edge's graph (read `graph_id` with the `edge_id`) and have `EraseGraph`
  delete the reifier nodes of the graph's edges; a live test that reifies an edge in G, erases G and finds no reifier.

### F-1503 delete_reification deletes every row for the id in every graph and leaves the node's edges
- Evidence: `delete_reification` deletes `rdf_reifications`, `rdf_props`, `rdf_labels` and `nodes` rows `WHERE s = ?` /
  `node_id = ?` with no graph predicate, does not check that the id is a reifier, and does not touch `rdf_edges` or
  `^KG` (`iris_vector_graph/_engine/schema.py:3361-3397`). The docstring says "Not graph-scoped".
- Impact: `delete_reification("x")` removes the labels, properties and node row of an unrelated node `x` in any graph
  (a tenant's included) and leaves its edges and adjacency without a node row. It is documented as not graph-scoped but
  contradicts SYS-I2 and the "a refused command changes nothing" spirit of the 4.6.0 write rules.
- What would close it: refuse an id with no `rdf_reifications` row, scope the deletes to the reifier's graph, and
  delete its edges through the Eraser (`EraseEdges`) as `delete_node` does.

### F-1504 map_sql_table looks for an unqualified table in schema USER
- Evidence: `map_sql_table` checks `INFORMATION_SCHEMA.COLUMNS WHERE TABLE_SCHEMA = ?` with
  `table.split(".")[0] if "." in table else "USER"` (`iris_vector_graph/_engine/fhir.py:113-120`). IRIS puts an
  unqualified table in `SQLUser` (premise P-1509). Every test uses a qualified name
  (`tests/unit/test_sql_table_bridge.py`, `BridgeTest.<table>`).
- Impact: mapping a table created without a schema is refused with "Table ... not found", though the later Cypher
  translation would find it.
- What would close it: use `SQLUser` (or the namespace's default schema) for an unqualified name, and a test with an
  unqualified table.

### F-1505 FHIRSearchTool says it handles pagination; the search reads one page
- Evidence: `FHIRSearchTool`'s docstring says it "Wraps FHIR REST API details (pagination, auth, resource parsing)"
  (`iris_vector_graph/fhir_bridge.py:305-310`); `fhir_search_conditions` issues one GET and parses that Bundle only,
  never following `link[relation=next]` (`fhir_bridge.py:105-110`).
- Impact: a patient with more Conditions than one page holds loses the rest, so fewer anchors resolve. Deprecated code
  (removal planned for 5.0), still reachable from the Cypher API's bridge fallback (`cypher_api.py:293-324`).
- What would close it: follow `next` links (with a page cap), or correct the docstring.

### F-1506 With rdflib 8, export and SHACL say rdflib is missing
- Evidence: `_build_rdflib_graph` imports `ConjunctiveGraph` in the same `try` as `rdflib` and turns any `ImportError`
  into "rdflib is required for RDF operations. Install with: pip install 'iris-vector-graph[rdf]'"
  (`iris_vector_graph/_engine/_rdf_utils.py:125-133`). With rdflib 8 installed (premise P-1507) `export_rdf` and
  `validate_shacl` fail with that message, while `export_rdf_from_cypher` and `prov_export` (plain `Graph`) work.
- Impact: the refusal names the wrong cause (SYS-I9). The `[rdf]` extra pins `<8`, so this needs an environment that
  overrode the pin (the conflict `docs/KNOWN_ISSUES.md:716-722` describes).
- What would close it: check `rdflib.__version__` and name the rdflib 7 requirement.

### F-1507 The bridge anchor lookup matches a node of that id in any graph
- Evidence: `get_kg_anchors` joins `fhir_bridges` to `nodes` on `node_id` only
  (`iris_vector_graph/_engine/fhir.py:470-477`). `migrate_fhir_bridges_to_crosswalk` documents that "Bridges point at
  default-graph nodes" (`iris_vector_graph/_engine/fhir_graph.py:650-652`).
- Impact: a bridge target that exists only in a named graph (another tenant's, say) counts as an anchor, and the
  pipeline then seeds a rank walk with it. Deprecated code.
- What would close it: add `AND COALESCE(n.graph_id, '') = ''` (or the anchors' graph) to the join.

### F-1508 The Cypher API falls back to the old bridge when reading the FHIR graphs fails
- Evidence: `_patient_anchors` wraps `fhir_patient_anchors` in `except Exception: found = {"graphs": []}`
  (`iris_vector_graph/cypher_api.py:331-336`) and then uses the external bridge. Spec 235 FR-021 says the bridge is used
  "otherwise", meaning when no synced FHIR graph holds the patient; the 4.6.0 rule is that a failed read is an error the
  caller sees (CHANGELOG, commit 2d1d6f46).
- Impact: an IRIS error, a privilege error or a graph written by a newer IVG (RuntimeError) is answered as
  `anchor_source: "fhir_bridge"`, often with no anchors, and the query runs on the wrong anchors silently.
- What would close it: catch only "no FHIR graph tables" (already answered by `fhir_patient_anchors`) and let other
  errors reach the response.

### F-1509 The old clinical pipeline reports a failed rank walk as "no graph connectivity"
- Evidence: `unified_clinical_pipeline` catches any exception from `kg_PERSONALIZED_PAGERANK`, logs it, and sets
  `status = "anchors_resolved_but_no_graph_connectivity"` (`iris_vector_graph/fhir_bridge.py:281-295`). Its docstring
  also omits the `fhir_error` status the code returns (`fhir_bridge.py:220-227`, `:255-258`).
- Impact: a broken walk reads as a graph fact. Deprecated code, removal planned for 5.0.
- What would close it: re-raise, or a distinct `ppr_error` status; document `fhir_error`.

### F-1510 RDF export claims bounded memory but holds the whole graph in memory
- Evidence: the module docstring says export uses a "Streaming cursor pattern — memory-bounded for any graph size"
  (`iris_vector_graph/_engine/rdf_export.py:10-14`). `_build_rdflib_graph` fetches rows in batches of 500 but adds every
  triple to one in-memory rdflib `ConjunctiveGraph` (`_rdf_utils.py:135`, `:210-284`), serialized at the end
  (`rdf_export.py:143`). The same graph backs `validate_shacl`.
- Impact: memory grows with the exported graph; a large export can exhaust the Python process.
- What would close it: write N-Triples or N-Quads row by row, or correct the docstring and SEMANTIC_LAYER.md.

### F-1511 A failed register can leave its new settings written
- Evidence: `Register` upserts the `fhir_graphs` row (`FHIRGraph.cls:235-245`) outside any transaction, then runs
  `Open`, `LoadColumns` (which runs `LoadLinks`, `LoadCompartment` and `LoadProps`) and the `json_links` update
  (`FHIRGraph.cls:247-258`). A throw there returns an error (`:276-278`) with the upsert kept.
- Impact: a refused register changes the endpoints, denylist and interval (SYS-I3). The json-link list itself is
  pre-validated, so the window is small (schema metadata reads, `HS.FHIRServer.Schema.LoadSchema`).
- What would close it: wrap the upsert and the link update in one transaction, or validate before writing.

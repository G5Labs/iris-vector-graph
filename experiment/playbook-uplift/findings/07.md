# Findings: module 07 (text search and fusion)

All evidence is from reading code and tests at pin `3eaa79cf`; nothing here was run.

### F-0701 BM25 Build and Drop write without the write lock or a transaction
- Evidence: `iris_src/src/Graph/KG/BM25Index.cls:97-175` (Build: `Kill ^BM25Idx(name)` at line 99, then
  `IndexDoc` writes `tf`, `df`, `doc`, `len` per document with no `LockWrite`, no `TStart`; the header `N`/`schema`
  is set at lines 160-170) and `:587-591` (Drop: a bare `Kill`). Insert and Delete take `^BM25Idx(name,"lock")`
  and a transaction (`:456-491`, `:500-512`). The seed says "schema 2 updates token records and frequencies together
  under a write lock"; ADR-0007 says "does every write under an index-level lock in a transaction".
- Impact: an Insert during a Build finds no `N`, creates a fresh header (`:461-466`) and is then overwritten by
  Build's `Set N` (`:160`), so `N`/`totalLen` disagree with `len` and `df` (spec FR-018). A Build or Drop during an
  Upgrade pulls the posting lists from under it. A stopped Build leaves postings with no header; `Info` says the index
  does not exist and the next Insert starts a new header over the leftovers. Search during a Build answers `[]`.
- What would close it: decision HD-0701, then a live test that runs Insert (and Upgrade) beside a Build and checks
  `df`/`N`/`totalLen` against a brute-force count.

### F-0702 Erasure leaves BM25 indexes holding an erased graph's terms and node ids
- Evidence: `iris_src/src/Graph/KG/Eraser.cls:138-147` deletes the `docs` rows ("the BM25 corpus") but nothing in the
  Eraser touches `^BM25Idx`; `iris_src/src/Graph/KG/GraphStores.cls:28-133` lists neither `^BM25Idx` nor a reason it is
  not scoped, although every BM25 index records its graph (`BM25Index.cls:168`). ADR-0004 and CONTEXT.md:198-208
  say erasure removes content from every store; GraphStores' own comment (lines 113-115) states "no answer outlives
  erased content".
- Impact: after `EraseGraph(g)` (or erasing some nodes), `bm25_search` on an index built for `g` still returns the
  erased node ids with scores, and `^BM25Idx` still holds the terms of their text. A later node that reuses an id is
  found by the old text. For the redaction work, erased tenant text survives in a global no inventory names.
- What would close it: add `^BM25Idx` to the inventory (scoped by its recorded graph) and drop or prune each index
  built for the erased graph inside the erase; a live test that erases a graph and searches its index.

### F-0703 A BM25 index goes stale silently when node text changes
- Evidence: nothing outside `Graph.KG.BM25Index` writes `^BM25Idx` (grep at the pin); property writes, node deletes
  and imports do not call `Insert`/`Delete`, and the index carries no version token. `docs/USER_GUIDE.md:893-894`
  leaves it to the caller (`bm25_insert` / `bm25_delete` "keep an index current"). The system invariant SYS-I8
  (CONTEXT.md:109-120) says a store built from other stores matches them or says it is out of date.
- Impact: a deleted node, or a node whose text changed, is still found by its old text, with nothing in `Info` or the
  answer to say so.
- What would close it: either a staleness signal (for example the graph-version token stored at build time and
  compared in `Info`/`Search`), or a recorded exemption from SYS-I8 for caller-maintained indexes.

### F-0704 A refused index-handle build has already destroyed the old BM25 index
- Evidence: `iris_vector_graph/_engine/vector.py:299-310` calls `bm25_build`, which runs `Build` and so `Kill
  ^BM25Idx(name)` first (`BM25Index.cls:99`), and only then raises `IndexNotBuiltError` when zero documents were
  indexed. `Build` with only blank property names kills the index and returns `indexed 0` with no header
  (`BM25Index.cls:99-111`).
- Impact: violates SYS-I3 (a refused command leaves every store as it was): a mistaken rebuild of a working index,
  for example over a property no node has, both errors and empties it.
- What would close it: check the property list and the row count before killing, or build under a temporary name and
  swap.

### F-0705 An index with no recorded graph is read as the default graph's own index
- Evidence: `BM25Index.cls:608-612` and `docs/API_REFERENCE.md:834` say an index from before graphs were recorded
  reports `graph` as `""` though it covers every graph. `iris_vector_graph/_engine/vector.py:164-185` takes that `""`
  as the recorded graph, so `_fusion_leg_index` (`:208-210`) picks it as the default graph's own index with no warning,
  and the translator's `_index_graph_rows` (`iris_vector_graph/cypher/translator.py:3125-3142`) tags its rows as the
  default graph's.
- Impact: such an index answers other graphs' node ids in a default-graph fusion or Cypher call, the leak the
  "unknown scope" warning exists to flag.
  The same holds for an index created by a first `Insert` (`BM25Index.cls:461-466` writes no `graph`), whatever graph
  its documents came from.
- What would close it: `Info` answering `graph: null` when the `graph` subscript is absent (indexes built before
  4.0.0, and indexes created by `Insert`), and a unit test of `_index_graph` on that answer.

### F-0706 The stopword node `__stop__` is listed and writable as a BM25 index
- Evidence: `iris_vector_graph/_engine/vector.py:84-104` builds the engine's index registry by walking every first
  subscript of `^BM25Idx` when `iris.gref` exists (embedded Python), with no skip for `__stop__`; only
  `BM25Index.List()` skips it (`BM25Index.cls:626-633`, fixed in 4.6.0 R165). `BM25BuildInput`
  (`iris_vector_graph/_validate.py:163-179`) checks only that the name is not blank; spec 044 (Edge Cases) says index
  names are validated with `sanitize_identifier`.
- Impact: in embedded mode `list_indexes()` shows a BM25 index named `__stop__`; its handle's `drop()` deletes the
  stopword list; a fusion with no index for its graph may fall back to it. `Build("__stop__", ...)` writes an index
  into the stopword list.
- What would close it: skip `__stop__` in the registry walk; decide HD-0704.

### F-0707 Under USE GRAPH, BM25 calls do not check that the index was built for that graph
- Evidence: `iris_vector_graph/cypher/translator.py:3133-3134` returns early under a graph context, so
  `ivg.bm25.search` reads whatever index is named; `_translate_retrieve` (`:3283-3292`) reads the BM25 index
  `bm25_name` (default `"default"`) with no graph check while its vector arm is scoped (`:3304-3322`).
- Impact: `USE GRAPH 'g' CALL ivg.bm25.search('idx_of_h', ...)` answers graph h's node ids and scores, then resolves
  them as graph g's nodes; `ivg.retrieve` fuses another graph's text ranking with g's vectors. SYS-I2 says content of
  one graph never shows up in an answer about another.
- What would close it: compare the index's recorded graph with the graph context and refuse a mismatch (and an
  unknown graph); a unit test like `test_460_r192_all_graphs_procedures.py` under `USE GRAPH`.

### F-0708 Spec 044 states behaviour the code no longer has
- Evidence: `specs/044-bm25-index/spec.md` FR-002 and FR-010 (stored `avgdl` and `idf`), User Story 2 scenario 4
  (an empty query returns an empty list, but `bm25_search` raises a validation error: `_validate.py:182-195`,
  `tests/unit/test_bm25_index.py::test_bm25_search_empty_query_raises_validation_error`), User Story 4 scenario 2 (a
  warning on a dropped index; none is logged), Edge Cases (`sanitize_identifier` on names; not done) and FR-012 / User
  Story 5 (kg_TXT falls back to BM25 `default`; not implemented, see HD-0703). The test
  `TestBM25IndexE2E::test_kgtxt_returns_bm25_scores_not_like_scores` never calls `kg_TXT`; it calls `bm25_search`.
- Impact: the spec, still marked Draft, is the cited intent for BM25; readers get the wrong contract.
- What would close it: amend the spec to the 4.2 and 4.6.5 behaviour, or implement what it keeps; rename the test.

### F-0709 Fused searches can hide a failed leg
- Evidence: engine `kg_RRF_FUSE` (`iris_vector_graph/_engine/vector.py:1421-1436`) logs any leg failure and fuses
  what it has (known issue, `docs/KNOWN_ISSUES.md:172-181`); it also fuses with no text leg at all when no BM25 index
  exists (`:1432-1434`), silently, although spec 044 US7 scenario 9 requires the text leg to contribute.
  `HybridSearchFusion.multi_modal_search` raises a failed text leg but logs and drops a failed vector leg
  (`iris_vector_graph/fusion.py:144-152`); `adaptive_search` returns `[]` when every path fails (`fusion.py:301-310`,
  pinned by `tests/integration/test_fusion_dbapi_bulk.py::test_adaptive_search_all_fail`). The repo's own rationale
  (`fusion.py:165-168`) is that a swallowed leg made "hybrid" results indistinguishable from real ones.
- Impact: an empty or one-legged answer reads as "nothing matched" or as a real hybrid ranking.
- What would close it: the 4.7.1 plan (raise naming the leg) applied to every fusion path, or a field in each answer
  naming the legs that ran.

### F-0710 Weighted fusion's default weights go to legs by position, not by kind
- Evidence: `iris_vector_graph/fusion.py:214-219`: `weights = [0.5, 0.3, 0.2][:len(result_lists)]` with the comment
  "vector=0.5, text=0.3, graph=0.2", but `result_lists` holds only the legs that ran, in order.
- Impact: a text-only call with graph expansion weights text 0.5 and graph 0.3, not 0.3 and 0.2; the weights the
  comment promises are applied only when all three legs ran.
- What would close it: map default weights from `search_modes`.

### F-0711 `TextSearchEngine` answers across graphs and cannot reach iFind
- Evidence: `iris_vector_graph/text_search.py:96-255`: `search_entity_qualifiers`, `extract_entity_names` and
  `search_with_context` read `rdf_edges`, `rdf_props` and `rdf_labels` with no `graph_id` predicate (and the label
  join is on `s` alone). `search_documents` (`:31-66`) uses `WHERE %FIND(text, ?)` and `%FIND.RANK()`, which
  `tests/unit/test_ifind_and_fusion_sql.py` documents as not IRIS syntax (SQLCODE -359), and reads `FROM docs`
  unqualified, which resolves in the connection's default schema, where spec 262 left no IVG views; its fallback reads
  the same table and returns `[]` on any error.
- Impact: an exported class (`iris_vector_graph/__init__.py:93,124`) returns other graphs' nodes, labels and edges,
  against SYS-I2, and its document search always answers from the fallback or not at all.
- What would close it: decision HD-0705; then a graph argument and predicate on every query, the
  `%ID %FIND search_index(...)` predicate, and the schema-qualified table.

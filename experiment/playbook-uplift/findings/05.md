# Findings: 05 Temporal edges and the temporal index

Every finding here comes from reading code and tests at pin `3eaa79cf`. None was run in this uplift; each says what
would close it.

### F-0501 An update-mode write counts its edge again in the bucket aggregate
- Evidence: `iris_src/src/Graph/KG/TemporalIndex.cls:82-83` (mode "update" kills `edgeprop` and skips the collision
  check), then `:100-124` run for every write: `$Increment(^KG("bucket", g, b, s))`, `$Increment(... "count")`,
  `$Increment(... "sum"), w`, and min/max fold in the new weight. The comment at `:77-79` and the docstring at
  `iris_vector_graph/_engine/temporal.py:273-278` say the aggregates "remain based on the original value"; they do
  not: after one update the bucket counts two edges and sums both weights while `^KG("tout")` holds one.
  `tests/e2e/test_254_collisions_e2e.py::test_update_is_unchanged` checks the weight and the attributes through a
  window that cuts the bucket (read edge by edge, `TemporalIndex.cls:1469-1485`), so it never reads the aggregate.
- Impact: `get_temporal_aggregate`, `get_bucket_groups`, velocity and bursts over whole buckets over-count after any
  upsert; a window that cuts the bucket answers differently from one that holds it whole. Deleting the edge later
  decrements the bucket counter once, leaving a counter of 1 for a bucket with no edge (`:357-358`).
- What would close it: a live test that writes, updates the same coordinates, and asserts the whole-bucket count is 1
  and the sum equals the new weight; then make "update" subtract the old weight (or rebuild the bucket with
  `RebuildBucketAggregate`), or document the double count as the contract (CONTEXT.md:173-177 says an upsert
  "replaces the edge").

### F-0502 A temporal write with no time lands at epoch 0, not at the current time
- Evidence: `create_edge_temporal(..., timestamp=None)` sends `int(timestamp) if timestamp is not None else 0`
  (`iris_vector_graph/_engine/temporal.py:292-299`) and the store sends `str(timestamp)`, i.e. `"0"`
  (`iris_vector_graph/stores/iris_sql_store.py:2680`). `InsertEdge` defaults only `""` to now
  (`TemporalIndex.cls:51`), so the edge is stored at ts 0. The batch path does the opposite: `If ts = 0 Set ts = now`
  (`TemporalIndex.cls:170`), so a caller who really means epoch 0 gets the current time.
- Impact: a caller who leaves out the time gets an event in 1970, invisible to recent windows, velocity and bursts,
  and immediately eligible for any retention purge; the two write paths disagree about what 0 means.
- What would close it: send `""` for a missing timestamp (or compute now in Python), stop treating an explicit 0 as
  "missing" in `BulkInsertCounts`, and add a test for each path.

### F-0503 A temporal write can create node rows that the ledger never records
- Evidence: with the adjacency index, `WriteStores` calls `Adjacency.AssertTemporalRow`
  (`TemporalIndex.cls:109-111`), which inserts `Graph_KG.nodes` rows for missing endpoints
  (`iris_src/src/Graph/KG/Adjacency.cls:591-602`). Neither the engine path nor `LedgerApply.OpCreateTemporalEdge`
  (`LedgerApply.cls:617-641`) writes a `create_node` record. `verify` reads every node row
  (`iris_vector_graph/ledger/replay.py:590-597`) and only skips marked edge rows (`:617-620`). The ledger tests use
  endpoints that already exist (`tests/integration/test_ledger_us11_temporal_coexist.py`, fixture creates a and b;
  `tests/e2e/test_460_ledger_temporal_edge_e2e.py` creates both nodes first), so none covers a new endpoint.
- Impact: on a ledger-enabled namespace, a temporal edge to a new id (and a changeset temporal op whose target has no
  node op, as in `test_224_temporal_changeset_e2e.py::test_temporal_op_in_diff`) should make `verify()` answer
  `diverges` with an unrecorded node; strict mode does not stop it (TMP-B12.6).
- What would close it: a live test on a ledger-enabled namespace that writes a temporal edge to an unseen id and runs
  `verify()`; then the decision HD-0501.

### F-0504 Purges and the row drop delete node rows without the strict-mode check or a record
- Evidence: `purge_before` and `purge_raw_before` (`iris_vector_graph/_engine/temporal.py:623-685`,
  `iris_vector_graph/stores/iris_sql_store.py:2798-2814`) and `drop_temporal_structural_rows` (`temporal.py:760-809`)
  default to retiring bare nodes (`TemporalIndex.cls:1020-1042`, `TemporalPolicy.cls:205-207`) through
  `Graph.KG.Eraser.RetireBareNodes`, a SQL delete of `Graph_KG.nodes`. None calls the ledger guard. The sweep they
  share a rule with, `erase_bare_nodes`, does (`iris_sql_store.py:2823-2825`).
- Impact: in strict mode a purge deletes governed node rows that `delete_node` would be refused for; with the ledger
  on, a node a changeset created with nothing else on it, and used as a temporal endpoint, can disappear without a
  record, and `verify()` reports it.
- What would close it: decide whether node retirement is a structural write (guard it, as `erase_bare_nodes` is) or
  excluded by rule (skip nodes the ledger knows), and test it on a strict ledger.

### F-0505 The marker test differs between the deleters and the ledger
- Evidence: `Adjacency.IsTemporalMarked` answers 1 when `tObj.%Get("temporal") = 1`
  (`iris_src/src/Graph/KG/Adjacency.cls:735-748`), true for JSON `true`, the number `1` and the string `"1"`.
  `LedgerGenesis.TemporalMarked` requires a JSON boolean (`LedgerGenesis.cls:62-75`, whose comment says "a qualifier
  temporal of 1 or "true" is an ordinary qualifier"), as do `replay.read_canonical` (`replay.py:617`) and
  `create_edge`'s adopt (`nodes_edges.py:1297`). `RetractTemporalRow` (last-time delete, purge fallback) and
  `DropRows` pass 2 use `IsTemporalMarked`.
- Impact: an explicit edge whose qualifiers hold `temporal: 1` is governed by the ledger, yet the last temporal delete
  on its triple, or a drop, deletes it.
- What would close it: one shared predicate (JSON boolean true) and a test with `qualifiers={"temporal": 1}`.

### F-0506 Without the adjacency index, the Python mirror writes an unmarked row for any predicate
- Evidence: when `_adjacency_indexed` is false and `graph` is given, `create_edge_temporal` and
  `bulk_create_edges_temporal` insert an `rdf_edges` row with no qualifiers and its two nodes
  (`iris_vector_graph/_engine/temporal.py:309-331`, `:453-475`). They do not read the opt-out list, while the server
  skips even the shadow for a temporal-only predicate (`TemporalIndex.cls:108-115`). ADR-0015 says an opted-out
  predicate writes "nothing else"; ADR-0009 says the row a temporal write asserts is marked.
- Impact: on such a namespace the row looks explicit: no purge or delete removes it, the ledger governs it (verify
  reports it as unrecorded), and a temporal-only predicate still grows rows and nodes in named graphs.
- What would close it: write the marker and honour the registry in the mirror (or drop the mirror now that setup
  declares the index), with a unit test.

### F-0507 TemporalIndex.Purge wipes every graph's temporal index and leaves the marked rows
- Evidence: `Purge()` is `Do ..EraseAll()` (`TemporalIndex.cls:808-811`), which kills `tout`, `tin`, `bucket`,
  `tagg`, `edgeprop` and `tlast` for every graph (`:379-391`) and touches no row. The ADR-0009 amendment says the
  marked row goes when the triple's last timestamp goes, "in every graph". The `create_edge_temporal` docstring
  (`iris_vector_graph/_engine/temporal.py:273-278`) tells callers to "call Purge() and rebuild" to fix aggregates;
  there is no public aggregate rebuild (`RebuildBucket` is private, `:1259`).
- Impact: marked rows and their `^KG("out"/"in")` entries outlive their timestamps; no later purge can find them (no
  timestamp names them), so only `drop_temporal_structural_rows` or a manual delete removes them. A caller following
  the docstring erases all temporal data of all graphs.
- What would close it: retire the marked rows in `Purge` (or remove it), fix the docstring, and test it.

### F-0508 find_burst_nodes accepts a predicate and ignores it
- Evidence: `FindBursts` reads `^KG("bucket", g, b, node)`, which has no predicate level, and never reads its
  `predicate` argument (`TemporalIndex.cls:772-806`). The docstring's Args says "predicate: Filter to edges with this
  predicate" while its first paragraph says it "filters nothing" (`temporal.py:893-897`).
- Impact: a caller filtering bursts by edge type gets every type counted.
- What would close it: remove the argument (or read `tagg` counts per predicate) and make the docstring agree.

### F-0509 InternLabelSet's canonical form is not valid JSON for some inputs
- Evidence: keys and string values are wrapped in quotes without escaping (`TemporalIndex.cls:1366`, `:1375`); an
  object or array value falls through to the string branch and is written as an object reference; `%FromJSON` throws
  on invalid input instead of returning `""` as the comment at `:1337` says.
- Impact: a label set with a quote or backslash resolves to text that is not JSON; nested values intern under a hash
  that depends on the process's object references, so the same set can get different hashes.
- What would close it: build the canonical form with `$ZConvert(, "O", "JSON")` and recursion, catch the parse error,
  and add unit cases (spec 204 FR-012).

### F-0510 The millisecond index computes "now" in seconds
- Evidence: `TemporalIndexMS` changes only `TSUNIT` and `BUCKETMS` (`TemporalIndexMS.cls:7-9`). The inherited
  defaults use `DATEDIFF("ss", ...)`: `InsertEdge` (`TemporalIndex.cls:51`), `BulkInsertCounts` (`:170`),
  `GetVelocity` (`:760-761`), `FindBursts` (`:775-776`).
- Impact: a millisecond write with no time lands about 1.7 billion ms (about 20 days after 1970); velocity and bursts
  with no `nowTs` look at the wrong buckets.
- What would close it: scale "now" by 1000 when `TSUNIT="ms"` and test it.

### F-0511 A changeset's insert-mode temporal op is recorded even when it collides
- Evidence: `Changeset.create_temporal_edge` documents `"insert"` as "fail if key exists"
  (`iris_vector_graph/ledger/changeset.py:334-335`). `OpCreateTemporalEdge` calls `InsertEdge`, which returns 1 for a
  collision (`TemporalIndex.cls:62-64`), and then always writes a `create_temporal_edge` record
  (`LedgerApply.cls:634-640`). The record also omits weight, attributes and mode.
- Impact: the history claims a write that changed nothing, and cannot say which weight an edge had.
- What would close it: return the collision from `WriteStores` to `LedgerApply`, refuse or skip the record, and fix
  the docstring; decide under HD-0502 whether the record should carry the weight.

### F-0512 The batch field that suppresses the reverse index is not the one spec 204 names
- Evidence: spec 204 FR-009 (`specs/204-temporal-index-gaps/spec.md:185`) names `suppress_reverse`; `BulkInsertCounts`
  reads `"sri"` (`TemporalIndex.cls:173`). The Python store sends `"sri"` (`iris_sql_store.py:2734-2735`).
- Impact: an ObjectScript caller following the spec writes the reverse index it meant to skip; nothing reports it.
- What would close it: accept both names, or amend the spec.

### F-0513 Temporal writes validate their input on one path only
- Evidence: `create_edge_temporal` runs `TemporalEdgeInput` (timestamp >= 0, weight >= 0, non-empty names) only when
  a timestamp is given (`temporal.py:289-291`, `_validate.py:207-227`). `bulk_create_edges_temporal` checks presence
  and keys only (`temporal.py:138-154`). `delete_edge_temporal` always validates (`:370-373`).
- Impact: a negative weight or time is refused on one path and stored on the others.
- What would close it: validate every edge on every path, with a unit test per path.

### F-0514 The Python structural-row migration cannot read a large graph
- Evidence: `_temporal_triples` reads the whole graph with `get_edges_in_window(start=0, end=9999999999)`
  (`iris_vector_graph/migrations/temporal_structural_rows.py:55-63`), which raises past about 35 k edges
  (`iris_vector_graph/_engine/temporal.py:502-504`, `:518-524`). The module docstring does not say so.
- Impact: the migration fails on exactly the graphs that need it most; the ObjectScript backfill
  (`TemporalIndex.BackfillRows`) does not have the limit.
- What would close it: read with `iter_edges_in_window`, or call `backfill_temporal_structural_rows`, and test with a
  window past the cap.

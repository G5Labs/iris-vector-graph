# Findings of module 08 (Cypher on the SQL path)

Cited from `ontology/08-cypher-sql.md` as `finding:F-08kk`. Paths are at pin `3eaa79cf`. Q = `iris_vector_graph/_engine/query.py`,
T = `iris_vector_graph/cypher/translator.py`, S = `iris_vector_graph/stores/iris_sql_store.py`. Nothing here was run
against IRIS. "Translated in memory" means the pure-Python parser and translator were called with `python3 -I` and no
IRIS connection, to see the SQL text they produce; no test suite was run. None of these findings is closed by this
uplift.

### F-0801 Ledger strict mode is a cached client check that fails open
- Evidence: `iris_vector_graph/ledger/guard.py:20` (`TTL_SECONDS = 5.0`), `:38-59` (probe cached per engine; any
  exception gives "never-enabled"), `:75-80`; `iris_vector_graph/_engine/ledger.py:72-80` (no guard: no-op);
  `iris_src/src/Graph/KG/Ledger.cls:360-381` (SetStrict only sets meta). Unit tests assert both behaviours:
  `tests/unit/test_ledger_guard.py::test_cache_honours_ttl_and_refresh` ("still cached → no raise") and
  `::test_probe_failure_fails_open`. The contract `specs/213-graph-revision-ledger/contracts/ledger-api.md:82-92`
  says the guarded calls "raise `LedgerStrictModeError` and change nothing".
- Impact: for up to 5 s after another process turns strict mode on, and whenever the probe fails (privilege refused,
  class missing, Native API down), a Cypher write runs and is not recorded. The erasure/redaction modules cannot
  assume that, in strict mode, every change to the graph tables has a ledger record.
- What would close it: decision HD-0801, then either documenting the window and fail-open in the contract and
  USER_GUIDE, or a fail-closed / server-side check with a live test of a second process.

### F-0802 Text shortcuts answer by substring and ignore USE GRAPH
- Evidence: Q:1809-1827 (`"CALL DB.LABELS() YIELD"` and `"UNION"` anywhere), Q:1829-1839 (`"RETURN DISTINCT"`,
  `"UNION ALL"` and `"ENTITY"` anywhere: answers `TOP 25` node ids and `TOP 25` edge types of the whole namespace),
  Q:1841-1856 (`"MATCH ()"`, `"COUNT(*)"`, `"UNION ALL"`: answers whole-table counts as `[{"name":..., "data":...}]`
  under one column `result`). The text is upper-cased first (Q:1807), so `entity` in a property name or alias
  matches. No graph predicate in any of the three. Tests only assert the type of the answer
  (`tests/integration/test_query_special_patterns.py::test_count_union_all_pattern`, `::test_entity_union_all_pattern`;
  `tests/unit/test_query_unit.py::test_match_count_union_all`).
- Impact: a legitimate query such as `USE GRAPH 'g' MATCH (n) RETURN count(*) AS c UNION ALL MATCH ()-[r]->() RETURN
  count(*) AS c`, or any `RETURN DISTINCT ... UNION ALL ...` touching an `entity_*` name, gets a canned answer of
  another shape, from every graph. That breaks CONTEXT.md:27-43 (graph isolation) and returns another tenant's ids.
- What would close it: match the exact Neo4j Browser / Bloom texts (or parse first and compare the AST), honour
  `USE GRAPH`, and a test that a near-miss query is answered by the translator.

### F-0803 A WHERE after RETURN is parsed and dropped
- Evidence: `iris_vector_graph/cypher/parser.py:287-291` eats `WHERE`, calls `parse_expression()` and discards it,
  then accepts a further RETURN as a chained part. `MATCH (n) RETURN n WHERE false` parses with no filter (reported by
  a survey that ran the parser in memory). `tests/unit/test_lexer_parser_coverage.py::test_standalone_where_return`
  asserts nothing (it swallows any exception).
- Impact: a filter the caller wrote is silently not applied; rows come back that the caller excluded. openCypher
  refuses this text.
- What would close it: raise CypherParseError for WHERE after RETURN (or apply it), with a unit test.

### F-0804 Lexer errors are Python SyntaxError, not CypherParseError
- Evidence: `iris_vector_graph/cypher/lexer.py:229-232`, `:267-270`, `:311-314`, `:394-397` raise `SyntaxError`;
  `CypherParseError` (`parser.py:18`) derives from `Exception`, not from `SyntaxError`. USER_GUIDE.md:313 says "A
  query that does not parse raises `CypherParseError`". A `;` outside the CALL split path (Q:1858) reaches the lexer.
- Impact: `except CypherParseError` misses an unknown character, an unclosed string or a stray `;`; the same
  `SyntaxError` type is also used for "parses but invalid" (USER_GUIDE.md:313-316), so the two cases cannot be told
  apart by type.
- What would close it: raise CypherParseError (or a subclass) from the lexer, or document both types.

### F-0805 A duplicate edge CREATE between literal endpoints fails instead of adding nothing
- Evidence: T:10212-10248 (both endpoint ids literal: `INSERT INTO rdf_edges ... VALUES (...)`, no `NOT EXISTS`
  guard) against T:10306-10365 (matched endpoints: guarded). The e2e test
  `tests/e2e/test_234_multigraph_cypher_e2e.py::test_mode_off_never_makes_a_second_edge` says in its comment that the
  unique key refuses the second INSERT (-119) and the statement rolls back, and asserts no edge remains after
  `CREATE (a:MgA), (b:MgB) CREATE (a)-[:MG_T]->(b) CREATE (a)-[:MG_T]->(b)`, with the error suppressed. KNOWN_ISSUES.md:25-31
  says such a CREATE "returns no error and writes nothing" and that -119 was "early 4.0 builds" only.
- Impact: outside multigraph mode, a query that creates the same edge twice, or creates an edge that exists between
  nodes named by literal id, raises GraphWriteError and loses all of its other writes; the documented behaviour is a
  silent no-op for that edge only.
- What would close it: guard the literal-endpoint INSERT as the matched path does, or correct KNOWN_ISSUES; a live
  test for `CREATE ({id:'a'})-[:R]->({id:'b'})` over an existing edge.

### F-0806 A stepped write's error message says earlier steps are kept
- Evidence: Q:1692-1705 (`_raise_if_step_failed`): the docstring says an earlier step "has written (and committed)
  its rows", and the message adds "the rows of the steps before it are written". Since 4.6.4 every write query runs
  in one `write_txn` that rolls back on any exception (Q:1946-1962), as USER_GUIDE.md:266-271 says.
- Impact: a caller told that rows remain may try to clean up or retry partially, against a graph that is unchanged.
- What would close it: drop the `left` text (or say "nothing written"), with a unit test of the message.

### F-0807 Some refused writes raise ValueError or SyntaxError, not GraphWriteError
- Evidence: Q:1980-1985 (count-only CREATE over 100,000 rows: `ValueError`), T:11513-11519 (MERGE on a null:
  `ValueError`), T:11382-11404 and T:11103-11120 (MERGE SET refusals: `SyntaxError`), T:13795-13799. USER_GUIDE.md:317-318
  and the `execute_cypher` docstring (Q:1756-1758) say a write IRIS or IVG refuses raises GraphWriteError.
- Impact: a caller that catches GraphWriteError to detect a refused write misses these; nothing is written in any of
  them (the write transaction rolls back), so the effect is on error handling only.
- What would close it: wrap translator refusals of writes in GraphWriteError (keeping the cause), or list the other
  types in USER_GUIDE, Errors.

### F-0808 FOREACH over a parameter or variable list does not run per item
- Evidence: T:3949-3963 unrolls only a literal list; T:3964-3967 runs the body once with the loop variable unbound for
  any other source. `_bind_literal_params` (T:7262-7307) binds a parameter only inside a list or map literal, so
  `FOREACH (x IN $list | ...)` keeps a bare parameter. No test pins the outcome (the touching tests swallow
  exceptions or check only the result type, per the survey); not observed live.
- Impact: openCypher runs the body once per element; here the body runs once with `x` unbound, which either raises
  or writes something other than asked.
- What would close it: bind a parameter source before translation (as UNWIND does), and a live test.

### F-0809 MERGE ON CREATE SET / ON MATCH SET values frozen for 4.7.1
- Evidence: KNOWN_ISSUES.md:131-142 and CHANGELOG.md:274: `ON MATCH SET n.s = size(n.id)` fails SQLCODE -23; in a
  pattern MERGE `ON CREATE SET a.c = a.count + 1` answers `<ARGUMENT ERROR>`; `ON MATCH SET n.v = 1 / 0` raises -149
  on a node the MERGE creates. Code: T:12062-12451.
- Impact: documented; the workaround is a SET after the MERGE. Planned for 4.7.1.
- What would close it: the 4.7.1 fix with live tests per shape.

### F-0810 SET n.p = null keeps the key
- Evidence: T:13655-13665 (literal null: `UPDATE ... SET val = NULL` and an INSERT of NULL, no DELETE); a computed
  null is deleted (T:13648-13654). KNOWN_ISSUES.md:144-152 (planned 4.7.1). The e2e test
  `tests/e2e/test_470_set_null_e2e.py::test_a_null_value_removes_the_property` covers computed nulls only, though its
  module docstring says a literal null removes the property.
- Impact: `keys(n)` lists the key and `properties(n)` answers `''` for it; openCypher removes it.
- What would close it: delete the row for a literal null too; a live test of `keys(n)` after `SET n.z = null`.

### F-0811 RETURN r.p of an edge number past 64 bits answers an integer
- Evidence: `iris_vector_graph/prop_values.py:141-168` (`parse_rel_prop_text` turns any canonical integer text into
  `int`, line 165, with no 64-bit cap; `decode_typed_text` caps at 224-230). KNOWN_ISSUES.md:163-170 (planned 4.7.1).
  `tests/unit/test_470_json_int64_decode.py` covers the capped path only.
- Impact: after `SET r.p = 1e20`, `RETURN r.p` answers `100000000000000000000` where openCypher answers `1e+20`.
- What would close it: cap the relationship reader as the node reader is capped; a unit test on `parse_rel_prop_text`.

### F-0812 A whole-number result of SET arithmetic reads back as an integer
- Evidence: KNOWN_ISSUES.md:154-161 (planned 4.7.1): `SET n.w = n.w * 1.5` over `w: 2` stores `3`; on an edge
  `SET r.w = r.w * 1.5` and `SET r.w = $v` with `3.0` too. Code path T:13784-13887.
- Impact: a float reads back as an integer; comparisons are unaffected.
- What would close it: keep the float type through the SET writer; a live test.

### F-0813 Values carry no stored type (typed storage planned for 4.8.0)
- Evidence: T:10232-10238 and T:465-504 (a Cypher edge number is stored as a JSON string); KNOWN_ISSUES.md:118-130,
  183-240 (edge number filters match strings, `ORDER BY` sorts number-like strings as numbers, arithmetic reads
  number-like strings as numbers), :332-368 (a string spelling a boolean, list or map reads as one), :305-330 (a
  ledger-written value is stored as text).
- Impact: answers differ from openCypher for mixed-type data; documented with workarounds. Node filters read the stored
  type from 4.7.0.
- What would close it: typed storage (4.8.0) and the TCK typed runs on mixed data.

### F-0814 AQL text values are pasted into the Cypher text, and execute_aql ignores read-only
- Evidence: `iris_vector_graph/cypher/aql/translator.py:50-58` (`AQLLiteral` string → `f'"{v}"'`, no escaping) and
  `:166-168` (collection names joined into the relationship type). Q:1730-1745 (`execute_aql` has no `read_only`
  argument and calls `execute_cypher` with defaults). A survey translated in memory a string `x" OR true OR "` that
  changed the filter, and a collection name that produced `... DETACH DELETE v ...` (`writes_cypher` True).
- Impact: AQL input that reaches `execute_aql` from a user can change the query's logic or write (delete) data, and
  no read-only setting stops it at the engine level. The servers' read-only checks apply only if they check the
  Cypher text, not the AQL.
- What would close it: send every AQL literal as a query parameter, validate collection names as identifiers, add
  `read_only` to `execute_aql`, and unit tests with hostile literals.

### F-0815 A dotted function name pastes raw text into the SQL
- Evidence: `iris_vector_graph/cypher/parser.py:1627-1640` builds `name.fn` from two identifier tokens, and a
  back-quoted identifier may hold any character but a back quote (`lexer.py:257-275`); T:29563-29567 lets a dotted
  name past the UnknownFunction check and T:29578 emits `f"{sql_fn}({args})"` with `sql_fn = fn.upper()`.
  Translated in memory: `` RETURN `x(1) AS a, (SELECT 1) AS b --`.f(1) AS v `` gives the SQL
  `SELECT X(1) AS A, (SELECT 1) AS B --.F(1) AS v`. `tests/unit/test_cypher_posos_bugs.py::test_qualified_function_uppercased`
  asserts the pass-through (`SQLUser.someCustomFn(...)`), and the behaviour is not in USER_GUIDE.
- Impact: any caller who can send Cypher text, including through a read-only server, can run arbitrary SQL
  expressions in the SELECT: read tables outside the graph tables and other graphs regardless of `USE GRAPH`, or call
  SQL functions with side effects (for example `Graph_KG.Txn_Begin` / `Txn_Undo`), none of which read-only mode
  refuses (it judges clauses only). P-0806 bounds this to one statement. Not observed on IRIS.
- What would close it: refuse a back-quoted or non-identifier namespace in a function call, allow-list qualified
  functions (or require a setting to enable them), refuse them in read-only mode, and unit tests with hostile names.

### F-0816 Schema procedures ignore USE GRAPH
- Evidence: `iris_vector_graph/engine.py:1313-1318` (`db.labels`: `SELECT DISTINCT label FROM rdf_labels`),
  `:1321-1323` (`db.relationshipTypes`), `:1489-1491` (`db.propertyKeys`), `:1617-1619` (`apoc.meta.data`); the
  dispatcher passes `graph=` only to handlers that declare it (`:1702-1714`) and these do not. USER_GUIDE.md:401-404
  says `USE GRAPH` scopes a query to one graph.
- Impact: under `USE GRAPH 'tenantA'`, `CALL db.labels()` lists every tenant's labels, edge types and property keys
  (metadata leak across graphs).
- What would close it: give the schema handlers a `graph` parameter (or refuse them under USE GRAPH), with a unit test.

### F-0817 An unknown db, dbms or apoc procedure answers no rows
- Evidence: `iris_vector_graph/engine.py:1716-1720` returns `IVGResult(columns=["value"], rows=[])` for any
  unregistered `apoc.*`, `db.*` or `dbms.*` name; an unknown `ivg.*` name raises (T:2266-2270) and an unknown `gds.*`
  answers `IVGResult.error` (Q:686-695).
- Impact: a misspelt procedure reads as "nothing found"; three behaviours for one condition.
- What would close it: raise for every unknown name (openCypher ProcedureNotFound), with a unit test.

### F-0818 A variable-length walk in an all-graphs read can cross graphs
- Evidence: T:15404-15431: with no `USE GRAPH`, the walk is confined to the start node's graph only when the start is
  a plain node alias (`n<k>.node_id`) and graphs are correlated; any other start (a WITH-carried value, an UNWIND id,
  a parameter) passes `gall = 1`, and `CY_VLP_PATHS` / `CY_VLP_ENDS` then drop the `graph_id` test
  (`iris_vector_graph/schema.py:2390`). The code comment says the single walk "let an edge of g1 continue from g2's
  node of the same id". Not observed live; KNOWN_ISSUES does not list it.
- Impact: an all-graphs read can return paths that mix two graphs' edges through a shared id, against CONTEXT.md:38-43
  ("an edge meets only nodes of its own graph"); across tenants, that joins their data.
- What would close it: carry the start's graph into the walk for every start shape (or refuse the shape), and an e2e
  test with a WITH-carried start in two graphs.

### F-0819 approx_count_distinct in an all-graphs read merges graphs
- Evidence: Q:4361-4407 (the HLL route calls `Graph.KG.NKGAccel.CountDistinctKHop` over `^NKG`); Q:4420-4421 refuses
  the route only under `USE GRAPH`. `^NKG` has no graph key (CONTEXT.md, Interned snapshot; KNOWN_ISSUES.md:734-741),
  and unlike the k-hop shortcut (Q:4318-4320) there is no check for named graphs with edges. `tests/unit/test_approx_hll_read.py`
  has no several-graph case.
- Impact: with a node id used in two graphs, the estimate counts both graphs' neighbours as one graph's, and a walk can
  continue across graphs.
- What would close it: take the HLL route only when the default graph is the only graph with edges (as Q:4318 does),
  with a unit test.

### F-0820 kg_GRAPH_PATH reads every graph
- Evidence: `iris_vector_graph/_engine/algorithms.py:679-697` runs a Cypher read with no `USE GRAPH` (an all-graphs
  read) and takes no `graph` argument; `iris_vector_graph/operators.py:46-49` forwards to it. USER_GUIDE.md:462-464:
  "Python methods that write or read take `graph=`; omitted, they mean the default graph, never every graph."
- Impact: a caller of `kg_GRAPH_PATH` gets paths from every graph, across tenants.
- What would close it: add `graph=` (default: the default graph) and prefix `USE GRAPH`, with a unit test.

### F-0821 The published TCK figures cannot be tied to this repository
- Evidence: docs/dev/TCK.md:184-216 cites the typed runs at `9ca0edca` / `99514e62` and the 4.6.0 runs at `2406c7dc`
  (also `500ecd40`, `da666988`); none of them is an object in this repository (`git cat-file -t` fails). The latest
  cited full-suite runs that are ancestors of the pin are `0e69c125` and `f7a8c581` (October 2026), with 260 and 264
  commits to `iris_vector_graph/cypher` and `_engine/query.py` between them and the pin. TCK.md:191-193: no typed run on
  IRIS Community 2026.1. The 4.7.0 CHANGELOG reports area subsets (for example "TCK merge, create, set, delete,
  remove, match: 661 of 661", CHANGELOG.md:161-165), not a full run.
- Impact: "3896 / 3896" cannot be reproduced or attributed at the pin; the harness also runs with multigraph mode on
  and with queries rewritten (CYP-T16.2, CYP-T16.4).
- What would close it: a full typed run at the pin on IRIS Community and enterprise, multigraph on and off, with its
  RUN_INFO and results.tsv kept.

### F-0822 CREATE or MERGE after UNWIND $p AS e WITH e fails with SQLCODE -119
- Evidence: KNOWN_ISSUES.md:585-596; T:7044-7087 (`rewrite_ambiguous_param_unwind`), MR:258-262.
  `tests/e2e/test_470_unwind_param_rewrite_e2e.py::test_a_later_create_stores_the_element` covers the parameter
  rewrite; `tests/unit/test_470_unwind_param_rewrite.py:123` names -23 for the same shape where KNOWN_ISSUES and
  CHANGELOG.md:154 name -119.
- Impact: documented; workaround is UNWIND without the WITH.
- What would close it: a fix with a live test, and one SQLCODE in the docs and tests.

### F-0823 An aggregate in a CALL subquery that matches nothing answers 0
- Evidence: T:14543: `context.select_items.append(f"COALESCE(({scalar_sql}), 0) AS {alias}")` for every correlated
  scalar subquery, whatever its aggregate. No test covers an empty `max`, `avg` or `collect`; not observed live.
- Impact: `CALL { WITH a MATCH (a)-[:R]->(q) RETURN max(q.v) AS m }` answers 0 where openCypher answers null, and
  `collect` 0 where it answers `[]`. `count` is right.
- What would close it: COALESCE only for `count`, and a live test per aggregate.

### F-0824 Two slashes inside an AQL string start a comment
- Evidence: `iris_vector_graph/cypher/aql/lexer.py:46-63` (`_strip_comments` scans for `//` and `/*` without regard to
  quotes). A survey's in-memory run of `'http://x'` gave AQLParseError "Expected RETURN".
- Impact: an AQL query holding a URL or a path is refused or cut.
- What would close it: strip comments in the tokenizer, outside strings; a unit test.

### F-0825 An expression the translator does not handle becomes SQL NULL
- Evidence: T:29676-29756: `translate_expression` falls through to `return "NULL"` (T:29756) for an AST node type it
  has no branch for, with no error and no warning.
- Impact: a new or rare expression kind silently answers null (and a filter on it matches nothing) instead of raising.
  Which inputs reach the fall-through today was not determined.
- What would close it: raise a translation error at the fall-through, and run the TCK and unit suites to find any
  shape that relied on it.

# Trust: module 11 (ledger core)

Premises the LED statements rely on, beyond the system premises P-0001 to P-0004 in `TRUST.md` (which LED cites
directly). None is checked by this uplift; each says what would check it.

### P-1101 SQL writes made inside an open ObjectScript transaction belong to it
- Statement: DML run with `%SQL.Statement.%ExecDirect` while `$TLEVEL > 0` (as `Graph.KG.LedgerApply.Run` does inside
  `Graph.KG.Ledger.Commit`'s `TSTART`) is part of that transaction: `TROLLBACK 1` takes the rows back with the
  `^IVG.Ledger` and `^KG` global sets, and the rows become durable only at the outermost `TCOMMIT`.
- Used by: LED-P1, LED-I1, LED-B4 (a commit saves all of a changeset or nothing across SQL tables and globals).
- Check: upstream live tests `tests/integration/test_ledger_us02_rollback.py::test_failing_op_mid_changeset_leaves_everything_unchanged`
  and `tests/integration/test_ledger_store_failures.py::test_a_refused_insert_fails_the_whole_commit` assert the
  outcome (not run here).

### P-1102 Nested transaction levels behave as the 4.7.0 commit assumes
- Statement: `TCOMMIT` at a nested level only lowers `$TLEVEL`; `TROLLBACK 1` undoes only the innermost level and
  leaves the levels below it open; the outermost `TCOMMIT`/`ROLLBACK` decides for every level. SQL `COMMIT` and
  `ROLLBACK` end every level (`iris_vector_graph/_write_txn.py:13-18`, measured upstream on IRIS 2026.3).
- Used by: LED-P2, LED-B9.2, LED-B9.6 (a commit nested in a caller transaction).
- Check: upstream live test `tests/e2e/test_470_ledger_caller_txn_e2e.py::test_a_caller_rollback_takes_back_the_revision_and_its_writes`
  (not run here).

### P-1103 An object opened by %OpenId holds no lock until %Save, and %Save writes the whole row
- Statement: `Graph.KG.LedgerStats.Ensure()` opens the stats row with `%OpenId` at the class's default concurrency;
  no lock is held between the open and the `%Save`, and `%Save` writes every property of the row (one `$List` data
  node), so two processes that read-modify-write it can overwrite each other's increments. A transaction rollback
  restores a global node's before-image even when another process changed the node after it.
- Used by: LED-P3, LED-I3 and finding F-1102 (lost counter updates).
- Check: documentation only; a live test with two processes bumping `rej_lock_timeout` while a third commits in a
  caller transaction that it then rolls back would check it.

### P-1104 The fingerprint a caller sends matches its payload
- Statement: `Graph.KG.Ledger.CommitInTxn` compares the `fingerprint` in the commit's meta JSON with the one bound to
  the retry key; it never computes a fingerprint from the payload. Callers reach `Commit` through
  `iris_vector_graph.ledger.client.GraphLedger`, which sends `Changeset.fingerprint()`.
- Used by: LED-P4, LED-B4.7 (a retry is matched by key and fingerprint).
- Check: none possible in code: `Graph.KG.Ledger.Commit` is a public class method any user with EXECUTE can call
  with any fingerprint. Holds only while every writer goes through the Python client.

### P-1105 Only trusted code writes the ledger globals
- Statement: `^IVG.Ledger` (records, statement and tuple maps, retry keys, head) has no trigger or other guard; the
  immutability rules of `Graph.KG.LedgerRevision` cover the revision table only. Database-level write access to the
  namespace's globals database is limited to the product's code and its operators.
- Used by: LED-P5, LED-I2 (records never change except by redaction).
- Check: deployment review of the database resource and roles (docs/ADMIN_GUIDE.md "privileges" section); not
  checkable from the code.

### P-1106 Saving a second revision row with an existing seq fails
- Statement: `Graph.KG.LedgerRevision` has `Index SeqIdx On Seq [ IdKey, Unique ]`; `%Save` of a new object whose seq
  is already stored returns an error status (ID key not unique) and writes nothing.
- Used by: LED-P6 and finding F-1104 (the second of two concurrent first enables fails with an inconsistency).
- Check: documentation only; a live test that runs two `Enable()` calls on a never-enabled ledger at once would check
  the outcome.

### P-1107 A class call made through the caller's own connection runs on the caller's server process
- Statement: `iris.createIRIS(conn)` on the DB-API connection itself (`WriteTxn.native()`), and IRIS embedded calls,
  run class methods in the same IRIS process as that connection's SQL, so an ObjectScript `TSTART` there nests in the
  caller's transaction. A Native API object built on a separate connection (`from_connect`, `engine._iris_obj()` with
  stored credentials) runs in another process.
- Used by: LED-P7, LED-B9.3, LED-B9.11 and decision HD-1102.
- Check: upstream live test `tests/e2e/test_470_ledger_caller_txn_e2e.py::test_the_head_lock_is_held_until_the_callers_transaction_ends`
  (not run here).

### P-1108 The revision table's row triggers fire for every ordinary SQL update and delete
- Statement: `RejectUpdate` and `RejectDelete` (`Foreach = row/object`) run for each SQL `UPDATE` and `DELETE` of
  `ledger_revisions`. Not checked here: whether `DELETE %NOTRIGGER` (needs the `%NOTRIGGER` privilege) or
  `TRUNCATE TABLE` bypass them on the deployed IRIS build.
- Used by: LED-P8, LED-B7.1, LED-B7.2.
- Check: upstream live test `tests/integration/test_ledger_us01_commit_head.py::test_revisions_are_immutable_via_sql`
  covers plain UPDATE and DELETE (not run here); `%NOTRIGGER` and `TRUNCATE` are unchecked.

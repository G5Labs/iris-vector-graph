# Decisions of module 04 (ADJ, adjacency)

### HD-0401 How should erase and rebuild retire a source generation?
- Owner: human
- Question: the degree cache's reader protocol (ADR-0012, `Graph.KG.Adj.Degree`) assumes a source generation only moves
  forward. `Adjacency.RemoveSource`, `RemoveGraph` and `RemoveAll` kill `^KG("gen")` instead, so a generation can return
  to a value an in-flight reader already read (finding F-0401). Which rule should hold?
- Options:
  - A. Keep killing the generation (no residue for an erased node) and accept the narrow window, documented.
  - B. Step the generation with `$Increment` and kill only `^KG("degc")` (a counter per erased source stays behind; it
    survives a rollback, which only makes entries stale).
  - C. Keep the kill but add a namespace-wide epoch, stepped by every kill, to each cache entry and to the reader's check.
- Default the code applies today: A (`Adjacency.cls:376-377`, `437-438`, `461-462`; the comment at `Adj.cls:46-48`
  covers an old entry, not an in-flight reader).

### HD-0402 May two adjacency rebuilds run at the same time?
- Owner: human
- Question: `TraversalBuild.BuildKG` takes the writer lock on the parent name in shared mode (`Adjacency.BeginRebuild`),
  which keeps readers from caching but does not keep a second `BuildKG` out. Only the interned snapshot's build has its
  own exclusive lock (`^IVG.NKGBuild`). `docs/ADMIN_GUIDE.md:1049-1050` says "One rebuild runs at a time", naming that
  lock. Is a second `sync()` while one runs supported (and if so, what must the result be), or should it wait or be refused?
- Options:
  - A. Allowed as today; the last full fill wins (non-indexed path: each kills and refills; indexed path: two
    `%BuildIndices` over the same rows).
  - B. Serialize: an exclusive build lock for the adjacency rebuild, like `^IVG.NKGBuild`.
  - C. Refuse the second call with a clear error.
- Default the code applies today: A, with no test of two rebuilds at once.

# Decisions: module 06 (vectors and vector search)

### HD-0601 Are the IVF, tree (VecIndex) and PLAID indexes inside the erasure promise?
- Owner: human
- Question: erasure is defined as removing a graph's content "from every store" (CONTEXT.md:198-208, ADR-0004), but
  `^IVF`, `^VecIdx` and `^PLAID` are keyed by index name only, hold no graph, and are named nowhere in
  `Graph.KG.Eraser` or the `Graph.KG.GraphStores` inventory. The 4.0.0 migration guide calls the IVF index a
  "remaining gap" (docs/migration/v4.0.0.md:742-750). After `EraseGraph(g)`, must these indexes stop answering g's
  node ids and stop holding g's vectors?
- Options: (a) record each index's source graph (IVF already records its source table) and drop or prune indexes
  built for the erased graph inside the erase; (b) declare these indexes caller-managed derived stores outside the
  erasure guarantee, say so in ADMIN_GUIDE and the inventory, and require a rebuild after erasure; (c) refuse to build
  them over a named graph.
- Default the code applies today: (b), undocumented. The indexes keep erased ids and vectors until dropped or
  rebuilt (finding F-0606).

### HD-0602 May an index build be seen half-done, and may a stopped build leave a partial index?
- Owner: human
- Question: `ivf_build` calls `Build` (which kills `^IVF(name)`), then `AddBatch` per 500 rows, then
  `FinalizeIndex`, each a separate call with no lock and no transaction; `VecIndex.Build` kills the trees and
  rebuilds them; `PLAIDSearch.Build` kills `^PLAID(name)` and refills it. A search during the build sees an empty or
  partial index, and a stopped build leaves one. Is that acceptable?
- Options: (a) build under a temporary name and swap it in at the end; (b) take a per-index lock that searches and
  inserts respect, and set a "building" marker that searches refuse; (c) keep today's behaviour and document it.
- Default the code applies today: (c), undocumented. The same question for BM25 is HD-0701.

### HD-0603 Should the vector-and-graph search keep its k best candidates?
- Owner: human
- Question: `kg_VECTOR_GRAPH_SEARCH` puts vector hits, their one-hop neighbours and text hits in a Python set, keeps
  `all_entities[:k]` (any k, set order), then sorts those k by vector similarity
  (`iris_vector_graph/_engine/vector.py:1513-1543`). The best vector hits can be dropped before the sort. The docstring
  admits "keeps k of that set in no particular order". Is that the intended contract?
- Options: (a) score every candidate and keep the top k; (b) always keep the vector hits first, then fill with
  expansion and text hits; (c) keep today's behaviour as documented.
- Default the code applies today: (c).

### HD-0604 May two embed queue workers run at once?
- Owner: human
- Question: the queue has no claim state (`ClaimPendingBatch` is "a plain ordered scan", `EmbedQueue.cls:22-25`),
  yet a namespace can run the IRIS task (`start_background_embedding`) and the Python `process_embed_queue` at the same
  time, or two Python workers. Both then process the same PENDING entries: double model calls, last writer wins on the
  vector, and status races between DONE and ERROR.
- Options: (a) add an atomic claim (status CLAIMED with owner and time, set under a lock) and make both workers use
  it; (b) refuse to start a second worker (a namespace lock held while a worker runs); (c) document single-worker as an
  operator rule (premise P-0606).
- Default the code applies today: nothing enforces it and nothing documents it to users.

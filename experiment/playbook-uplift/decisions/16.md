# Decisions for the human: module 16 (interfaces)

### HD-1601 Should a server limit which graphs a caller may name?
- Owner: human
- Question: every interface uses whatever graph a caller names (GraphQL `graph:`, the FHIR event `graph` field, the
  REST dispatcher's `graph`, `USE GRAPH` in Cypher over HTTP, Bolt and MCP). The docs say a graph ID is not a security
  boundary and tenants need separate namespaces (`docs/USER_GUIDE.md:467-468`, `docs/FHIR_GRAPH.md:553-556`), while
  `CONTEXT.md:248-250` plans an Execution Context that binds a session to one graph, and spec 256 models a tenant as a
  named graph plus an id prefix inside one namespace.
- Options: (a) keep the namespace as the only boundary and say so on every interface; (b) bind each API key to a list
  of graphs, enforced on graph fields and on `USE GRAPH`, with unscoped reads refused; (c) build the planned Execution
  Context (an authenticated principal mapped to one graph per session).
- Default the code applies today: (a). Any caller who passes the key gate (or IRIS login for the REST dispatcher and
  MCP) may read and write every graph in the namespace.

### HD-1602 Should admin work need a different key from reading?
- Owner: human
- Question: the Cypher HTTP server has one `IVG_API_KEY`. The same value that runs a read also runs
  `/admin/schema/init`, `/admin/load`, `/admin/indexes/rebuild` and `DELETE /admin/queries/{id}`, which ends any IRIS
  process the server's IRIS user may kill.
- Options: (a) one key for everything (today); (b) a second, admin-only key for `/admin/*` write methods and the kill
  route; (c) turn the kill route off unless an operator enables it.
- Default the code applies today: (a).

### HD-1603 Should the Cypher HTTP server run a failed query a second time?
- Owner: human
- Question: `_run_cypher` (`iris_vector_graph/cypher_api.py:239-250`) resets the engine and runs the query again after
  any exception, writes included. A write whose commit reached IRIS before the error (for example a dropped connection
  after commit) would then be applied twice; a refused write is attempted twice.
- Options: (a) retry every query once (today); (b) retry only reads, or only on a connection error raised before the
  statement ran; (c) never retry and return the error.
- Default the code applies today: (a).

### HD-1604 Should the REST dispatcher's `/metaPath` take a graph?
- Owner: human
- Question: `/vectorSearch` and `/hybridSearch` gained a `graph` field (spec 230 FR-014); `/metaPath` has none and
  always walks the default graph (`iris_src/src/Graph/KG/Service.cls:304-319`), though `Traversal.BFSJSON` accepts one.
- Options: (a) default graph only (today), documented; (b) read `graph` from the body as the search routes do.
- Default the code applies today: (a).

### HD-1605 Should the generated GraphQL server match the sample API's safety limits?
- Owner: human
- Question: `iris_vector_graph.gql.create_app` has the key gate but no depth limit (its `Node.outgoing` ->
  `Relationship.node` -> `Node.outgoing` nests without bound), no read-only middleware (only its `cypher` field checks),
  and a health route that always answers healthy (F-1611). The sample API has `QueryDepthLimiter` with
  `IVG_GRAPHQL_MAX_DEPTH`.
- Options: (a) leave it as an example server; (b) add the same depth limiter and health check; (c) deprecate it in
  favour of the sample API.
- Default the code applies today: (a).

# Decisions for the human: 05 Temporal edges and the temporal index

### HD-0501 Are the end nodes a temporal write creates governed by the ledger?
- Owner: human
- Question: with the adjacency index, every structural temporal write inserts its two endpoint rows into
  `Graph_KG.nodes` when they are missing (`Adjacency.AssertTemporalRow`, `Adjacency.cls:591-602`). Node rows are
  governed content: `verify()` reads every one (`replay.py:590-597`). Neither the engine path nor a changeset's
  `create_temporal_edge` op records them, and strict mode does not refuse the write. Should those nodes be recorded,
  refused, or excluded from what `verify()` compares?
- Options: (a) a changeset temporal op records `create_node` for the endpoints it creates, and the engine path in
  strict mode refuses a temporal write whose endpoints are missing; (b) endpoints a temporal write created are
  derived like the marked row: mark them (a column or a registry) and leave them out of genesis and `verify()`;
  (c) a temporal write never creates nodes: the caller must create them, as `create_rel` requires.
- Default the code applies today: the nodes are created and not recorded; `verify()` would report them as
  unrecorded writes (finding F-0503, not yet observed live).

### HD-0502 Is the temporal index inside the ledger's guarantee?
- Owner: human
- Question: CONTEXT.md:75-76 says a temporal edge is "subject to the revision ledger (via a Changeset temporal op)".
  At the pin a changeset can write temporal edges in the ledger's transaction and records
  `create_temporal_edge` with the triple, graph and time only (`LedgerApply.cls:637-640`). There is no op for a
  temporal delete, purge, bucket purge or row drop; engine temporal writes make no revision
  (`test_ledger_us11_temporal_coexist.py::test_temporal_writes_and_purges_create_no_revisions`); replay ignores
  temporal records (`replay.py:170-208`) and `verify()` never reads the temporal index. Redaction does match temporal
  records by tenant (`LedgerRedact.cls:97`). What does the ledger promise about temporal edges?
- Options: (a) outside: temporal records are an audit trail only, and the glossary says so; (b) inside for changeset
  writes: records carry weight, attributes and mode, replay rebuilds the temporal edges, and verify compares them;
  (c) fully inside: deletes and purges get ops too, and engine temporal writes are refused in strict mode.
- Default the code applies today: (a) in practice, with the glossary saying otherwise. The orchestrator's replay
  module should treat temporal records as present in history, matched by redaction, and absent from replay and
  verification.

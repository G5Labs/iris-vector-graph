# Decisions: module 09 (native Cypher executor)

### HD-0901 Should a running engine notice a revoked table right or a dropped adjacency index?
- Owner: human
- Question: the native gate asks three facts once per engine and keeps them: SELECT on the four graph tables
  (`engine._native_privileges`, never asked again), the adjacency index (`_adjacency_indexed`, asked again only by
  `initialize_schema`) and the executor's plan version (same). The native path reads globals, which SQL rights do not
  guard (ADMIN_GUIDE, "What is the boundary"). After `REVOKE SELECT` on `rdf_props`, or after another process drops
  `idx_edges_adj`, a long-lived engine keeps reading natively. Must a revoke or an index drop take effect on engines
  already running, and how fast?
- Options: (a) keep the per-engine caches (today) and document that a revoke needs new engines; (b) re-ask on a timer
  or every N reads; (c) have `Graph.KG.Cypher.Exec.Run` check the rights itself per process and user, as spec 253
  FR-011 says (also closes F-0908); (d) for the index, check `Graph.KG.Adjacency.Indexed()` inside `Run`.
- Default the code applies today: (a), undocumented. The plan version is safe anyway: `Run` refuses a plan of another
  version (NAT-X9).

### HD-0902 Should shadow mode fail when the native path raises an error?
- Owner: human
- Question: spec 253 US1 says shadow mode "fails on any difference"; US4 and FR-007 say any native failure falls back
  to SQL with a warning once per reason. In shadow mode a native exception today makes `_try_native` answer None, the
  SQL path answers, and nothing is compared (`query.py:2071-2073`), so a native defect that raises is invisible to a
  shadow run except for one warning line. Should shadow mode raise `NativeMismatch` (or another error) when the native
  path raises?
- Options: (a) keep the fallback in shadow mode (today); (b) raise in shadow mode only; (c) count native failures and
  report them at the end of a shadow run without raising.
- Default the code applies today: (a).

### HD-0903 What may a native read answer while another writer's transaction is open?
- Owner: human
- Question: a native read takes no lock and no snapshot (NAT-T4.6). It reads `^KG` (adjacency and labels), the
  `rdf_props` storage globals and, for an id or property start, the node and property rows through SQL, at moments
  spread over the walk. A writer's open transaction is visible to it (P-0002), and may be visible in part: a new
  edge's `^KG` entry before its far node's label, or a property changed between two reads of the same run. Spec 253
  speaks only of the caller's own transaction. Is "whatever each store holds at the moment it is read" the promise,
  as on the SQL path at IRIS's default isolation, or must a read see a writer's transaction all or nothing?
- Options: (a) dirty, per-store reads, documented as equal to the SQL path's default isolation; (b) readers wait on
  a lock writers hold (cost: every native read); (c) a version check before and after the walk, retrying when a
  writer committed in between (does not cover uncommitted writes).
- Default the code applies today: (a), undocumented for the native path.

### HD-0904 Should a compiled plan that fails while running be set aside?
- Owner: human
- Question: ADR-0014 says the interpreter answers every shape that is not compiled, failed to compile or cannot be
  recorded. A compiled class that compiles but raises while it runs (a generator defect, a class deleted under a
  running read) is not covered: the error leaves `Run`, the engine falls back to the SQL path (NAT-T6.1), and the entry
  stays "ok", so every later read of that shape fails natively first and is answered by SQL. Should such a failure mark
  the entry so the interpreter answers the shape next time?
- Options: (a) keep today's behaviour (SQL answers, one warning per reason per engine); (b) catch errors from `Walk1`
  in `RunA`, mark the entry failed and re-run the walk interpreted; (c) mark the entry failed but let SQL answer this
  read.
- Default the code applies today: (a).

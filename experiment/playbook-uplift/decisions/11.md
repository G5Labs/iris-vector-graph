# Decisions: module 11 (ledger core)

### HD-1101 What should a node change do when only a named graph holds the id?
- Owner: human
- Question: the ledger keeps nodes in the default graph (4.6.0 R281/R290) but asks whether a node exists by id in any
  graph (`Graph.KG.LedgerApply.NodeExists`, `iris_src/src/Graph/KG/LedgerApply.cls:79-84`), on purpose for edge end
  nodes (`:86-95`). For a node id that only a named graph holds, what should `create_node`, `upsert_node`,
  `set_prop`, `add_label`, `remove_*` and `delete_node` (plain and detach) do?
- Options: (a) treat the id as not found for node changes (refuse with `node_not_found`), keeping the graph-blind
  check for edge end nodes only; (b) create the default-graph node row first, then apply the change, with a record;
  (c) keep today's behaviour and document it.
- Default the code applies today: (c), undocumented. `create_node` is refused as `node_exists`; `upsert_node` with no
  labels or properties writes nothing; `set_prop` writes a default-graph property row for a node with no
  default-graph row (rdf_props has no foreign key); `add_label` fails on the `fk_labels_node` foreign key with
  "insert label failed"; `delete_node` deletes nothing and records a `delete_node` with an empty prior snapshot
  (finding F-1105). Tests cover only an id held in both graphs
  (`tests/e2e/test_460_r290_ledger_node_ops_graph_e2e.py`).

### HD-1102 Should disable() and set_strict() refuse a caller's open transaction, as enable() does?
- Owner: human
- Question: 4.7.0 made `enable()` and `redact()` refuse a caller transaction that holds a write
  (`iris_vector_graph/ledger/client.py:268-279`), because over a separate Native API connection they ran outside it.
  `disable()` and `set_strict()` were not changed (`:299-309`): they run `Graph.KG.Ledger.Disable` / `SetStrict`
  through `engine._iris_obj()`, which is the caller's own process for an engine made on a connection without stored
  credentials and another process for a `from_connect` engine (`iris_vector_graph/engine.py:1894-1941`). So the
  caller's rollback undoes a disable on one kind of engine and not on the other.
- Options: (a) refuse both inside a caller transaction (as enable); (b) join it explicitly (run on `WriteTxn.native()`,
  as commit does); (c) keep today's behaviour and document the difference.
- Default the code applies today: (c), undocumented.

### HD-1103 Should strict mode be enforced by the server, or stay a Python-only check?
- Owner: human
- Question: strict mode is checked only by `iris_vector_graph.ledger.guard.LedgerGuard` before engine writes
  (`iris_vector_graph/ledger/guard.py:75-80`). It caches the state for 5 s per engine and fails open when it cannot
  read it (`:38-59`). The server's own writers (`Graph.KG.Eraser`, `Graph.KG.TemporalIndex`, the SQL procedures),
  raw SQL, `BulkLoader`, the GraphQL mutations and other clients are not held to it. The contract documents
  "BulkLoader and raw SQL are not guarded" (`specs/213-graph-revision-ledger/contracts/ledger-api.md:92-93`); the
  user guide says strict mode "refuses them" for "create_node, create_edge and the other methods"
  (`docs/USER_GUIDE.md:1107-1109`).
- Options: (a) keep a client-side, fail-open guard and document precisely which surfaces it covers; (b) add a
  server-side check (for example in the structural tables' triggers or the ObjectScript writers) that refuses
  unrecorded writes while strict is on; (c) make the guard fail closed when strict cannot be read.
- Default the code applies today: (a), with two Python write paths outside the guard (finding F-1108).

### HD-1104 Should the ledger's settings be changeable after the genesis?
- Owner: human
- Question: `max_ops` (the size limit) and `recon_bound` are written only by the genesis
  (`iris_src/src/Graph/KG/Ledger.cls:289-292`). `enable()` on an enabled ledger ignores every argument (`:254-260`).
  Re-enable after disable ignores `max_ops` and `recon_bound` but overwrites strict mode with the value passed, which
  defaults to off (`:271-275`), so `set_strict(True)`, `disable()`, `enable()` leaves strict off, and a
  `set_strict(True)` made while disabled is lost on re-enable. Is this the intended lifecycle?
- Options: (a) add setters (or let `enable()` update the settings it is given) and keep strict mode unless the caller
  passes a value; (b) keep settings fixed at genesis and document it, including the strict reset; (c) keep today's
  behaviour undocumented.
- Default the code applies today: (c).

### HD-1105 Should post-commit properties be recorded by the ledger?
- Owner: human
- Question: `post_commit_properties` (spec 218, "Approach A: direct SQL, no new revision",
  `iris_vector_graph/ledger/client.py:430-487`) write `rdf_props` rows outside the revision: they are unrecorded
  writes to a governed store, so `verify()` reports them (upstream comment in
  `tests/e2e/test_470_ledger_caller_txn_e2e.py:218-219`), redaction's liveness check sees them, and replay never
  rebuilds them. They are written outside the head lock and, with no caller transaction, in a second transaction.
- Options: (a) turn them into `set_prop` records of the same revision (the revision id is then known only after the
  revision row is written, so the server would have to substitute it); (b) keep Approach A and document that every
  post-commit property makes `verify()` diverge until adopted; (c) drop the feature.
- Default the code applies today: (b) without the documentation; see also finding F-1101 (a replayed commit writes
  them again).

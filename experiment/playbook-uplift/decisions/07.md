# Decisions: module 07 (text search and fusion)

### HD-0701 Must a BM25 Build (and Drop) exclude writers and be all-or-nothing?
- Owner: human
- Question: ADR-0007 says schema 2 "does every write under an index-level lock in a transaction", but the spec's
  requirement (FR-019) names only Insert and Delete. `Build` kills `^BM25Idx(name)` and rewrites it with no lock and
  no transaction; `Drop` kills with no lock. While a Build runs, what may an Insert, a Delete, a second Build, a Drop or
  an Upgrade on the same name do, and may a stopped Build leave a partial index?
- Options: (a) Build and Drop take the write lock (and set a "building" flag that refuses writers), keeping the
  rebuild outside a transaction; (b) Build builds under a temporary name and swaps it in at the end, so readers and a
  stopped Build never see a partial index; (c) keep today's behaviour and document that Build and Drop must not run
  beside other writers.
- Default the code applies today: (c), undocumented. A concurrent Insert during Build sees no document count, creates
  a fresh schema-2 header, and Build's final `Set N` overwrites it; a stopped Build leaves postings with no header,
  which the next Insert treats as a new index.

### HD-0702 Which reciprocal-rank-fusion rule is the product's?
- Owner: human
- Question: five surfaces fuse a vector list with a text list by rank, with three rules for an item one list lacks
  and two different text lists:
  engine `kg_RRF_FUSE` (BM25 index; missing item at place `len(leg) + c`, so it adds `1/(2c + len)`),
  SQL `kg_RRF_FUSE` and `/hybridSearch` (docs-table term counts from `kg_TXT`; missing item at place 10^9),
  `CALL ivg.retrieve` and `RRFFusion.fuse_results` (missing item adds 0). The engine method and the SQL procedure
  share a name and can rank the same query differently. Which rule, and which text list, is the contract?
- Options: (a) standard RRF everywhere (missing adds 0); (b) keep per-surface rules and document each; (c) adopt the
  engine rule everywhere (it is pinned by `tests/e2e/test_460_rrf_fuse_ivf_e2e.py`).
- Default the code applies today: (b), with only the engine rule documented by a test.

### HD-0703 Is spec 044's kg_TXT-to-BM25 fallback still wanted?
- Owner: human
- Question: spec 044 FR-012 and User Story 5 say that when iFind is unavailable `kg_TXT` uses a BM25 index named
  `default` before the LIKE fallback. No code does this at the pin: `kg_TXT` goes straight to LIKE. Spec 230 later
  re-keyed `docs` and gave `kg_TXT` a graph, and a BM25 index named `default` covers one graph only.
- Options: (a) implement FR-012, choosing the BM25 index recorded for the requested graph; (b) strike FR-012 and US5
  from the spec; (c) leave the spec as draft.
- Default the code applies today: no BM25 fallback; LIKE substring matching with every score 1.0.

### HD-0704 Is `__stop__` a reserved BM25 index name?
- Owner: human
- Question: the stopword list lives at `^BM25Idx("__stop__")`, beside the indexes. `Build`, `Insert`, `Drop` and
  `Search` accept the name `__stop__`; `Drop("__stop__")` deletes the stopword list (rebuilt on the next tokenize) and
  `Build("__stop__", ...)` mixes an index into it. `List()` skips the name. Should writers refuse it, or should the
  stopword list move out of the index global?
- Options: (a) refuse `__stop__` in Build/Insert/Delete/Drop and in `BM25BuildInput`; (b) move the stopwords to their
  own global; (c) leave it.
- Default the code applies today: (c).

### HD-0705 Are `TextSearchEngine`, `RRFFusion` and `HybridSearchFusion` supported public API?
- Owner: human
- Question: all three are exported from `iris_vector_graph` (`__all__`) but none is in `docs/API_REFERENCE.md`.
  `TextSearchEngine` still uses the `%FIND(col, ?)` predicate the repo calls invalid elsewhere, reads an unqualified
  table, and has no graph scope. Fix them to the product's rules, deprecate them, or remove them?
- Options: (a) bring them under the graph-scope and failure rules and document them; (b) deprecate with a warning;
  (c) remove from `__all__`.
- Default the code applies today: exported, undocumented, unscoped.

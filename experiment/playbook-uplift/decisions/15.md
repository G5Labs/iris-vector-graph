# Decisions for the human: module 15 (INT)

### HD-1501 Should a FHIR sync be governed by the ledger?
- Owner: human
- Question: a FHIR sync, rebuild and reinterpret write nodes, labels, properties and edges of the FHIR graph from
  ObjectScript (`Graph.KG.FHIRGraph`), with no ledger record. Strict mode is enforced only in the Python guard
  (`iris_vector_graph/ledger/guard.py:75-80`), and `FHIRGraph.cls` never reads `^IVG.Ledger("meta","strict")`, so strict
  mode does not refuse them. `docs/USER_GUIDE.md:1107-1109` says strict mode refuses writes outside the ledger.
- Options: (a) a FHIR graph is a rebuildable projection of the repository and is exempt from the ledger; document the
  exemption and make `verify()` skip FHIR graphs; (b) refuse rebuild, sync and reinterpret while strict mode is on;
  (c) record each batch as a ledger revision.
- Default the code applies today: (a) without the documentation: the writes happen, are not recorded, and `verify()`
  would report them.
- Cited by: INT-F11.

### HD-1502 Should erasing a FHIR graph stop its sync task?
- Owner: human
- Question: `EraseGraph` keeps the `fhir_graphs` row and sets both watermarks to 0 (`Eraser.cls:1151-1180`). A scheduled
  `Graph.KG.FHIRGraphSyncTask` keeps running, and its next run re-projects the whole repository into the graph. When the
  FHIR graph is erased for a tenant (and then to be redacted), the content comes back on the next tick, and redaction
  refuses a live target.
- Options: (a) erase also unschedules the task (or clears `task_id`); (b) erase leaves the task, and the docs say an
  erased FHIR graph refills itself unless it is unscheduled first; (c) a separate "deregister" command removes the
  registration, the task and the content together.
- Default the code applies today: (b) without the documentation.
- Cited by: INT-F10.3.

### HD-1503 What happens when an erase runs during a FHIR sync?
- Owner: human
- Question: `Graph.KG.Eraser.EraseGraph` takes no lock, and in particular not the sync lock `^IVG.FHIRGraph(graph)`. A
  sync running in another process can commit its next batch, and move its watermark, after the erase commits. The graph
  then holds the rows of that batch only, with a watermark past rows it no longer has, until a rebuild. This is
  reasoned from the code (`Eraser.cls:47-57`, `FHIRGraph.cls:1964-1966`), not observed.
- Options: (a) erase of a FHIR graph takes the sync lock and refuses (or waits) while a sync holds it; (b) a sync
  re-checks its watermark under the lock before each batch and stops when it went back; (c) leave it and document that
  a FHIR graph must be unscheduled and idle before an erase.
- Default the code applies today: no coordination.
- Cited by: INT-F10.4 and the open cell (FHIR graph, busy, erase).

### HD-1504 Should one unreadable FHIR resource block its graph's sync?
- Owner: human
- Question: a resource whose body is not JSON, nests deeper than 64 levels, or has more than 10,000 json-link matches
  makes `ResyncKey` throw (`FHIRGraph.cls:2380-2397`, `:2976-2977`, `:2983-2988`). Its batch rolls back and the
  watermark stays, so every later sync fails on the same batch and no later change reaches the graph. With the default
  json links (they include an extension entry) every resource body is read.
- Options: (a) record the key in `fhir_unresolved` (or a new reason) and continue; (b) keep failing, and document how
  an operator finds and fixes the resource (`last_error` names it); (c) skip only after N repeated failures.
- Default the code applies today: (b), with the key named in `last_error` but no documentation of the stall.
- Cited by: INT-F5.10.

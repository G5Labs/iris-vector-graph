# Decisions for the human: module 08 (Cypher on the SQL path)

Cited from `ontology/08-cypher-sql.md` as `open:HD-08kk`.

### HD-0801 Where and how should ledger strict mode refuse a Cypher write?
- Owner: human
- Question: strict mode is enforced only by the Python `LedgerGuard` of each engine
  (`iris_vector_graph/ledger/guard.py:38-80`). It caches the ledger's setting for 5 s and fails open when the probe
  fails. IRIS itself does not refuse (`Graph.KG.Ledger.SetStrict` only sets `^IVG.Ledger("meta","strict")`). The
  contract (`specs/213-graph-revision-ledger/contracts/ledger-api.md:82-92`) says the guarded calls "raise
  `LedgerStrictModeError` and change nothing", with no window and no fail-open case. The redaction and erasure
  modules rely on knowing which writes the ledger saw.
- Options: (a) keep the client check, and document the 5 s window and fail-open in the contract and USER_GUIDE;
  (b) fail closed: refuse the write when the probe fails, and re-read the setting on every write (cost: one class
  call per write); (c) enforce in IRIS (a check in `Txn_Begin` or a table trigger), so raw SQL and every client are
  covered.
- Default applied today: (a) without the documentation: cached for 5 s, fails open
  (`tests/unit/test_ledger_guard.py::test_cache_honours_ttl_and_refresh`, `::test_probe_failure_fails_open`).

### HD-0802 Does a mapped label belong to every graph?
- Owner: human
- Question: `map_sql_table` maps a label to an outside SQL table for the whole namespace. The graph filter of a scoped
  query is added only to the four graph tables (`translator.py:404`, `719-779`), so under `USE GRAPH 'g'` a mapped
  label still answers every row of its table. The glossary says graphs are isolation units (CONTEXT.md:27-37); the
  mapping docs say nothing about graphs.
- Options: (a) a mapped label answers under every graph scope (document it); (b) a mapping names its graph, and other
  scopes see no rows; (c) refuse a mapped label under `USE GRAPH` with a named graph.
- Default applied today: (a), undocumented.

### HD-0803 Is `sql/operators.sql` product code?
- Owner: human
- Question: `sql/operators.sql` defines `kg_KNN_VEC`, `kg_TXT`, `kg_RRF_FUSE`, `kg_GRAPH_PATH`, `kg_RERANK` and `kg_PPR`
  with no graph argument, unqualified table names and a label join without `graph_id`. Nothing in the package or
  setup loads it (the live procedures are in `iris_vector_graph/schema.py:2437-2526`;
  `scripts/deploy_production.py` loads `sql/operators_fixed.sql`). The uplift's denominator counts it as product SQL.
- Options: (a) delete it; (b) keep it as a reference and mark it as not deployed; (c) bring it in line with
  `schema.py` (graph-scoped) and load it.
- Default applied today: it stays in the tree, unloaded.

### HD-0804 Should `CREATE CONSTRAINT` / `CREATE INDEX` be refused rather than accepted as a no-op?
- Owner: human
- Question: `execute_cypher` answers any text that starts with `CREATE CONSTRAINT`, `DROP CONSTRAINT`, `CREATE INDEX`,
  `CREATE TEXT INDEX`, `CREATE RANGE INDEX`, `CREATE POINT INDEX`, `DROP INDEX`, `CREATE FULLTEXT` or `CREATE LOOKUP`
  with an empty result and does nothing (`iris_vector_graph/_engine/query.py:1886-1897`). A client that creates a
  uniqueness constraint believes it is enforced. It exists so that Neo4j tools that send such DDL keep working.
- Options: (a) keep the silent no-op and document it; (b) answer with a warning in `metadata`; (c) refuse with an
  error that says IVG keeps no constraints.
- Default applied today: (a), undocumented in USER_GUIDE.
